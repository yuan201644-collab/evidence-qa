## 四、关键发现：瓶颈是 LLM 通道，不是实现

同一批题、同一候选版本，**唯一差别是有无节流**：

| 套件 | 无节流（首轮） | 节流后 | 说明 |
|---|---|---|---|
| T3 | 429 达 20/43 轮，仅 2 条 SQL | 429 降至 2/43，18 条 SQL | 恢复 |
| T4 | 单条探测 6.8 s 即 429 | 429 降至 2/20，16 条 SQL | 恢复 |
| T5 | **20/20 全 429，0 条 SQL** | **20/20 全 SQL，0 个 429** | 完全恢复 |

本机 `.env` 用的 `LLM_MODEL=glm-4.5-flash`（`https://open.bigmodel.cn/api/paas/v4`）**属备用档**；A 的 `runtime_manifest` 记录正式模型为 `deepseek-v4.1-flash`。glm 免费档对连续请求的速率限制极严：无间隔连发时，从第 3–4 次起即持续 429。

**结论**：上一版报告把 T4/T5 的 429 记为"大 schema 的 token 级限流、降速无解"，本轮**修正**为：加间隔 + 退避后可以跑通；瓶颈在通道配额，不在实现。要完全消除 429，仍建议换 A 的 DeepSeek 正式通道。
