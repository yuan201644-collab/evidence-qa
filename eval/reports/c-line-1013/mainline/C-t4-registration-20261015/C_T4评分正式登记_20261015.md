### 4.1 ⚠️ 行尾策略与哈希的两个形态（跨平台复核必读）

仓库 `.gitattributes` 声明 `* text=auto eol=lf`，因此**入库后拿到的是 LF 形态**。
本登记中由 CRLF 来源复制而来的文件（评分 JSON 及其哈希自校验对象）
在本机工作区是 CRLF、**入库后是 LF，两者哈希不同**。

`SHA256SUMS.txt` 因此对每个文件给出两个形态：

- **`[LF]`** —— 入库形态。**跨机器/跨平台复核时用这一列。**
- **`[本地]`** —— 本机工作副本形态。

⚠️ 另一处必须知道的口径差异：评分文件内部的
`raw_answers_sha256` / `freeze_sha256` / `question_pack_sha256` / `reference_queries_sha256`
是**采集当时在本机工作区算出的值**（CRLF 形态）。
在本机复核时它们与 `[本地]` 列一致（登记脚本 12/12 PASS 即验证了这一点）；
但**在 clone 出来的仓库里直接 `sha256sum` 会得到 `[LF]` 列的值**，与评分文件自述值不同。
这是行尾归一化导致的**已知且可解释的差异**，不是数据不一致；
判定数据是否被改动，**以 `SHA256SUMS.txt` 的 `[LF]` 列为准**。
