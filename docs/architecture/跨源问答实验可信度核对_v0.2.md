- 新旧流程对照协议 v0.3 已规定配对运行、运行前冻结、题包与 Gold 角色分离、双人匿名盲审、独立 trace 审计及合成数据的解释边界。
- 运行器、解析器和封存后评分器已补齐可验证性边界。本次静态代码审查通过；审查者未读取任何确认性题包、Gold 或答案输出。
- 全部项目源测试通过；`compileall` 与 `git diff --check` 通过。以上只验证实现和评测工具，不代表新架构效果或在线端到端验收。
- 实现源码与评分器清单共 85 个文件，SHA-256：`dac1c5a101ab1f65bb4dee7e1920280fb3b5bca76c31e0322377981475e9e82e`。题目、Gold、代码、运行登记和封存输出均须分别保存哈希；运行前后不得覆盖历史文件。

## 本轮新增的可信度保护

1. 客户编号缺失、空白或空值哨兵时不接受跨源合同映射；工单题目文本必须且只能出现登记的同一工单号。
2. 合同阈值须与当前设备关联；异设备编号、相似设备名、特别/补充约定和重大故障例外不能被单一候选数字绕过。无法按明确条款确定时停止判断。
3. 有重排 trace 时，文档依据仅从最后一次重排候选中取；最终候选未命中合同，不回退到生成答案的引用。
4. A/B 原始输出评分在封存之后执行。评分器核对外部封存哈希、原始输出哈希、运行前清单和随机调度表，并将运行记录中的工单号与冻结题目匹配。
5. 评分器要求显式提供题目和 Gold 的外部 SHA-256 锚点；题目哈希须与运行前登记的运行包问题文件一致。Gold 不自动搜索，不随系统请求发送；评分写入运行目录之外的新文件。

上述保护由对抗式单元测试覆盖。它们属于评测有效性/错误拒答保护，不得写成准确率提升证据。

## 仍须完成的有效性步骤

1. 代码与协议冻结后，由未参与实现的编题者另建新业务域题包；另由不同核验者从结构化数据与合同原文复算 Gold。若任何审计信息暴露给实现者并引发修改，该包降为回归集，另造全新包。
2. 确认运行包仅含问题与输入数据；将 Gold 和独立复核依据置于包外并分别锚定哈希。预注册中固定模型端点、参数、代码/依赖、数据库与索引快照、只读权限、随机种子和题目调度。
3. 正式 A/B 每题各运行一次，不因质量选择性重跑、删题或修复输出。原始错误、超时和空答案全部保留；封存清单哈希由运行目录外的保管人锚定。
4. 封存后用固定评分器进行自动配对评分；另由至少两位未参与实现或出题的人独立盲审答案与证据，并由独立技术审计者检查真实 trace。AI 复核只可用于诊断，不能替代人类盲审。

## 对导师的准确口径

目前可以说：**“我们已把跨源关系校验、文档阈值适用性、早停与封存评分做成可测试的机制，并通过了代码和评测工具审查；v0.3 因已暴露仅作回归，确认性新旧流程对照仍待全新题包、独立 Gold 复核、真实配对运行和人类盲审完成。现在没有可报告的新架构效果结论。”**

实验完成后只能按证据说“在这批冻结的合成题上的配对观察”；不外推真实业务，不称总体准确率提升、统计显著或赛题整体验收通过。远程模型权重修订号目前不可核验；若平台未提供服务端 token/费用记录，则明确标为未测。
