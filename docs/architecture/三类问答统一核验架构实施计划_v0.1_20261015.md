## 1. 目标与授权边界

将最先用于跨源工单—合同问题的事实核验架构，扩展到数据库问数、文档问答。三条路径共用“明确事实 → 执行取证 → 按适用规则检查 → 登记状态及证据 → 组织回答”的机制，使用各自的查询与检索工具。

现有多轮上下文、纠错改写、主动澄清、表字段定位、多表查询、SQL 修复、文档解析与目录切片、原文引用、分页导出、登录隔离均列为保留能力。统一卡片只是展示端，不能替代实际架构接入。

用户于本轮确认新增：标准问答默认使用项目 RAG；手动“深度检索”可由 KAG 补充 RAG 候选，再由项目核验与回答器统一处理。当前助手只负责与 KAG 支线执行者保持接口交接，不实现 KAG 调用、不新增 KAG Python 占位、不配置 KAG。本轮获准实现三类问答的共同账本与响应展示，因此会新增 v2 可选响应字段；修改不改变 AskRequest、业务路由、原 SQL/RAG 处理器或跨源业务判定。本轮不提交、推送或合并。

## 3. 统一运行方式

```text
当前用户、会话与本轮原话
  → 接续上下文、保留原文、纠错标准化、必要澄清
  → 明确待确认事实、条件、来源范围及依赖
  → 问数工具 / 文档工具 / 既有跨源任务
  → 适用的代码检查与证据关联
  → 本轮事实账本
  → 回答、事实状态、来源证据、真实处理记录
```

- 普通问数沿用 SQL 链路；普通文档问答沿用 RAG 链路；跨源保留关系和口径检查。
- 三路共享事实计划、执行结果和证据状态的规则；各自提供适用的任务处理器。复杂表格作为有范围的结果事实，不为每一行单独调用模型。
- 输入保留原话、接续后的问题和标准化问题；不得因新增规划而丢弃已澄清的条件或原始业务名词。
- 请求头只控制新展示字段的序列化；实际核验执行不依赖用户是否要求展示卡片。
- 本轮账本按请求隔离。追问可以继承问题条件和查询状态，不能把历史证据索引当作本轮证据；对象、时间或口径变化后，重新取得受影响事实及下游结论。

## 5. 状态及证据的约束

1. 分开记录任务终态、事实支持、业务结果、证据关联。确认“超时”可以是事实有证据支持，同时业务不达标；明确的否定事实不自动算系统失败。
2. 检查结果只来自实际结果记录。`*_checked` 开关、流程完成、HTTP 200 或检索命中均不能推出事实正确。
3. 检查结果允许未确定、未执行；真正不适用的检查须与缺少配置区分。缺少可选检查记录，不应一律把可用回答改成拒答。
4. 查询证据分别覆盖原始行、统计结果和零行断言。零行只能证明当前查询条件下没有命中，不能扩张为全库/全业务绝不存在。
5. 文档证据需有文档身份、文本版本及原文位置。数值、单位、适用范围、条件和例外决定是否支持所问事实；有引用不能直接判支持。
6. 模型参与的候选抽取或语义判断记录实际方法，不能标为代码独立证明。无法可靠核验时保留候选或不足状态。
7. 最终引用排序、去重后计算 `evidence_ref_indices`，与同一响应 `refs` 一起持久化；索引范围正确还需来源身份对应正确。
8. 单源新增结果级证据和三类覆盖值纳入 v2 设计。无新字段的旧响应继续可读；v1 客户端不接收 v2 扩展枚举。
9. 本轮先做事实项与来源关联，不宣称答案每句话均已独立核验；句子级标记需有额外明确关联。

## 6. 三路适配的重点

### 6.1 问数

- 目标事实包括所问指标、对象、时间、筛选、分组和排序；查询结果须能对应这些目标。
- 保留原有只读校验、表定位、关联语义检查及带错误信息的修复上限。
- 从最终成功执行记录读取 SQL、输出列/单元、完整性及实际检查结果。修复前错误保留在处理记录，终态以最终结果为准。
- 聚合值用查询执行及结果证据定位，不人为制造数据库行主键；详细结构在 B 阶段明确并纳入测试。
- 分页、完整导出和截断提示沿用原能力；不能把有引用但不完整的结果显示成完整清单。

### 6.2 文档问答

- 用问题及现有多跳规划明确待回答事实，复用已有 `retrieve_and_rank`、`generate` 及引用处理能力，避免再造重复检索循环。
- 事实候选保留支持片段、位置和条件。代码核对引用定位、逐字片段、值及单位等能检查的部分；语义支持不能只靠生成器自述。
- 一次请求合并证据后统一组织回答，保持现有多跳引用链；不为每条事实重新建索引或生成一份答案。
- “文档明确未约定”“本次有界检索未找到”“条款冲突”“工具失败”分别记录。
- 统一核心预留补充候选接口，标准请求不调用 KAG。深度模式的细节见配套交接。

### 6.3 跨源

- 保留已有工单—合同任务中的受控映射、客户、双有效期、设备范围、事件顺序及指标定义检查。
- 单源扩展不能放宽跨源前置依赖；关键条件不成立，依赖结论仍应停止。
- 深度检索只补充已允许合同/资料范围内的文档候选，不接管 SQL、映射裁定或最终业务结论。
- 已冻结代码、题包、评分和实验锚点不回写；新候选验证另留记录。旧题用于回归，不重新包装为未见题。

## 8. KAG 增量纳入本轮的具体范围

- 前端“标准问答 / 深度检索”是检索策略，与首页“问数 / 问答 / 跨源”方向、模型选择分别表达。
- 标准默认项目 RAG；深度手动选择，KAG 提供候选原文，项目完成融合、核验、统一回答与引用。
- 纯问数不新增 KAG 调用；跨源的深度检索继续受已确认的合同与文档范围限制。
- 主线预留请求模式、来源范围、事实目标、剩余预算、候选返回、状态、耗时和引用身份的接口。实际 OpenSPG/KAG 调用及服务配置交给支线执行者。
- 引用错挂修复、原文坐标映射、资料版本一致性和端到端时间预算为深度模式启用门槛。
- 自动发现缺口后触发 KAG 仅保留为后续实验方向；本次产品策略以用户手动选择为准。
