# 主线补齐内部接入约定 v0.1

更新日期：2026-10-07。本文定义主线补齐期间的内部模块接口；不改变 `app/contracts.py` 公共请求与响应。

## 数据流

```text
原问题 + session_id
  → 会话状态恢复
  → 标准化与语义澄清
  → QueryIntent
  → LinkResult（候选、依据、降级）
  → JoinPlan（候选外键路径与粒度风险）
  → 生成器接收受限 schema 提示
  → 原有 sqlglot 只读校验
  → SemanticCheckResult
  → 执行 / 澄清 / 有界失败
```

文档问答与既有跨源事实计划不强行调用 SQL 定位器。SQL 校验始终以完整 `SchemaCatalog` 为准；定位结果只限制生成器上下文，不构成执行授权。

## 私有数据模型和所有权

| 模型 | 创建者 | 消费者 | 生命周期 |
|---|---|---|---|
| `QueryIntent` | `SemanticClarifier` | 编排层、定位器 | 单次请求；只保留可确定要素 |
| `ClarificationDecision` | `SemanticClarifier` 或下游工具 | 编排层 | 请求结束；澄清时写入会话状态 |
| `SessionState` | `SessionMemory` | 编排层 | 进程内、有容量与过期上限；不是持久事实库 |
| `LinkResult` | `SchemaLinker` | SQL 流程、trace | 单次请求；候选分数不等同真实业务关系 |
| `JoinPlan` | `JoinPlanner` | 生成器、语义检查器 | 单次请求；关系仅来自元数据外键或受控规则 |
| `SemanticCheckResult` | `SqlSemanticValidator` | SQL 流程 | 单次 SQL 尝试；`unknown` 不得当作通过 |

`QueryIntent.source_question` 保留用户原始措辞，仅供定位器把原词别名与标准化后的表/字段名联合匹配；它不是新增业务结论或生成提示，也不扩展公共 HTTP 契约。这样可避免标准化把一个具体字段别名改成裸字段名后，被反向匹配到多个同名列。

这些模型位于 `app/nl2sql/planning_models.py` 或会话私有模块，不追加公共响应字段。步骤使用现有 `TraceStep`：推断材料写入 `output`，只有实际查询或检索命中进入 `hit`。

## 定位、关联与执行边界

- 定位先读取当前 `SchemaCatalog`、独立中文描述和别名文件；版本以活动 schema 元数据版本为准。外部语义召回只允许通过注入接口提供，不在 import 或构造时启动模型。
- 候选有上限：定位最多 8 张语义表；外键关系补全后最多 12 张；扩展最多 1 次。任何上限都属于工程预算，未测试前不表述为性能结论。
- 没有可用语义组件时允许关键词降级，必须在 `LinkResult.degraded` 留痕。候选歧义、元数据缺口或无法构造唯一业务路径时，停止自动选取，不按最高分或最短路径直接认定业务关系。
- SQL 生成器获得限定 schema 作为上下文；正式校验仍使用完整权威目录和只读规则。任何生成的 SQL 都必须通过现有 sqlglot 校验。
- 语义检查仅覆盖可由 AST 与目录确定的关系。超出检查范围返回 `unknown`，不把“检查器看不懂”包装成数据为空或语义正确。
- 所有模型调用须沿用已装配客户端的超时、重试和降级策略；结构化链路首版不增加独立模型规划调用。总生成重试仍由 `Nl2SqlPipeline.max_attempts` 统一限制。

## 兼容和会话边界

公共 API 保持 `AskRequest(question, session_id)` 与既有 `AskResponse`。新内部步骤依序加入 trace，并通过已有 `need_clarify` 表达澄清。会话存储按 `session_id` 隔离，有限容量、过期清理；用户明确开始新问题或取消时清除挂起澄清，不把模型输出写成已确认事实。多进程共享会话不在本版承诺范围。

## 实施状态

本约定只固定接入结构和安全边界，不证明运行正确。代码与文档须逐项标记“已实现、未测试”；恢复测试之前，不执行单元测试、真实数据库查询、在线试问、模型调用或跑分。
