# 主链路事实核验原型：阶段一实现与验证记录 v0.1

日期：2026-10-04  
状态：最小内部原型已接入并完成合成演示库在线验证；不代表真实业务泛化、赛事正式评测或中级任务验收。  
范围：仅限显式启用的 `CROSS_SOURCE_FACT_PLAN_ENABLED=1` 与 `CROSS_SOURCE_DEMO_ENABLED=1` 路径；未修改公共响应契约、默认后端、默认路由或团队任务书。

## 1. 结论

现有通用编排入口现在可对工单—合同复合问题建立私有事实任务依赖，调用项目真实 NL2SQL 流程、真实 RAG 检索—重排—生成流程，再由代码逐项校验对象映射、客户范围、两类有效期、合同条款和事件时间。验证通过的事实才可供后续任务使用；缺少关系或事件时停止产生肯定结论。

该结果证明的是“最小原型在一套合成数据上的端到端链路可运行”，不是架构创新效果已被证明。当前实验未与旧链路做同条件对照，也未使用未曝光留出题、真实业务数据或比赛正式数据库，故不报告准确率提升，也不代表赛题中级任务四/五完成。

## 2. 实现边界与代码落点

| 文件 | 本轮职责 |
|---|---|
| `app/fact_planner.py` | 为工单时限问题生成事实任务及依赖关系。 |
| `app/fact_executor.py` | 依拓扑顺序运行任务；前置事实未受支持时早停；只采纳当前工具 trace 中真实出现的证据。 |
| `app/evidence_ledger.py` | 区分候选来源、受支持事实与最终响应证据；同一来源位置出现摘要和完整切片时保留更完整原文。 |
| `app/cross_source_fact_plan.py` | 绑定隔离库 NL2SQL 与合同 RAG；确定性核验 SQL 键连接、映射依据、客户、映射/合同有效期、条款口径、事件顺序和时长。 |
| `app/orchestrator.py` | 只在两个显式开关同时开启时，替代合成演示路由的单工具执行，跑私有事实计划；默认关闭时保持原路径。 |
| `tests/test_fact_executor.py`、`tests/test_evidence_ledger.py`、`tests/test_cross_source_fact_plan.py` | 覆盖任务依赖、证据绑定、受控编号连接、有效期、零行元数据及跨源边界。 |

文档检索由隔离适配器按已核验的合同编号过滤，实际执行项目 RAG 的混合检索、重排与生成。确定性条款抽取只读取真实重排候选的完整源切片，不采信生成答案自述；引用卡片仍带原切片偏移。结构化链路仍使用项目 SQL 生成、AST 校验、只读执行与 trace。

## 3. 在线验证记录

运行方式：在当前工作区启动的独立 `cross_source_demo` PostgreSQL 容器及数据上，通过 `build_default_orchestrator().answer(...)` 调用项目应用链路。数据库连接为只读且设置隔离 schema 搜索路径；合同索引仅写入独立演示库。未重载、清空或修改默认数据。调用均为真实 NL2SQL / RAG / 模型运行，不是 mock 或标准答案回放。

| 工单 | 实测结果 | 关键 trace / 核验 |
|---|---|---|
| `WO-2026-0001` | 设备 DEV-001，适用合同 HT-MNT-2026-001；时限 8 小时；受理至恢复 27,600 秒（7 小时 40 分），判定满足。 | 实际 SQL 与 RAG trace；文档节点 `supported`；最终对齐记录显示受控依据 `explicit_equipment_schedule`、客户范围与双有效期均已核验；最终结论绑定 SQL 与文档来源。 |
| `WO-2026-0005` | 合同映射/合同有效期未覆盖工单日期；回答无法判断。 | 映射节点 `insufficient`，不调用文档检索，不产生肯定结论。 |
| `WO-2026-0006` | DEV-006 与 DEV-005 名称相同，但编号映射查询为零行；回答无法判断。 | 实际执行的精确设备编号查询返回 `row_count=0`，trace 增加由执行元数据构造的 `cross_source_absence_check`；不按同名设备套用合同。 |
| `WO-2026-0007` | 缺少 `service_restored` 事件；回答无法判断。 | 实际 RAG 条款节点受支持；事件节点因终点事件缺失而停止，最终对齐节点不执行。 |

上述 4 题都是开发样例中的已曝光合成题，仅用于证明链路可运行及检查失败行为，不可视为盲测成绩。正例输出引用的完整合同切片同时含目标设备范围与 8 小时修复时限；事件证据来自该工单的受理及恢复记录。

## 4. 已执行的自动测试

- 定向测试：事实计划、账本、执行器、规划器和路由共 24 项通过。
- 全仓库测试：`PYTHONPATH=<项目根目录>`、`PYTHONUTF8=1` 下执行 `uv run pytest --import-mode=importlib -q`，295 项全部通过；有两条依赖库弃用提示，无失败。
- 采用 UTF-8 与 `importlib` 收集模式是 Windows 工作区的运行条件：默认收集会遇到测试快照同名模块冲突；未启用 UTF-8 时，既有 git 状态测试在读取非 ASCII 路径时可能出现子进程输出解码问题。这些是测试收集/环境差异，不是本原型代码失败。

单元测试和真实在线样例是两类证据：前者检查确定性边界；后者仅验证本地隔离演示链的实际接通。二者均不代替新题对照实验。

## 5. 限制与下一阶段

1. 事实计划目前只覆盖“工单修复是否符合合同 SLA”这一种复合问题；不是通用事实规划器。
2. 数据是小规模人工合成样例；SQL 生成稳定性、实际客户字段语义及文档形态尚未在赛题正式库或授权业务库上验证。
3. 尚未完成同数据、同问题、同工具条件下的旧链路/新链路对照，也没有未见题泛化结果；不将当前样例继续作为盲测集。
4. `AskResponse` 仍只有兼容的答案、trace 和扁平 refs；逐主张—证据绑定留在编排层私有状态，公共契约是否扩展仍需团队评审。
5. NL2SQL 各任务的生成、校验和执行 trace 会增加步骤与模型调用成本；本轮未做性能基准或成本对照，不作效率承诺。
6. 本原型不证明任务四在数十表及干扰项上的表/字段定位能力，也不证明任务五的复杂 JOIN / 聚合 / 子查询能力。

下一步应先审阅这份内部原型及其失败早停 trace，再决定是否冻结内部数据结构，以及是否设计全新未见题的同条件对照。公共契约、默认路由、默认后端或任务书如需变更，必须另行团队确认。
