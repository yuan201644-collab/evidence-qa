# 阶段 C 新留出集编制简报 v0.1

用途：交给未参与本轮工具实现、调试和旧题修正的组员，编制并复核下一批合成工单—合同问题。本文件是任务简报，不是已生成或验收的数据集。

## 已知情况

- 旧 H01–H07 已调试并经人工审阅，只能作回归。
- 对照规则已在 `阶段C对照规则冻结_v0.1.md` 记录。
- 目标是检查当前合成场景内真实运行输出与证据链，不证明统计显著、普遍业务泛化或赛事得分。

## 请编制者交付

1. 一份独立合成 PostgreSQL 快照：`schema.sql` 和各表 CSV，覆盖工单、设备、客户、合同、设备—合同映射和事件；主键、时区、日期区间端点口径明确。
2. 合同 ID 对应的 Markdown 原文，写清起始事件、结束事件、单位、时限和有效期。问题若无法回答，gold 写清具体缺失/冲突证据。
3. `questions.jsonl` 与单独保管的 `gold.jsonl`。逐题说明预期状态、计算依据、映射/合同选择依据、必须出现的证据位置或停止原因；说明与旧题的差别。
4. 数据、文档、问题和 gold 的 SHA-256；数据生成规则、独立答案复核者和日期。标准答案不放在运行请求或生成提示中。

优先考虑系统已实现、但未被新题检验的条件组合，例如恰好达到 SLA、映射日期边界、映射与合同有效期不同、缺少受理起点或客户号冲突。由编制者依据自然的数据关系决定是否纳入，不为凑类别造不自然问题。题数由团队依据工程目标决定并注明是小规模探索，不能冒充竞赛硬指标。

## 保密和冻结要求

- 不用改工单编号、设备名或合同号来伪装新题。
- 不把 gold 发给运行端，也不在看到候选回答后调整答案。
- 冻结数据后如改了程序，另建新版本、披露改动和题目是否已曝光；不再沿用“未见”标签。
- 复核人先确认每个答案有明确 SQL/事件/条款来源，再冻结全部文件哈希。

## 交接顺序

编制者分别保管问题/数据与答案 → 第二人核对事实和证据 → 冻结哈希 → 操作者按冻结规则运行 A/B → 匿名审阅真实回答与引用 → 解盲汇总。当前复现入口和能力边界见 `docs/architecture/阶段C验证与定向修复记录_v0.2.md`。本简报不代表外部成员已经执行。
