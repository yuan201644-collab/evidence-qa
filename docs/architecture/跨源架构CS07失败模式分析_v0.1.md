# CS07 跨源架构失败模式分析 v0.1

日期：2026-10-07  
数据：`2026Q4_fresh_cs07_v0.1`，16 题、两臂各 16 条回答。  
结果来源：两位匿名盲审、AI 辅助诊断和正式运行轨迹。AI 标签仅用于诊断，不替代第三位人类裁决。

## 一、当前结论

AI 辅助暂定汇总中，匹配参考臂和事实核验臂的严格通过数均为 5/16，差异为 0。新架构没有在本批题上显示出整体优势；同时，新架构的过度拒答明显偏高（暂定 11/16）。因此当前只能得出：

1. 事实核验流程能够识别部分客户冲突、双合同、失效映射、非受控依据和异常事件；
2. 事实核验流程仍会把“已经有明确映射和条款”的可答题误判为证据不足；
3. 当前没有足够证据证明新架构相对参考流程提高了题级效果。

## 二、主要失败模式

### 1. 把“文档片段没有重复设备编号”误判为“合同关系不明确”

多条新流程回答使用了类似“合同候选片段未明确覆盖该设备编号或设备名称”的理由，但其 SQL 证据已经给出：

- 设备编号与合同设备映射唯一；
- 映射依据受控；
- 设备客户与合同客户一致；
- 映射有效期和合同有效期覆盖工单日期。

这说明当前实现把“结构化映射已经成立”和“合同文档正文必须再次出现设备编号”混成了同一个条件。合同正文只要明确服务范围或条款适用范围，未必需要重复设备编号。

**影响**：新流程在本来可计算的题上提前拒答，形成过度拒答和引用理由不匹配。

### 2. 文档条款已召回，但条款解析失败后被包装成关系不确定

部分轨迹中已经检索到包含 `service_restored` 和时限的合同片段，但文档验证器没有抽取出可用限值，随后回答却把原因写成“设备覆盖不明确”。这会掩盖真正的能力边界：条款抽取或特别约定解析失败。

**影响**：评审无法区分“合同确实不适用”“检索没有找到条款”和“已找到条款但解析失败”。

### 3. 早停原因码与回答正文不一致

新流程能够记录结构化阻断原因，但最终答案有时使用了泛化理由，未说明到底是：

- 映射不存在；
- 映射过期；
- 合同未生效或已失效；
- 客户冲突；
- 多合同歧义；
- 事件缺失或倒序；
- 条款解析失败。

**影响**：证据可能真实存在，但引用与结论理由不匹配，导致证据维度被判不充分或引用不匹配。

### 4. 安全核验有效，但“未知”和“否定”边界不够清楚

“未从合同正文中再次找到设备编号”只能说明文档范围证据不足，不能直接推出“合同关系不存在”。当前新流程在部分题上把未知状态直接转成拒判，且拒判理由写成确定性否定。

**影响**：安全性提高的同时牺牲了可答题覆盖率，造成保守偏差。

## 三、建议的修复顺序

### P1：拆开三类状态

对每个候选合同分别记录：

1. `mapping_status`：无映射、唯一映射、多映射、非受控依据；
2. `temporal_status`：映射有效期和合同有效期分别为覆盖、过期、未生效；
3. `document_status`：未检索到、已检索但解析失败、已解析、条款冲突。

只有明确的阻断状态才能输出“无法判断”；“文档未重复设备编号”应进入待核验或限定回答，而不是直接写成关系不存在。

### P2：让回答直接投影结构化原因码

答案正文应由原因码和实际引用生成。例如：

- `mapping_expired` → “映射有效期截至……，工单日期为……，因此合同不适用”；
- `contract_sla_unparsed` → “已找到合同原文，但暂未能可靠解析修复时限，无法判断”；
- `customer_conflict` → “设备客户为……，合同客户为……，合同明确仅适用于……名下设备”。

禁止用“合同片段未覆盖设备”统一代替不同阻断原因。

### P3：增加可答正例回归

修复后先在已曝光题和开发题上验证：

- 唯一 explicit 映射 + 客户一致 + 双有效期覆盖 + 条款明确；
- 时长等于上限；
- 文档正文不重复设备编号但结构化映射明确；
- 条款召回成功但解析失败；
- 客户冲突、映射过期、多合同等应拒场景。

这些只用于回归，不重新计算 CS07 的正式效果。

### P4：重新编制全新题包

代码修复后重新冻结代码、规则、模型和比较器，再由独立编题人制作全新留出集。CS07 已经曝光，不能继续用于证明修复后的泛化效果。

## 五、已完成的第一项定向修复

在 `app/cross_source_fact_plan.py` 中已加入受控映射标记 `mapping_relation_verified`：

- 上游三表精确 JOIN、客户一致、映射依据受控、双有效期覆盖且合同 active 时，结构化关系被视为已核验；
- 合同正文不再被要求逐字重复设备编号或设备名称；
- 但合同正文若明确写出“不适用/不包括”并点名当前设备，仍然阻断；
- 未带该标记的手工/旧调用保留原保守行为，避免无依据放宽规则。

新增测试已覆盖“正文不重复设备编号仍可判断”和“明确排除仍拒判”，定向测试通过。该修复尚未重新运行 CS07，也不改变本轮正式或 AI 暂定结果；修复后的效果必须用全新冻结题包验证。

## 六、已完成的第二项定向修复

事实记录现在可携带内部 `diagnostic_code`，文档验证节点和轨迹会区分：

- `document_retrieval_empty`：文档检索没有返回可用内容；
- `document_reference_missing`：没有形成目标合同的可定位原文引用；
- `document_sla_unparsed`：已检索到原文，但没有可靠解析出修复时限；
- `document_sla_unstated`：原文明确未约定修复总时限；
- `document_sla_ambiguous` / `document_sla_override_unresolved`：存在多个阈值或优先约定，当前无法唯一确定；
- `document_scope_excluded` / `document_sla_scope_unproven`：合同明确排除设备，或时限条款未能证明适用当前设备。

最终回答会优先投影这些原因，而不是把所有情况都写成“合同覆盖不明确”。定向测试和全仓库测试均已通过。该修复同样尚未用于重算 CS07。

## 七、修复后开发回归新增观察

在 2026-10-06 的修复后开发回归中，两条流程各运行 12 道已曝光开发题，共 24 条，运行错误为 0，数据库与文档索引前后快照一致。该回归不打开 Gold，也不计入正式效果。

其中 ARC-10 同时暴露了事件倒序和合同原文未约定修复总时限：轨迹已经记录 `event_time_reversed`，但旧的答案投影按计划顺序先返回文档诊断，导致用户看不到更直接的数据质量阻断。现已调整为：只要事实计划记录了受控的跨源早停原因，就优先展示该原因；并补充事件倒序、关键事件缺失和设备主数据缺失的答案映射与单测。这样答案与 `cross_source_alignment` 轨迹中的首要阻断原因保持一致。

本次回归仍未覆盖“合同正文不重复设备编号”“明确排除设备”“已检索但未解析”三类新题，不能据此宣称这些边界已经在线验证通过。

## 四、对导师的简短口径

“新架构已经能把数据库事实、合同条款和跨源关系放在同一条核验链里，对客户冲突、过期映射和多合同等风险有更明确的拒判能力。但这批新题显示它目前偏保守：部分本来可以回答的问题被错误拒绝，严格通过率暂时没有超过参考流程。因此下一步不是继续堆技术，而是先把‘关系不明确’与‘条款解析失败’拆开，再用全新题重新验证。”
