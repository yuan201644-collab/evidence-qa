# 主链路接入与契约变更提案 v0.1

日期：2026-10-03
状态：供团队评审；不是已批准的接口设计，不代表已实现或已验收。
范围：讨论如何把“事实拆解—工具取证—事实核验—证据关联”接入现有主问答链路；本稿不修改代码、公共契约、默认后端或团队任务书。

## 1. 结论摘要

建议把下一阶段目标从“继续扩充工单—合同专用演示”调整为“在现有通用问答编排里试接一个最小事实核验层”。它应当让系统对复合问题先明确要回答哪些事实、事实之间依赖什么，再复用现有数据库查询与文档检索，最后检查跨源对象关系、时间和口径，并把每项结论连接到实际证据。简单问题仍走现有短路径；只有问题确实需要时才拆解、多跳或补查。

这是一项待验证的架构主张，不是既有能力的总结。当前代码已有 NL2SQL、单跳 RAG、多跳文档检索选项和隔离的工单—合同演示工具，但演示工具尚未接入通用事实计划/核验阶段；KAG 当前为模拟工具，不能作为已接通能力陈述。公共响应契约也尚无“答案中的哪项主张由哪些证据支持”的显式表达。

因此建议分两步评审：先批准内部原型边界与验收用例，不动公共接口；原型证明事实记录确有价值后，再由团队决定是否扩展公共契约。不要先定字段名，更不要仅因增加了一个“核验层”就宣称赛题中级任务四或五已完成。

## 3. 建议的目标流程

目标不是给每个请求都多加一轮模型调用，而是按问题复杂度走短路或核验路径：

```text
用户问题
   ↓
识别问题类型与必要事实
   ├─ 简单单源问题 → 现有 NL2SQL 或 RAG → 组织答案与引用
   └─ 复合/跨源问题 → 建立事实清单及依赖
                       ↓
             按事实调用 NL2SQL / RAG / 必要时多跳检索
                       ↓
             核对对象对应、有效期、时间/单位/指标口径
                       ↓
             为每项结论关联实际采用的证据
                       ↓
             回答 / 局部限定 / 请求澄清 / 有界停止
```

以“某工单是否满足合同修复时限”为例，内部至少需要确认：工单对应哪台设备；该设备在工单日期适用哪份合同；受理与修复完成事件的时间差是多少；适用条款规定的时限是多少。设备—合同关系不明确时，不应继续得出时限结论；时间顺序、时区、单位或条款适用范围不成立时，应限定或停止。最终“满足/超时”主张应关联映射与有效期、事件时间、合同条款等实际来源，而不是把所有检索命中都当作支持证据。

具体预算（最大补查次数、总耗时等）沿用现有已测配置或另行实验决定；本提案不把演示工具预算冒充赛事要求，也不预设未经测量的阈值。

## 4. 内部记录和证据语义

建议先在编排层内部表达四类对象，名字仅为讨论用，不是公共字段定稿：

| 对象 | 需要表达的内容 | 与现有概念的区别 |
|---|---|---|
| 事实任务 | 待确认的原子事实、依赖、候选工具、执行状态 | 不只是“接下来调哪个工具” |
| 事实记录 | 主体、属性/关系、规范值、时间范围、口径、校验状态 | 工具原始输出尚不自动成为可信事实 |
| 来源证据 | SQL 查询条件及结果定位，或文档片段定位；记录是否为候选或已采纳 | 不能将全量召回等同于答案引用 |
| 主张—证据关联 | 最终每个答案主张依赖哪些已采纳事实与证据 | 现有扁平 `refs` 无法表达共同支持和分项支持关系 |

对于 SQL 聚合结果，不虚构源行主键；应保留可复核的查询范围、过滤条件、字段、时间窗和聚合粒度。对“没有映射/没有事件”一类负证据，应由真实执行层的查询元数据构造，不采信生成文本自称的零行结果。跨源关系只能使用明确编号、受控映射或经确认关系，不以名称相同或语义相似代替关系证据。

## 5. 公共契约变更选项（供团队选，不在本稿代选）

| 选项 | 做法 | 优点 | 代价与限制 |
|---|---|---|---|
| A. 先做编排层私有原型 | 私有事实任务/事实/证据关联对象；工具仍使用当前 `ToolResult` 和 `TraceStep`；仅将结果投影为兼容响应。 | 不立即影响前端、接口消费者和团队契约；适合验证是否值得增加这一层。 | 外部看不到完整的逐主张证据关系，评测器只能从内部测试钩子检查；需避免私有状态与响应 trace 不一致。 |
| B. 私有原型通过后增加可选响应字段 | 在兼容旧字段的前提下，增加逐主张的结构化证据关系；旧版消费者可忽略该字段。 | 前端与评测器可明确呈现/核对“结论—证据”。 | 属公共接口变更，需同步后端、前端、评测、文档和三人契约确认；必须定义旧客户端兼容和序列化规则。 |
| C. 只改现有 `refs` / `hit` 语义 | 让现有扁平字段承载最终证据，或改变汇总规则。 | 表面改动较小。 | 不建议：可能破坏 trace 对候选命中的记录；无法自然表示一条主张由多份证据共同支持；目前注释与运行行为已经存在语义分歧。 |

建议评审时优先讨论 A 是否足以完成最小验证；若团队确认前端/验收必须直接检查逐主张关联，再转入 B 的契约差异设计。即使选择 A，也要给内部测试定义确定的数据结构和断言，不能靠答案自然语言自述来替代证据绑定。

公共契约若进入修改，至少先决策并写清：`TraceStep.hit` 是候选还是实际命中；`ToolResult.refs` 是工具认可引用还是最终引用；`AskResponse.refs` 表示所有来源还是答案引用；逐主张关联中的证据标识如何稳定定位；老客户端如何处理新增内容。按项目协作规则，契约改动前须先形成差异稿并同步团队，不在当前提案中直接改 `app/contracts.py`。

## 6. 与比赛要求及创新主张的关系

题面任务四要求：根据提取要素，在数十张表的业务库中定位正确表与字段，排除语义相近但无关的干扰项；任务五要求复杂多表 JOIN、聚合、嵌套查询的 SQL 生成稳定，并正确选择表关联路径（出处：`赛题八_题面原文.txt`）。本架构提案能提供事实依赖、已验证关系和证据检查的组织方式，但不能替代这两项专项能力：

- 任务四需要在数十表及干扰项数据上测量表/字段召回与误召回，并展示定位结果如何影响 SQL；仅把工单演示工具接进编排不算完成。
- 任务五需要多表 JOIN、聚合、嵌套查询及多条可能关联路径的专门用例，测量 SQL 执行正确率和关联路径正确性；单纯增加事实记录对象不能证明 SQL 质量提升。
- 可解释性和鲁棒性分别对应项目评分说明中的 5 分与 10 分相关项；这套架构只有在真实主链路里产出可审计证据、并经对照评测显示边界错误减少后，才可能支撑相应得分，不能预先记分。
- 中级任务分值按项目题面口径取决于实际攻克任务的数量/质量；本提案本身不构成任务完成，也不自动产生相应分数。

建议把创新表述限定为可证伪的工程假设：

> 对复合问答，显式管理事实依赖，并在形成答案前核对跨源对象关系与口径、绑定逐项证据，可能减少错误关联和无证据结论；我们将通过相同问题、相同数据与工具条件下的对照评测，同时报告正确性、证据完整度、过度断言和额外耗时，检验这一假设。

不要表述为“已证明整体架构创新有效”或“解决了任务四/五”。当前工单—合同实验属于合成数据上的专用链路评估，且相关题集已曝光；应继续标记为回归/已曝光结果，不作为未见题泛化证据。实验范围依据见 `新架构配对实验方案_v0.1.md` 及阶段 C 最新记录。

## 10. 2026-10-03 决策建议与首个实现切片

基于当前代码边界与项目协作约束，本轮采用以下工作方向，作为负责人可审阅的建议，不代替其他成员对公共契约的确认：

1. 继续保留工单—合同链作为已曝光合成回归和流程演示；不把它当作通用架构效果的主要证据。后续主链路验证应另选能同时调用通用结构化/文档工具的复合问题。
2. 先走选项 A：编排层私有事实/证据状态；暂不增加 HTTP 响应字段，也不改变 `ToolResult`、默认路由或 KAG 后端。
3. 将“步骤命中”“最终响应引用”“某个结论实际采用的证据”区分记录。前两项可由现有调用和工具输出确定；第三项必须由核验逻辑显式声明，不能自动把所有召回片段视为支持证据。
4. 前端暂不承担新字段消费；首阶段通过内部状态与确定性单测检查。是否扩展公共接口待原型显示消费必要性后再决策。
5. 任务四、五保持独立验收，事实账本不作为这两项完成的替代证据。

实现切片新增 `app/evidence_ledger.py`：将 trace 候选命中、最终响应引用和显式主张—证据链接分开存放；编排器引用汇总改由私有账本完成，响应字段与现有引用优先/兜底规则保持不变。另加入私有事实任务/事实记录模型：依赖必须存在且无环；事实只有在来源证据存在、所有前置事实已受支持后才能标为 `supported`。

随后新增 `app/fact_planner.py`，为明确的工单编号构造“工单/事件 → 受控映射 → 合同条款与修复时长 → 时限判定”的任务图；仅当 `CROSS_SOURCE_DEMO_ENABLED=1` 且问题含演示工单编号时，`route()` 才附带该私有计划，并在工具执行前校验依赖图。原演示工具调用、默认路由和 HTTP 响应均未改变。新增计划测试核对依赖顺序及工单编号格式。

此实现仍是受限演示路径上的任务规划原型，不是通用事实规划器：任务按演示业务预先定义，现有演示工具内部完成 SQL、文档检索与核验；编排器尚未把这张计划接入默认主问答路径。随后新增 `app/fact_executor.py` 作为私有调度原型：任务处理器可调用统一 `BaseTool.run()` 协议，也可执行确定性逻辑；任务只有在处理器显式判为 `supported`、且证据属于本轮工具输出或已登记候选时才算受支持，依赖不受支持时后续任务早停。缺处理器、异常、无来源的肯定判断均降为 `insufficient`。这验证了任务调度与账本的代码边界，不代表已把当前工单计划的各节点接到实际 NL2SQL、通用 RAG 和确定性核验函数上。

本轮进一步确认：独立跨源 PostgreSQL 容器和数据卷已存在，容器原先停止；只启动了这一个隔离容器并做只读检查，健康检查通过，五张表分别有 6 台设备、3 份合同、5 条映射、7 张工单、24 条事件。使用现有 `SqlExecutor(readonly=True)` 对隔离库执行 `SELECT count(*)`，实际返回 7；没有导入、更新或删除演示数据。另通过 `export_schema_meta.py` 从该库生成专用目录 `data/cross_source_demo/schema_meta.json`（1 个 schema、5 张表、22 个字段、4 条外键），并成功由 `SchemaCatalog.from_file()` 加载；默认 `infra/schema_meta.json` 未动。
