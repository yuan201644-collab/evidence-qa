## 2. 开跑前的可信度闸门

任一硬闸门不通过，停止计分运行并记录原因；不得临时修复后覆盖同一批运行。

| 闸门 | 必须留存的证据 | 不通过时的处理 |
|---|---|---|
| 题目独立性 | 编题人与实现者分离的声明；题集版本、生成/编制记录；旧题与旧答案泄漏检查 | 降级为开发/回归题，不作泛化评估 |
| Gold 正确性 | 独立复核者从源数据和原文重建事实；引用逐字核验；复算时间、映射、有效期、客户、状态及冲突边界 | 修订后重新冻结；已曝光版本不得再称未见集 |
| 条件公平 | A/B 实际配置差异清单；同数据库快照、文档、模型、底层 SQL/RAG 实现与预算证据 | 只描述为不同系统的探索性比较，不能归因于新架构 |
| 运行可复现 | 固定运行包外部哈希锚点；源码/依赖/模型标识；数据库与向量快照；随机种子、参数、时间戳 | 标记无效；保留原始现场，不覆盖重跑 |
| 防泄漏 | 运行者不可见 gold、密钥、组别映射；运行器不读取受控目录；留出题不用于调提示或代码 | 该批转为已曝光回归，另建新题 |
| 盲审可靠 | 匿名随机化 A/B 回答；至少两名独立盲审；分歧保留并裁决；另有技术审计查看 trace | 只能报告单人主观审阅，不能称独立盲审 |
| 完整性 | 所有题均有 A/B 原始输出；错误、超时、拒答均保留；运行前后哈希一致；无选择性删题 | 不计算成功率；解释缺失和失败，不补写或挑题 |

## 3. 导师可能追问及建议回答

**问：题目和标准答案是不是你们自己出的，如何避免偏袒新架构？**  
答：题目由未参与实现和本轮运行的人编制，另由不同人员仅依据冻结题目、结构化数据和文档原文独立重建标准答案与引用。运行者只拿运行包，不接触标准答案和组别映射。若人员隔离做不到，我们会如实降级为开发集，不称为未见测试。

**问：A/B 除架构外，模型、提示或数据是否也不同？**  
答：目标是控制底层数据库快照、文档语料、模型端点、NL2SQL/RAG 实现与调用预算一致；只让编排与事实核验流程按预注册有所不同。会公布实际配置与调用记录。若发现其他差异，则将结果解释为“端到端流程包差异”，不声称单一机制因果效果。

**问：如何证明运行中没有改代码、数据或向量库？**  
答：运行前外部锚定题包和代码/依赖清单哈希，并记录数据库行快照、文档和向量索引快照；运行后复算。任何实验相关哈希漂移均使该批无效，原始输出保留但不计入正式结果。

**问：为什么不是你们自己给结果打分？**  
答：候选答案匿名化并随机排序，至少两名未参与实现/出题者独立评定结论和证据，分歧保留、必要时第三人裁决；技术审计另查 trace 是否真实支持回答。Gold 独立核验、答案盲审和 trace 审计是不同角色，不能由一份自评替代。

**问：样本量够不够，差异是否显著？**  
答：小规模合成留出集只支持对这批题的逐题配对描述，不足以代表真实业务总体；除非样本设计和统计功效另有预先依据，否则不宣称统计显著或普遍准确率提升。报告逐题结果、原始计数和不确定性，不只给一个汇总分。

**问：合成数据能说明什么？**  
答：可以在可控边界上验证机制是否按设计处理关系歧义、口径冲突、证据缺失和拒答；不能替代真实业务数据上的有效性、部署可靠性或用户价值验证。下一步若取得合规真实数据，应另经授权、脱敏和独立评测，不能把合成结果外推。

**问：新架构如果更慢、调用更多，还算成功吗？**  
答：正确性、证据完整度、过度断言、拒答质量与效率分开报告。架构收益要和额外耗时及调用成本一起评估；没有可审计的 token/费用数据就标记未测，不能估算成实测值。

## 4. 结果报告必须同时给出的量

- 题目总数、有效配对数、运行错误/超时数，以及每题 A/B 的结论和证据判定；
- 错误肯定、正确拒答、过度拒答、证据充分、引用匹配与 trace 合规的原始计数；
- 逐题的 A→B 改善、退化或持平，不隐藏任何失败题；
- 两臂实际调用的工具、SQL/RAG/模型调用次数及端到端耗时分布；费用/token 仅在服务端记录可审计时给出；
- 留出集、Gold、盲审、代码/依赖、数据库和索引的哈希及实验有效性审计结论；
- 限制：合成数据、样本规模、单一模型/数据快照、盲审分歧和潜在实验者效应。

## 正式运行器的冻结顺序

`eval/cross_source_heldout/tools/run_architecture_comparison.py` 提供运行前预检、冻结登记和正式运行三种操作。正式运行只接收运行包目录，不搜索 Gold；运行数据库须使用无 `INSERT/UPDATE/DELETE/TRUNCATE/CREATE` 权限的专用账户，登记与结果锚点保存在项目工作区之外。连接串通过 `ARCH_COMPARISON_DSN` 环境变量传入，不放命令行或登记文件。

实际执行前应先按留出包交接记录核验编题人、Gold 复核人和运行者的角色隔离。独立题包到位后，由实验保管人先计算两个外部锚点：运行包 `SHA256SUMS.txt` 的 SHA-256，以及本轮适用预注册（当前为 v0.2）的 SHA-256；将两者通过团队约定的只读交接渠道固定。之后先运行 `--preflight`，确认资源、题包、数据库/索引和本地模型快照可读；再运行 `--freeze-registration <工作区外路径>`，并将登记文件哈希独立保存。只有同一份登记及其哈希齐备后，才可用 `--registration-path` 与 `--registration-sha256` 启动正式问答。

运行结束后须将 `sealed_manifest.json` 的 SHA-256 复制到运行目录之外的只读位置，再把运行包、登记、盲审材料和组别密钥分别交给对应角色。脚本自身生成的 `seal_anchor.txt` 只是便利副本，不是独立锚点。更改代码、题包、模型快照、数据库或向量索引后必须重新预注册；不得沿用旧登记。

模型方面，运行器能逐文件哈希本地嵌入/重排权重，但当前远程对话模型客户端不暴露可核验的权重修订号；报告必须明确写“远程权重哈希不可得”，不可把接口模型名当作权重快照。

## 5. 对外表述红线

有效新实验完成前，统一说：**“已完成原型接线和开发题烟测，正在建立独立留出集与可信对照；目前没有可报告的新架构效果结论。”**

有效实验完成后，也只按证据说：**“在本次冻结的合成留出题上，观察到……；结果不代表真实业务泛化或赛题整体验收。”**

禁止将烟测说成效果实验，将历史无效运行说成正式结果，将合成数据结果说成真实场景验证，或把逐题差异包装成统计显著性。
