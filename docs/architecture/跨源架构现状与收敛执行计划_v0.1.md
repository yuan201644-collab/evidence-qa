## 一、架构现在到底是什么

### 1. 用一个问题看流程

用户问：“这张工单是否在合同约定的修复时限内完成？”

```text
用户提问
   ↓
识别工单编号，建立工单时限任务模板
   ↓
查工单：设备编号、开单时间
   ├─→ 查设备与合同候选：编号关联、客户、依据、两个有效期、状态
   │      ↓
   │    核验是否能唯一确定适用合同
   │
   └─→ 查事件：受理时间、恢复时间；检查缺失、倒序并计算耗时
          ↓
      上述必要事实都受支持，才继续查合同原文
          ↓
      检索实际条款，核验适用设备和约定时限
          ↓
      比较“实际耗时”和“适用时限”，输出结论与两类来源证据

依赖事实失败 → 不作无依据肯定；说明已知事实、阻断原因和证据
```

图中分支表示事实依赖，不表示当前实现并发执行。现有执行器按依赖顺序运行；映射失败时，独立事件节点仍可能执行，不能把“安全早停”理解成所有工具立即停止。

自然语言转 SQL（NL2SQL）负责把问题变成经过只读校验的数据库查询；检索增强生成（RAG）负责从实际文档检索条款。新架构的重点不是增加这两个工具，而是**明确后面的判断必须建立在前面哪些已核验事实之上**。

### 2. 哪些已实现，哪些不能当成完成

| 部分 | 当前实现和边界 |
|---|---|
| 事实任务计划 | `app/fact_planner.py`：工单修复模板，支持显式首次响应并列分支。不是任意问题自动规划。 |
| 依赖执行 | `app/fact_executor.py`：只有证据支持的前置事实才能支撑后续判断；保留异常和早停记录。 |
| 证据记录 | `app/evidence_ledger.py`：候选来源与受支持事实分开，内部保存事实—来源关系。对外仍是兼容的文本、轨迹和扁平引用，不是完整的逐主张前端展示。 |
| 跨源核验 | `app/cross_source_fact_plan.py`：设备编号、合同映射、客户、合同/映射双有效期、状态、条款与事件检查；本轮发现等价 SQL 过滤误拒绝和隐藏依据规则。 |
| 应用接入 | `app/orchestrator.py`：在 `CROSS_SOURCE_DEMO_ENABLED=1` 与 `CROSS_SOURCE_FACT_PLAN_ENABLED=1` 的装配路径接入；默认路径未全面切换。 |
| 有界失败处理 | SQL 节点最多两次生成；文档适配器现已支持最多一次策略变化的真实补查并记录尝试元数据，但还需在下一版正式比较包中独立验证。 |
| 零结果证据 | 有映射零结果辅助埋点，但过滤条件未完整结构化、覆盖面和完整执行来源仍需补齐；不等于本轮技术审计已经通过。 |
| 澄清与限定回答 | 当前能演示部分限定回答和拒判；不能把这些等同于跨源业务的交互澄清与后续恢复已经全面完成。 |
| 知识增强生成（KAG） | 这轮正式比较关闭图谱后端；它不是当前工单核验主链的必经环节。不得用模拟图谱返回引用来补证据。 |

**事实任务依赖图不是知识图谱。** 前者表示“要判时限，必须先确认合同和事件”；后者表示业务实体之间的知识关系。当前原型的价值主要来自前者与确定性核验，不应包装成经典图关系检索已经落地。

五层总架构不需要推翻：新增机制主要放在编排层，复用工具层、数据层与模型层。更准确的创新主张是“以事实依赖和跨源证据核验组织问答”，目前是待验证主张，不是已经证明的原创算法。

## 三、五步执行计划

所有步骤按顺序过关，不并行生成新留出题。下列产物名称为拟新增文件，不表示现在已经存在。执行者承担当前任务；独立代码/数据核验可交给未参与相应实现的子代理，人工答案评审仍需清楚标注评审者类型和角色，不能冒充多人类评审。

### 第一步：修确定性缺陷，让该答的题不被误拒绝

**输入**：v0.13封存回答、只读诊断、现有开发题；不改历史问题、标准答案（Gold）、引用或评分。

工作顺序：

1. 检查当前 Git 状态和相关文件已有修改；按逐文件摘要记录修复前基准，保留用户与队友未提交的改动。不要把整个脏工作区误当成本轮改动。
2. 修改映射查询核验：在抽象语法树（AST，即 SQL 的结构化表示）中确认可靠内连接等值关系后，接受设备表或映射表上的等价编号精确过滤。保留正确连接、目标编号、完整候选和只读约束，不能只删除原校验。
3. 修目标选择与早停正文：用户询问开单日期时，从已支持事实输出日期及来源；客户冲突应指出双方客户编号，时间倒序应指出实际事件顺序。对只问“适用协议能否唯一确定”的问题，不无条件强求与该结论无关的修复事件或时限判断；按所问事实调整场景模板依赖，不借此宣称通用规划。尚未支持的事实不能补写。
4. 补零结果证据：由实际执行的表名、精确过滤条件和行数构造机器可检查记录，并绑定同一次查询引用。区分“无映射”“设备缺行”“合同缺行”“事件缺行”，不能凭一个多表内连接的零行结果断定是哪张表缺失；必要时追加只读定位查询。
5. 补受限文档检索：首次真实检索不足时，在同一已核验合同范围内最多做一次明确策略变化的补查；记录每次策略、候选数、状态和耗时。不得从未命中的本地文档凭空补引用。发现条款存在却仍未召回属于失败；发现复杂优先条款解析不了应明说能力边界，不能装成语料无约定。
6. 补结构化状态与引用投影，满足已经明确的技术判据；如发现比较器问题，先新增提案和单测，下一版冻结时修订，不改本轮冻结比较器或历史分数。

主要文件：`app/cross_source_fact_plan.py`、`app/fact_planner.py`、`app/fact_executor.py`、`app/orchestrator.py`；测试落在现有事实计划、执行器、证据及路由测试中。

必须覆盖的单测：

- 正例：两种等价设备编号过滤、别名变化、等号左右交换、同客户唯一合同、期限端点包含、耗时等于上限。
- 反例：错误编号、名称关联、`OR`放宽、外连接或子查询孤立谓词、预筛选状态/期限或只取首项隐藏歧义。不能因为新增等价支持而放行这些查询。
- 正确拒判：客户冲突、多合同歧义、两类有效期分别失效、事件缺失/倒序；拒判保留已支持日期，不泄露未支持结论。
- 目标完整性：用户只问协议唯一性、只问修复时限、请求并列指标时分别选必要事实；不能漏答，也不能因与所问结论无关的指标缺失而拒答。
- 负证据：伪造“零行”文本不通过；表/过滤条件不一致不通过；关联查询零行不能冒充某张主表缺行。
- 检索：一次成功不多查；首次不足至多补一次；条款存在却没召回不能记成功；无证据不能肯定或宣称明确未约定。

**过关条件**：上述正反例及相关现有测试无失败；默认短路径与公共契约不变；独立代码核验确认不是放宽安全规则来换成绩。此步尚不解决映射依据的业务效力。

2. 实现完成后冻结代码、规则、模型/工具配置和判据；再由未参与本轮修复的作者编制新题，由另一核验者从表和文档独立复算。作者或核验者若参与修复，角色隔离不成立，须如实标记并更换人员或降低结论定位。
3. 新包包含明确的映射依据规则、事件口径、合同状态/双有效期语义；包含能答、应拒、阈值边界和引用缺失场景，不按实现者已知强项选题。不把旧题换编号当新题。题型及比例在运行前固定，运行者不查看Gold或静态核验的逐题答案。
4. 运行只接受无Gold运行包；预检只读库/索引、暖机、哈希、两流程工具配置与参考流程开发题完整性。预注册声明主指标与全题分母，运行后不调参数、不择优重跑、不删失败。
5. 原始回答完整生成后封存。中断尝试保留并按提前写好的处置规则处理，不临时挑选完成题计分；没有完整性通过就不能进入正式评审。
6. 独立技术核验SQL只读、实际检索引用、精确负查询来源、阻断原因、调用次数及预算，不读取Gold或人工评分。
7. 分别独立生成两份候选级打乱匿名包和各自密钥；必须检查包摘要不同、匿名标签映射不同、候选全覆盖、各模板与其包绑定正确。**两个不同文件名并不算两个独立包。** 当前生成器随机化不保证两次映射必然相反，必须在分发前检查；可重新生成包装并保留生成记录，但不能重新生成系统回答。
8. 两位未参与实现/出题/Gold的评审只接收各自匿名包和冻结源资料，不接收密钥、另一人意见、轨迹或作者自审。回收后校验字段/枚举；两份候选编号不能直接对齐，需按各自密钥还原题号×流程。争议项交第三人独立裁定，最后机器汇总。

**唯一主指标仍为正确且证据充分。** 次要指标分别报告可答题表现、恰当拒答、过度拒答、错误肯定、引用与轨迹合规、调用数、耗时、运行失败，不事后合成一个好看的总分。

**过关条件**：冻结、完整运行、独立技术核验、两份独立匿名包装、评审/仲裁/汇总都合规。出现资料不可裁定，按预注册报告问题并计入全题，不追加隐藏规则或曝光后改Gold。结果不理想也交付；不“继续换题跑到赢”。

**交付**：无Gold运行包、包外Gold/密钥、前置登记、原始回答/封存、技术审计、两份原始评审/仲裁、汇总与方法偏差清单。任何规范问题须写进结论，不能仅靠文件齐全宣称合规。

### 第五步：形成可复现演示和有边界的创新结论

1. 从已曝光资料选三类演示：证据完整的正常判断、明确超时、证据不足或关系冲突的拒判。只引用实际查询与检索记录，不使用Gold回放代替在线能力。
2. 交付一张架构图、一份实现/实验报告、一条可复现的启动与测试路径；展示用户问题→关键事实→工具调用→来源→结论/停止原因。
3. 结论分开写：①流程实现到什么范围；②在这批新合成题上观察到什么；③哪些机制贡献没有隔离；④哪些真实业务、规模、多模态和多轮能力未验证。
4. 新流程没有优于完整参考流程，也应如实交付，并明确“未证明效果优势”；不能把完成实验等同于创新主张成立。
5. 公共接口、默认路径或前端需要扩展时，另走团队契约确认；当前先保留兼容接口与受控启用方式。不得因原型通过而直接切换全项目默认路径。

**本阶段结束条件**：该场景实现与已知缺陷有可核验证据；规范对照已完成且无隐瞒失败；演示可重现；报告准确说明结论范围。达到的是有限场景的工程与实验闭环，不是全赛题或通用跨源架构验收。
