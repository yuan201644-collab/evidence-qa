## 1. 结论与交付目标

本次修复的目标是：系统明确用户要求的对象、指标、时间、筛选、分组和来源范围；无法确定时先澄清；执行前核对查询是否落实了这些要求；执行后如实展示检查范围和证据。

必须解决的问题并不限于“客户表没有日期字段”。当前存在合法 SQL 忽略条件、替换统计指标、遗漏排名要求、多轮丢失筛选、多个工单只处理第一个等行为。SQL 执行成功和引用可打开，都不能证明回答对应用户原意。

本轮交付采用有明确支持范围的实现，不承诺解决任意自然语言的全部歧义。对于识别到但无法可靠处理的实质条件，必须停止对应业务查询或结论，说明原因；不能忽略条件继续返回一个正常数字。

### 1.1 必须保留的能力

- 三个入口：问数、问答、跨源；普通单源问题继续走相应工具。
- 别名、错字、全角字符、相对时间标准化和原始问题留痕。
- 多轮补充、指标和分组修改、取消、换话题、会话隔离。
- 表字段定位、多表关联、嵌套查询、只读校验、有限次 SQL 修复。
- 文档解析、目录切片、混合检索、重排、原文引用和既有多跳能力。
- 结果分页、下载、截断提示、登录、普通及流式问答。
- 工单链路已有受控映射、有效期、客户、设备范围、事件和时限核验。
- 最新三入口前端、底部输入框、统一图标和动效。
- “标准检索 / KAG 补充深度检索”现有选择语义；本轮不要求启动真实 KAG 服务。

### 1.2 赛题依据与本项目验收规则的区别

题面依据：[赛题八原文](../reference/赛题八_题面原文.txt)。其中第 87 行附近要求理解模糊、有歧义的输入；第 134 行附近的任务 3 要求维度缺失时主动澄清，避免生成错误查询。

本修复直接支撑初赛 NL2SQL 执行准确率 10 分、鲁棒性 10 分、多轮对话 5 分、可解释性 5 分；任务 3 可作为一个中级任务计分依据，每项基础 5 分、中级任务合计上限 15 分。基础问数与问答各 10 分的正常能力不得因新增闸门而回退。

本文设置的“零静默丢条件”“错误 SQL 注入必须拦截”等是项目内部发布门槛，不是比赛新增评分标准，也不等于已经获得上述分数。

### 2.2 原始意见中需要收紧的口径

1. “去年有多少员工”按 `hire_date` 过滤只证明用了日期，不证明业务口径正确。去年新入职人数、去年某时点在职人数、去年任一时点在职人数分别处理；只有入职日期不足以还原完整历史在职情况。
2. `客户 数量`可以表达明确的对象与指标，不因为句子没有谓语而一律澄清。默认数据源已明确时，“一共有多少客户”也可以直接回答，并说明统计范围。
3. 当前 T3 的历史 20 题来自 `eval/mainline/development_v0.1/t3_v02_questions.jsonl`，不是 `eval/cases/robust_cases.jsonl`。两份题集分别保留，历史结果不改写。
4. 不能把所有现有不确定性检查概括为“多解才拦”；已存在关系、部分聚合、恒假条件等检查。本次缺的是条件与实际查询的完整对账及相应停止规则。
5. 用户未同意时，“该表没有时间列，已改查全量”仍属于更改问题；必须先询问是否接受变更。
6. 文档中的复现指令不得继续传播明文登录凭据，后续复现统一从本地环境变量读取账号信息。

## 4. 目标处理流程与停止规则

```text
本轮原话 + 当前明确的数据范围 + 已确认会话条件
  → 原文保留、受控改写、上下文接续
  → 建立对象/指标/条件清单，逐项保留原文依据
  → 检查必要信息与数据能力
      ├─ 可由用户补足：澄清，停止该业务查询
      ├─ 数据或能力不支持：说明缺口，停止对应结论
      └─ 信息足够：按原路线查询/检索
          → SQL 生成后、执行前核对条件和指标
              ├─ 不符合：有限次修复，再次完整校验
              ├─ 修复仍失败：停止，不返回候选 SQL 的业务结果
              └─ 通过：只读执行/有范围检索
                  → 登记真实检查、结果与证据
                  → 输出限定范围内的回答
```

### 4.1 统一决策表

| 情况 | 处理 | `need_clarify` | 是否允许执行原定业务 SQL |
|---|---|---|---|
| 数据源已明确，用户问客户总数，没有时间限制 | 正常查询并说明来源范围 | `false` | 允许 |
| 没有对象、未解指代、多个合理口径尚未确认 | 提出一个最必要的追问 | `true` | 不允许 |
| “2023 年客户数”，无法确定新注册/购买过/历史在册 | 询问统计口径，并说明当前数据能支持什么 | `true` | 不允许用全量代替 |
| 问题已清楚，SQL 漏筛选或算错指标 | 修复 SQL；修复失败说明系统未能可靠完成 | 通常 `false` | 只允许修复后通过的 SQL |
| 数据缺少完整历史记录，用户明确要求历史在职人数 | 说明数据无法支持；有可选口径时再询问 | 需要用户选择时 `true`，否则 `false` | 不允许用入职人数替代 |
| 数据库连接、模型、检索工具失败 | 返回执行失败及可理解原因 | `false` | 不继续碰运气切换其他口径 |
| 有效查询返回零行 | 按当前筛选范围报告零行 | `false` | 已执行，不扩张为全业务不存在 |
| 两个工单，但当前处理器只支持一个 | 要求分别查询，或待多对象实现后完整处理 | `true` | 不允许只执行第一个后当作完整回答 |

“停止查询”指停止用户所请求的业务查询。读取内存中元数据、登录校验和健康检查不属于业务数据查询。前置澄清测试须证明没有调用 SQL 生成器、业务执行器或文档检索器；生成后条件不匹配的测试须证明没有执行错误候选。

## 5. 修改设计

下文出现的新增文件、类型、函数、检查码和命令均为待实现设计，不表示当前仓库已经提供。

### 5.1 建立可对账的内部条件清单

修改 `app/nl2sql/planning_models.py`；建议新增 `app/query_requirements.py` 承担原始要求提取、范围解析与上下文合并，避免继续把所有判断塞进澄清器。

建议内部类型如下；实现时可按现有数据类风格命名，但语义不能省略：

| 类型 | 必需字段 | 用途 |
|---|---|---|
| `QueryRequirement` | `requirement_id`、`kind`、`source_turn_id`、`original_text`、`char_start`、`char_end`、`required` | 每个对象、指标或条件有原始依据，不能由生成 SQL 反推用户要求 |
| `ResolvedRequirement` | 原要求、`source_id`、表/字段候选、比较运算、规范化值、单位、时间边界、目标粒度、解析状态 | 区分用户说了什么与系统已经确定了什么 |
| `QueryRequirements` | 版本、原话、接续文本、标准化文本、明确来源范围、要求列表、未解析片段 | 每轮使用同一份快照，避免提取器与执行器各自理解 |
| `RequirementCheck` | 要求编号、`covered/missing/ambiguous/unsupported`、原因码、SQL 作用域和表达式定位 | 记录检查证据，不能只记“启用了检查” |

`kind` 至少覆盖对象、数量/合计/平均等指标、时间、取值筛选、数值范围、否定、分组、排序、前 N 条、去重粒度、文档范围和跨源对象。

具体规则：

1. 从本轮原文和已确认条件提取要求，再进行别名等规范化；保存二者映射。不能只从改写结果提取，否则改写时已经丢掉的内容无法发现。
2. 每项规范化条件必须能回到原话或明确会话操作；没有依据的默认值不能伪装成用户提供。
3. 记录绝对时间与相对时间。绝对年份、月、日、季度不能因为不在现有相对时间词表里就漏记。
4. 相对时间每轮只取一个锚点，沿用项目已经明确的日历整期口径；“今年至今”“截至某日”等显式要求另行处理，不能被整期默认覆盖。
5. 提取地名、阈值、`大于/不小于/等于/不含/除了`、前 N 条、平均/合计/去重等条件；否定与比较符作为结构保存。
6. `QueryIntent.filters`、`dimensions` 和 `time_expressions`不再长期保持空壳；内部执行使用更精确的条件清单，旧字段保留为兼容投影。
7. 明确提取器支持的表达形式。发现有实质约束信号但不能解析时，记为未解析并澄清/停止；没有匹配到规则不等于已经证明问题没有条件。
8. 初版优先复用既有词表、时间处理和代码解析，避免每条事实增加一次模型调用。若后续引入模型提取，模型只能给候选；原文位置、值、运算符、来源能力仍须校验，并单独评测提取漏检率。

条件检查的总结果还须包含“提取范围是否足以支持本题”。不能因为提取器漏掉了年份、只留下客户对象，就把剩余一项对象检查通过算成全部要求覆盖。对支持规则之外的实质约束返回未能判定；新增同义表达和未登录业务词的漏检继续通过独立测试发现，不能宣称开放语言零漏检。

### 5.2 来源范围与数据能力

新增内部来源能力目录，建议文件为 `infra/query_capabilities.v0.1.json`，以独立伴随文件方式维护，不修改冻结元数据。

来源身份使用“逻辑数据源 + schema + 表 + 字段”，不能只凭同名表或中文名称关联不同数据库。

至少登记：实体主键、可支持指标、时间字段的业务含义、是否支持历史快照、可证明的外键和粒度、已知单位。运行时须检查声明字段实际存在；声明缺失或不匹配时不能按声明通过。

| 典型要求 | 可接受依据 | 不可替代的口径 |
|---|---|---|
| 当前客户总数 | 当前问数库的 `customer` 实体 | 不能声称是三个数据源合并后的客户总数 |
| 2023 年注册客户数 | 真实的注册/创建时间及明确实体定义 | 当前 Chinook 客户表没有该时间依据，不用 `invoice_date` 冒充注册时间 |
| 2023 年购买过的客户数 | 发票时间、客户外键、按客户主键去重 | 不能统计发票张数或全部客户 |
| 去年新入职员工数 | `employee.hire_date` | 不等于去年在职人数 |
| 某历史时点在职人数 | 足够的入职、离职或有效期/快照记录 | 只有 `hire_date` 不能证明完整历史在职状态 |

前端展示了某个数据库卡片，只代表该数据源已登记，不自动代表用户选择它作为本轮统计范围。当前请求未携带来源选择时，可使用已明确的会话范围或系统公开说明的默认问数库，并在回答标明；不能从界面上“存在三个来源”推导为要跨三个库合计。

如果用户明确选择某个尚未受普通问数工具支持的数据源，必须告知支持边界；不得显示该数据源名称、实际却查默认 Chinook。

### 5.3 前置澄清与路由

修改 `app/clarifier.py`、`app/orchestrator.py`，保留现有四类检查并补齐以下规则：

- 对象/指标没有可确认解释且无明确上下文时，先追问；取消“无任何路由信号就默认生成 SQL”的行为。
- 区分简洁问法和缺项问法。`客户数量`在范围明确时正常查询；`有多少位？`没有可恢复对象时澄清。
- `同比/环比`只确认比较关系。本期仍需有明确时间或可继承时间；不能仅凭这两个词认为时间槽完整。
- 绝对时间解析覆盖同年不同季度，避免把两个不同季度折叠成一个年份。
- 指代解析检查候选唯一性；支持姓名、编号、明确选中的对象与文档。多个姓名、同名不同编号、仅出现通用“客户”均不能确定“他”。
- 对“它/这份/该合同/上述”同样检查上下文；仅凭最近成功查询不能跨实体继承指代。
- 不能仅因一个对象名称有唯一库表，就认定“去年客户数”只有一个业务口径。
- 当前问题本身已包含明确姓名/编号时，不能因为同句含“他”而无视这个锚点。

澄清句一次只问阻碍执行的必要信息，优先给数据实际支持的选项。不能让用户反复填写模型生成失误造成的“缺项”。

前置规则返回澄清后，编排器立即返回现有 `need_clarify=true` 响应；不会启动业务 SQL、文档检索或 KAG 请求。

### 5.4 生成后、执行前的条件覆盖闸门

建议新增 `app/nl2sql/requirement_validator.py`。接入顺序：

```text
生成候选 SQL
  → 既有 sqlglot 只读/语法/表字段检查
  → 既有关联/粒度检查（适用时）
  → 本轮要求覆盖检查
  → 追问合并后的要求检查
  → 实际执行
```

新的要求覆盖闸门不能受 `NL2SQL_SEMANTIC_PLANNING_ENABLED` 开关控制，也不能受是否展示 `fact_review` 控制。关闭表定位增强不等于允许丢条件。关联规划关闭时，以元数据和已解析要求核对适用部分；无法证明的实质条件按停止规则处理。

#### 5.4.1 最低检查范围

| 检查对象 | 通过所需依据 | 典型必须拦截的错误 |
|---|---|---|
| 数据源/实体 | 执行器、目录与本轮来源一致；目标表/实体有依据 | 显示跨源库，实际统计 Chinook 客户 |
| 时间 | 正确业务时间列、区间、边界、时区语义一致 | 没过滤、年份错、出生日期代入入职日期 |
| 地点/类别/编号 | 目标字段与规范化取值匹配，谓词实际约束目标对象 | 漏国家、错客户编号、账单国家替代客户国家 |
| 数值与否定 | 比较方向、开闭边界、单位、排除含义一致 | `>`改成`>=`、`不在巴西`改为`在巴西` |
| 聚合 | 对象粒度、聚合类型、参与字段和去重依据一致 | 平均变合计、客户数变发票数、常量替代计算 |
| 分组 | 所需维度来自正确对象，分组键与结果含义一致 | 客户国家与开票国家混用、删除分组 |
| 排名 | 指标、方向、前 N 条及已有并列规则一致 | 漏排序、最高变最低、前3变1000 |
| 条件作用域 | 目标数据行受到所要求条件约束 | 条件只在无关子查询/注释出现、`OR TRUE` |
| 关联粒度 | 外键和基数共同支持统计口径 | 一客多发票后 `COUNT(*)` 当客户数、父表金额重复累计 |

#### 5.4.2 不采用简单字符串匹配

- SQL 中出现年份、字段名或 `WHERE`，均不足以证明要求落实。
- 使用 sqlglot 的作用域、表别名和列来源解析；逐个核对 `WHERE`、`HAVING`、必要的 `ON`、条件聚合和子查询中的有效条件。
- 条件置于 `CASE` 等条件聚合时，须确认只有满足条件的数据贡献目标指标；不能见到条件就通过。
- `LEFT JOIN` 的 `ON` 与 `WHERE` 条件不天然等价；外连接、空值及否定语义必须单独判断。
- CTE、嵌套、`EXISTS`、窗口等结构按实际支持的作用域验证。先覆盖既有 T4/T5 正确样例使用的结构；不能用全拒绝复杂 SQL 的办法实现“安全”。
- 支持确定可证的等价形式，如别名变化、`AND` 条件交换、相同含义的区间表达。无法证明等价时保留明确原因，不声称一定错误或已经通过。
- 前 N 条要求不能被自动补的 `LIMIT 1000`满足；聚合结果行数也不等于被统计数据量。
- 原文要求存在歧义时不从候选 SQL 中挑一种解释，回到澄清阶段。

#### 5.4.3 修复、失败和执行边界

复用 `Nl2SqlPipeline` 既有最大尝试次数，不另加无限重试循环；重写时回灌遗漏要求及原因码。每次重写重新跑全部适用检查，不能只验证刚修的一项。

问题清楚但 SQL 不正确属于生成失败：修复用尽后，`error`有值、不得执行最后一条错误候选。`sql`继续遵循“真正执行过的 SQL”含义，未执行的候选只保存在 trace，不能放到答案中伪装为已查询。

只有确实需用户补信息时才返回 `need_clarify=true`。配置缺失、模型失败、检查器不支持当前 SQL 结构分别记录原因，不伪装成用户表达不清。

结果扩展、分页、导出复用已验证 SQL；若生成新的查询表达式，仍需重新校验。新轮次不得靠命中旧结果缓存绕开条件检查。

### 5.5 多轮条件合并

修改 `app/memory.py`、`app/nl2sql/followup.py`，在现有实际 SQL 状态之外记录已确认条件及来源，不存模型自由总结。

| 用户操作 | 条件处理 |
|---|---|
| “再按城市分组” | 增加分组，保留原指标和筛选；保留原人群的分组后筛选语义 |
| “改按国家分组” | 明确替换分组，其他条件继续生效 |
| “那只看上个月” | 替换被指明的时间槽，保留其余条件，不把两个互斥时间简单相加 |
| “只看巴西” | 加入或替换对应地点槽；字段口径不明时澄清 |
| “不要国家限制，统计全部国家” | 用户明确删除地点条件；记录删除依据 |
| “那就查全量客户” | 经本轮明确确认后删除原来不支持的时间条件；说明新统计范围 |
| “好的” | 只有待确认问题为明确且唯一的是/否选择时才视为确认；不能任意解释为取消全部条件 |
| “新问题……”/取消 | 清理待澄清状态，按已有明确规则切换 |

保护范围必须包含原有 `WHERE`、`HAVING`、子查询和条件聚合中的实际人群范围，不只比对表层 `WHERE`。添加分组后，如果保留“客户数大于5的国家”的原人群需要子查询，则按该语义生成，不直接把旧 `HAVING` 原样贴到新城市粒度上冒充保持一致。

SQL 中原有业务筛选不能凭生成器自行取消；用户明确替换或删除时则允许变化，并以本轮条件清单为准，避免“永远禁止删条件”导致正常修改失败。

条件清单仍按用户和会话隔离。长度/轮数超出可保留范围时记录失效并重新确认，不静默截断关键限定或借用其他会话的范围。

### 5.6 跨源演示路由收紧

修改 `app/orchestrator.py::route`、`app/fact_planner.py` 和 `app/tools/cross_source_demo.py` 的边界校验。

1. 先提取全部工单编号、所问指标和显式附加要求；不能只使用正则 `search()` 的首个命中。
2. 第一版继续支持已有单工单修复完成及已实现的组合指标。多工单暂未实现时明确提示分别查询；不偷偷启用批量查询。
3. 只问设备名称、合同编号、其他指标时，不自动构造修复时限结论。支持的查询走相应处理器；没有处理器则说明边界或澄清。
4. 识别到“按自然日/工作日”“首次响应/到场/修复”“只在某范围”等要求时，确认处理器支持并保留口径；不能由固定 SLA 计划覆盖用户请求。
5. 编排路由和演示工具都校验对象数量、格式和能力，避免直接工具调用绕开前置检查。
6. 原有单工单严格核验规则保持不变；本次只收紧问题与计划的对应关系，不放宽任何合同或事件条件。
7. 事实计划任务全部完成，不自动等于用户全部问题已覆盖；输出前核对请求对象/指标清单是否全部被处理。

### 5.7 文档问答与 KAG 的接口注意事项

修改重点为 `app/query_requirements.py`、`app/tools/doc_search.py`、`app/rag/answer.py` 的范围传递及上下文；复用现有检索流程。

- “合同里怎么规定的？”在无当前合同、无条款对象时先澄清；如果已明确当前合同及所问条款，则正常接续。
- “总结当前资料库所有文档的主题”是有范围的请求，不因没有单份文档名一律拒答。但有限 Top-K 召回不能冒充全库完整综述，必要时说明覆盖范围。
- 同名不同合同号、不同版本文档不能自动混用。明确的 `doc_id`和允许文档集合应作为检索器实际过滤，而非仅在提示词中提醒。
- 用户未指定单文档但明确提出跨文档比较时，允许既有跨文档检索；不能为了澄清把有效多跳能力关掉。
- 无法证明文档适用对象、年份、单位、条款例外时，不标为完整核验。一般文档的开放语义支持不在本轮代码全面证明范围内，继续如实标为候选/不足。
- KAG 作为补充候选继续接受同一对象、文档范围与预算；不能扩大范围解决本应先澄清的缺项。标准模式不调用 KAG。
- 本轮仅用替身验证 KAG 请求是否被错误触发、范围是否传递；不启动真实 KAG，不把接口通过写成检索效果通过。

### 5.8 统一记录与前端展示

新增真实 trace 步骤，建议名称为 `query_requirements`、`query_capability_check`、`sql_requirement_validate`、`followup_requirement_merge`。步骤输出包含要求编号、处理状态、有限原因和可定位检查依据；不记录秘密，不输出模型思维链。

在现有核验卡里增加“已识别的条件”和“尚未解决的条件”摘要，建议复用 `FactReviewItem.summary/reason` 与现有检查列表；完整的逐项证据先放入 trace。若必须新增公共字段，另列契约版本方案后执行。

`FactReviewCheck.result`当前只有 `passed/failed/unknown/not_run`：

- 实际覆盖检查通过才映射 `passed`。
- 明确遗漏或错误条件映射 `failed`。
- 不能证明映射 `unknown`。
- 未执行检查映射 `not_run`。
- 不适用的检查不生成“通过”项；原因写入摘要或 trace。

单源事实继续遵守现有范围：执行和条件覆盖通过，不自动将答案语义状态从 `candidate`升为 `supported`。HTTP 200、流程结束、引用索引有效、`*_checked=true`均不能代替条件检查结果。

前端具体要求：

1. 沿用最新三入口、底部输入、统一颜色/图标/动效；不恢复中级任务和测评入口作为主界面中心。
2. 澄清以正常对话卡呈现，显示待补的必要信息；不显示成服务错误，也不继续播放不存在的查询步骤。
3. SQL 生成失败与需用户补信息使用不同文案。修复成功保留过程记录，最终状态以成功查询为准。
4. 点击证据只打开本轮对应来源；历史卡片的引用不会随新轮条件变化而串用。
5. 旧响应没有新 trace 或新检查项时，仍能正常显示；不能补造“条件均通过”。
6. 同步 `web/src/utils/trace.ts`、`web/src/components/FactReviewCard.vue`、必要的 `AnswerBubble.vue`；若未改公共类型，不擅自增加新的字段依赖。

## 7. 第一批可直接编写的验收场景

下列 32 项是开发与发布诊断场景，不是未见题效果集。多轮场景包含多次请求，统计时同时报告场景数和请求数。

## 9. 如何继续发现同类问题

### 9.1 从单题修补改成条件变化成对测试

每条基础问题至少生成“增加条件、替换条件、否定条件、删除条件、改变指标”的成对或成组问题，记录预期变化。

例如客户总数 → 巴西客户数 → 非巴西客户数；发票总额 → 平均金额；2023全年 → 2023第一季度；单工单 → 两工单。不能只检查HTTP成功或答案有数字。

判断时同时看两项：

- 条件是否在正确来源、正确作用域中有效落实。
- 在特意设计的差异化样本中，结果是否随条件按预期变化。

相同结果并不一定错误；不同年份可能恰巧数量一样。因此不能仅用“答案相同”判定丢条件，也不能用“与参考数字相同”掩盖查询含义错误。

### 9.2 测试数据要让错误暴露

隔离样本至少包含：多个国家与空国家；多个年份、月份和区间边界；金额恰好100、低于100、高于100；一位客户多张发票、无发票客户；入职在区间前/中/后的员工；同名不同编号；两个不同结果的工单；同名但条款不同的合同版本。

使用小而有区分度的样本先验证规则，再到真实只读样本验证完整链路。不得修改业务库数据来配合断言。

### 9.3 约束变异与作用域对抗

对每个已接受的正确SQL，自动生成删除/改错一个实质条件的候选，再验证闸门；同时生成别名、条件重排、等价表达等应通过的候选。

长期补充：CTE、相关子查询、`EXISTS/NOT EXISTS`、`HAVING`、条件聚合、窗口排名、集合查询、外连接和空值、单位换算、时区和夏令时（涉及的业务场景才启用）、多个来源同名对象。

每支持一种新结构，就必须加入正确写法和绕过写法，不能只增加允许列表。

### 9.4 在适用前提下检查结果关系

- 增加有效的 AND 筛选，未截断的实体集合应是原集合子集。
- 去重客户数不应超过同范围客户总数。
- 相同范围的平均值应在最小值和最大值之间，空集/空值另行处理。
- 同一范围、同一指标的Top3结果应与Top5的前部一致，前提是并列规则确定。
- 前后问题只替换时间时，不相关的国家/实体/指标要求应保持。

这些是适用范围内的辅助检查；涉及不同粒度、空值、截断或随机并列时先核对前提，不能机械套用。

### 9.5 失败入库与独立新题

发现问题后固定最小复现：原话、上下文、条件清单、候选/执行SQL、trace、预期和实际、版本、数据指纹。新增一个失败用例和至少一个防误拒控制用例。

开发场景用于修复，见过答案后不再称未见题。候选稳定后另写一批未参与修复的新题，建议首批24个独立场景，覆盖时间口径、筛选、统计、多轮、文档范围及多对象；这是时间紧张下的工程复验规模，不是统计可信度阈值。

新题先锁定数据与判据再作答，保留全部错误、超时和拒答。若需正式人工效果结论，遵守现有盲评流程，并落实每位评审独立随机化顺序；不得沿用CS18已登记的随机化偏离。

独立新题失败后可以纳入下一轮开发集，但本轮首次结果保留，不能修后重跑覆盖首次分数。

### 9.6 日常反馈分桶

后续失败至少分类为：要求提取遗漏、口径未确认、来源选错、表字段定位错误、SQL条件遗漏、运算符/单位错误、聚合/粒度错误、追问继承错误、文档范围错误、计划漏对象、展示伪通过、执行/资源失败。

每轮优先处理会“正常返回错误答案”的类型；依靠同一份题集不断调到全对时，必须追加同义改写与新口径，而不是只扩充原句白名单。

## 10. 验收门槛与评分方法

### 10.1 不合并为一个含糊的通过率

| 指标 | 计算方式 | 内部发布要求 |
|---|---|---|
| 必要澄清正确率 | 应前置澄清且实际澄清、零业务调用的场景 / 应前置澄清场景 | 已登记必测场景全部满足 |
| 错误候选拦截率 | 错误SQL未进入执行器的候选 / 注入错误候选 | §8.3 已支持检查范围内全部拦截 |
| 静默遗漏数 | 已识别的实质要求未落实、未告知仍返回完整业务答案的次数 | 必测场景为0；任何新发现均登记阻断 |
| 正常问题保持率 | 应可回答且语义/结果正确的场景 / 应可回答场景 | 必测正常控制全部通过；原有正确关键样例无新增失败 |
| 条件覆盖率 | 已证明覆盖的要求数 / 本轮要求总数 | 辅助诊断；不能用大量简单条件稀释一个关键漏项 |
| 端到端场景通过率 | 行为、条件、实际结果、引用范围均满足判据的场景 / 全部场景 | 分开发/未见题报告，失败和超时不删分母 |
| 实际开销 | 新增模型调用数、数据库调用数、拒答前耗时、总耗时 | 前置澄清不触发业务调用；不开额外无限循环，耗时前后实测 |

一个场景即使结果数值碰巧正确，若漏了必要条件、查错来源或漏处理对象，仍判失败。反之，明确问题因系统生成失败而返回安全失败，也不能计为“正确回答”；只在拦截指标中体现有效停止。

文档问答除执行与引用定位外，业务支持不足的部分仍需独立核对；不把代码检查覆盖到的局部结论扩张成整段答案全对。
