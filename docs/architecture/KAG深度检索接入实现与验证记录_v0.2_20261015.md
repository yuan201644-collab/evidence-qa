# KAG 深度检索接入实现与验证记录

版本：v0.2
日期：2026-10-15（北京时间）
状态：项目代码接口和候选适配已实现；真实检索仍处于验证阶段，当前运行环境未启用深度检索。
依据：KAG深度检索接口预留与接入交接_v0.1_20261015.md；项目工作区代码与 D:/kag/workspace/askdata_mainline_deep_clean_20261015 实测。

## 1. 方向与接入边界

项目 RAG 仍是默认路径。用户选择“深度检索”后，项目先运行 RAG，再请求 KAG 返回候选原文；候选由项目校验身份和原文位置，与 RAG 一起重排，最终仍由项目回答器生成答案和引用。KAG 不负责向用户生成最终业务答案。

纯数据库问数不调用 KAG。KAG 服务不可用、索引未就绪、查询超时或候选不能映射回原文时，系统记录失败状态并回退到可用的项目 RAG 证据。

## 2. 已实现的代码

- app/contracts.py：问答请求新增 retrieval_mode，默认 standard；旧请求不传此字段仍走原路径。
- app/main.py：同步与流式问答透传深度模式；新增需鉴权的 /api/kag/status，只返回就绪状态和安全原因码。
- app/orchestrator.py：只把检索模式传给文档检索工具。
- app/tools/doc_search.py：深度模式下融合 RAG 与 KAG 候选，统一重排，并由项目生成答案。
- app/kag_supplement.py：使用独立 KAG Python 环境执行候选查询；校验文档集合、原始文件哈希、规范文本哈希和原文坐标。
- D:/kag/workspace/askdata_mainline_deep_clean_20261015/runtime/query_worker.py：抑制 KAG 最终答案和引用修补调用，只返回检索证据候选。
- web/src/components/Composer.vue、web/src/stores/conversation.ts：提供手动深度检索选项；标准模式不发送新增字段，服务未就绪时禁用深度选项。
- docs/契约设计_v0.6.md：记录新增请求字段与兼容约束。

KAG 页内容在查询链中会以带引号的序列化字符串返回，且首行重复页标题。适配层现会解开该包装并移除标题行，再对候选全文做唯一原文匹配。不能唯一回切到语料原文的候选仍会被拒绝为可引用证据。

## 3. 测试结果

### 自动化检查

- 后端定向测试：78 项通过，覆盖请求兼容、KAG 失败回退、候选边界校验、原文坐标映射和项目重排链路。
- 前端生产构建与受控界面测试：通过。
- git diff --check：通过；Git 对两份既有评测清单提示换行符规范化，不是空白错误。

自动化测试证明项目接口和候选融合逻辑按契约工作，不证明 KAG 在业务题上的召回质量。

### KAG 真实候选烟测

测试语料为 15 份文档、16 个页面索引单元、103 个项目 RAG 切片，原文约 8,603 字符；模型配置为 DeepSeek-V4.1-Flash 与 BAAI/bge-m3。烟测直接调用本机 OpenSPG 项目，并在隔离脚本中绕过构建身份就绪门禁；因此这些结果不能视为产品环境已就绪。

解析修复前，候选适配曾出现 8 条原始候选全部无法映射。加入序列化内容解包后，真实跨文档请求有 8 条原始候选，其中 5 条映射回来源、3 条未映射；5 条候选的字符区间全部通过规范文本回切校验。该题找到了 KB-012，但没有找到问题同时要求的 KB-001。另一轮单文档查询映射到 5 条候选，却没有返回目标 KB-001。将候选预算从 8 提到 16 后，返回 11 条原始候选、映射 6 条，仍没有目标 KB-001。

同一条 KB-001 问题的独立调用结果不一致：一次原始 KAG 查询返回了 KB-001，后续候选适配查询未稳定返回 KB-001。当前观察到的调用耗时约 24–138 秒；样本很少，不能当作性能分布。查询结果存在噪声、预算截断及跨轮波动，不能据此启用默认路径或宣称多跳增益稳定。

## 4. 索引构建状态

本轮索引清单包含 15 份文档和 16 个页面单元。构建日志中可逐项匹配 16/16 个 ASCII 文档编号与页面标记；旧构建身份文件仍记为 FAILED、完成数为 0，且没有保存子进程退出码。原因是旧计数逻辑依赖完整中文文件名，而 Windows 子进程日志中的中文文件名发生乱码。build_project.py 已改为按稳定 ASCII 编号计数，并记录索引子进程退出码，但没有为规避旧计数问题而重建冻结索引。

构建日志另有 3 次 NER / 三元组响应 JSON 解析异常：KB-002 在 NER 阶段，KB-004 和 KB-009 在三元组抽取阶段。离线检查构建检查点发现，KB-002 只有 1 个节点、0 条边；KB-004 有 67 个节点、78 条边；KB-009 有 66 个节点、77 条边。KB-004/009 的检查点并非空图，但异常轮次的关系抽取完整性仍未核清。KB-001 本身有 80 个节点、103 条边，说明其索引不是空的；因此目标 KB-001 偶发漏召回应继续从查询规划和检索稳定性定位。由于旧身份状态、缺失退出码和解析异常，/api/kag/status 目前应保持未就绪，不能手动伪造为成功。

## 5. 服务与数据状态

已停止项目 FastAPI 端口 8000、8001、8002；停止 Vite 端口 5173、5174、5175、5184；停止项目 PostgreSQL 容器 ict-db、ict-aw 和临时跨源数据库容器 askdata-cross-source-demo-db。停止服务未删除容器、镜像或数据卷。ict-aw 原先退出码 137；重启后 PostgreSQL 完成 WAL 恢复和检查点，随后通过容器内 pg_ctl 正常关闭，日志确认 database system is shut down，容器最终退出码为 0。为防止手动关闭数据库进程后容器按旧策略自动重启，ict-aw 的 restart policy 已改为 no；以后仍可手动 docker start。

本轮 KAG 烟测结束后，release-openspg-server（8887，KAG API）、release-openspg-neo4j（7474/7687，图数据）、release-openspg-mysql（3306，OpenSPG 元数据）和 release-openspg-minio（9000/9001，对象存储）也均已停止。Neo4j 第一次收到 10 秒停止宽限时退出码为 137；已重新启动并完成恢复，再给 90 秒宽限后以退出码 0 正常停止。容器、镜像和数据卷均保留。当前没有启动项目问答后端、前端或 KAG 服务。

## 6. 启用前的剩余验证

1. 用修正后的构建计数器审计冻结日志，确认索引子进程完成状态；将 3 份出现 JSON 解析异常的文档逐份检查实体、关系和向量片段覆盖。
2. 固定一组未参与提示词调试的跨文档问题，先由独立人员冻结必要事实和证据来源。
3. 对每道题重复运行 KAG 候选检索，分别统计必要来源召回、错误来源、候选回切成功率、超时率和耗时；不只看候选条数。
4. 在相同语料、相同问题、相同项目 RAG 候选上完成真实融合、重排和项目回答；人工核对事实和逐条引用。
5. 预先确定可接受交互时限。当前实测的长耗时可能超过前端 180 秒等待上限，需要在质量门槛通过后再决定预算配置；不能用无上限等待掩盖慢查询。
6. 上述门槛通过后，备份旧构建身份记录、写入可审计的索引身份，并配置本机 KAG 运行目录；在此之前保持 UI 深度选项不可用。

当前阶段结论：项目侧的可选接入代码已搭好，KAG 候选可以被安全回切到原文；真实检索的稳定性、召回质量、构建身份和交互耗时尚未通过启用门槛。
