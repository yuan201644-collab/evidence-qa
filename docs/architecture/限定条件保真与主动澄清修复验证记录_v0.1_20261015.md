## 5. 首轮真缺陷的修复（r2 已验证转 pass）

| id | 首轮现象 | 修法 | r2 结果 |
|---|---|---|---|
| SC-05 | 答「字段 created_at 不存在」但无能力边界说明 | `_coverage_note`（`app/orchestrator.py`）：从 nl2sql run 的 `requirement_coverage.checks` 取 repair/unknown 项拼成「其中说明：…」追加到答案（P1(c) 第三留痕）；`app/tools/nl2sql.py::_coverage_dict` checks 增 surface 字段 | **pass**：`failed` + 答案附「没有可用的时间依据」，且不含 59 |
| SC-08 | 去年员工硬算得 0 | `app/clarifier.py` 新增 `_relative_period_on_person` 分支：员工+指标+相对时间（去年/今年/明年）+原文无「新入职/在职」→ ask 口径确认，reason_code=`time_semantics_ambiguous` | **pass**：正确追问「统计去年内新入职的员工，还是去年期间在职的员工？」 |
| SC-11 | 两个明确季度被误挡 | `app/clarifier.py::_has_comparison_period` 第三参 requirements：清单里两个 actionable time 项 = 比较口径已给足。**判据是解析后的日历锚点不是字面串**（否则「去年」与「2023 年」字面不同日历同年会误放行——锚定回归 test_same_explicit_and_relative_period 抓过） | **pass**：正常出结果，不澄清 |
| SC-12 | 「至今」套 2026 全年无边界说明 | `app/nl2sql/requirement_validator.py::_check_time`：normalized 含「至今/到现在/到目前为止/今年以来」→ unknown 消息明确「需要明确的截止锚点（截至今日还是截至数据快照日）」 | **pass**：`unknown` 标黄 + 答案附「至今」锚点说明 |

**SC-11 修复的回归险情（记录教训）**：第一版用 `len(resolved_times)>=2` 字面判定 → `tests/test_mainline_clarifier_memory.py::test_same_explicit_and_relative_period` 失败（「对比期是去年」被改写成 2023 年，字面两个 token 日历同年，不该算比较）；第二版按年份锚定 → 又把 2023-Q1/Q2 坍缩成同一年（SC-11 复挂）。**最终判据：绝对时间项用字面 normalized（自带离散粒度），相对词用 normalizer 的 TimeExpression 日历年份归约**——两类信号分开处理，四个用例 + 既有 22 项 clarifier 测试全过。

**SC-11 r2 暴露的深层问题（登记，不属本轮修复）**：r2 里 SC-11 答案能出（-100%），但闸门如实标了 `failed`——模型生成的 SQL 本身没写两个季度的时间过滤，答案数字是全量对比的碰巧结果，闸门在结果层标注了「条件被丢弃」。这暴露**生成层（prompt/模型）与闸门层的职责边界**：闸门能拦住「静默丢弃」，但正确做法是生成层就该写对 SQL。这属于 S2 后续迭代（错误候选修复回路，母方案 §8.3），不是闸门缺陷。
