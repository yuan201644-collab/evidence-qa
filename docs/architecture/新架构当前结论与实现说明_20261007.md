# 新架构当前结论与实现说明

日期：2026-10-07

## 一、当前结论

本项目的新架构不是简单把自然语言转 SQL、文档检索、多跳和 KAG 并列堆放，而是围绕一个主线组织问答：

> 一个答案中的每项事实，是否都有正确来源、明确对象关系和可回溯证据。

在全新的 CS10 合成留出集上，12 道题完成独立数据核验、数据库导入、文档索引、正式 A/B 运行和自动评分。结果为：

| 指标 | 匹配参考消融臂 | 新事实核验臂 |
|---|---:|---:|
| 正确性 | 0/12 | 12/12 |
| 引用完整性 | 0/12 | 12/12 |
| Trace 合规 | 7/12 | 12/12 |
| 平均耗时 | 10.64 秒 | 7.33 秒 |
| 运行错误 | 0 | 0 |

新架构臂 12 道题均进入跨源对齐流程，正确处理了合同有效期失效、映射有效期失效、双合同、客户冲突、非受控映射、等于上限、正常满足和超时等场景。

这只能说明：在当前受控合成题集上，事实核验机制有效。由于题目数量少、数据为合成数据、题型集中，且尚未完成人工盲审，不能表述为真实业务准确率或整体泛化能力。

## 二、新架构如何实现

### 1. 问题识别与事实计划

用户提出工单—合同问题后，路由层识别工单编号，生成一个有依赖关系的事实计划：

```text
工单编号
  ↓
工单记录：设备编号、开单时间
  ↓
设备主数据：设备客户
  ↓
合同设备映射：合同编号、映射依据、映射有效期
  ↓
合同主数据：合同客户、合同有效期、合同状态
  ↓
跨源关系核验
  ↓
合同文档：修复时限、适用设备、时间定义
  ↓
事件记录：accepted → service_restored
  ↓
时长计算、证据关联和最终回答
```

简单问题仍可走普通短路径，不强行增加多跳；工单—合同问题进入隔离的跨源事实核验链路。

### 2. 结构化查询

系统通过自然语言转 SQL 查询：

- 工单表获取 `equipment_id` 和 `opened_at`；
- 设备表获取客户归属；
- 合同设备映射表获取候选合同、映射有效期和 `mapping_basis`；
- 合同表获取合同客户、合同有效期和状态；
- 事件表获取 `accepted` 和 `service_restored` 时间。

SQL 在执行前经过只读校验和结构化 trace 记录，禁止写入数据库。

### 3. 跨源核验与有界早停

拿到结构化事实后，系统按固定约束核验：

- 设备编号是否明确对应，而不是仅凭设备名称；
- 映射依据是否属于受控依据；
- 映射有效期和合同有效期是否分别覆盖工单日期；
- 设备客户与合同客户是否一致；
- 是否存在多份同时有效合同；
- 事件是否缺失或时间倒序。

如果关系已经无法成立，系统在文档检索前安全早停，并输出限定回答，例如“无法判断：存在客户范围冲突”。这一步避免把候选合同直接套到工单上。

允许早停的主要原因码包括：

```text
validity_window_not_cover
ambiguous_active_contracts
customer_scope_conflict
mapping_basis_unapproved
event_time_reversed
key_event_missing
equipment_master_missing
```

### 4. 文档检索与条款核验

只有在对象关系、客户和有效期均通过后，系统才检索适用合同文档，核对：

- 修复完成时限；
- accepted 和 service_restored 的时间定义；
- 适用设备范围；
- 是否存在更高优先级的特别约定。

合同文档片段被写入引用列表，不能只把语言模型生成的文字当成证据。

### 5. 计算、回答和 Trace

最后以结构化事件计算：

```text
修复耗时 = service_restored - accepted
```

再与合同条款比较，形成“满足 / 超时 / 无法判断”结论。Trace 记录：

- 调用了哪些工具；
- 每一步的输入、输出和耗时；
- 命中了哪张表、哪个字段、哪条记录；
- 引用了哪份合同文档、哪段原文；
- 为什么早停或继续检索。

## 三、主要新增和修改内容

### 1. 核心实现模块

- `app/fact_planner.py`：定义工单—设备—合同—事件的事实依赖计划。
- `app/fact_executor.py`：执行事实计划，串联 SQL、文档检索、对齐和早停。
- `app/cross_source_fact_plan.py`：实现跨源事实查询、对象对应、有效期、客户、事件和文档核验。
- `app/evidence_ledger.py`：维护事实与 SQL/文档证据之间的对应关系。
- `app/tools/cross_source_policy.py`：集中定义受控映射依据、早停原因和跨源策略。
- `app/orchestrator.py`：增加事实计划路由、执行、答案投影和 Trace 合并；补充事件倒序、关键事件缺失、设备缺失等安全回答。

### 2. 实验与评分工具

- `eval/cross_source_heldout/tools/run_architecture_comparison.py`：运行匹配参考臂和新事实核验臂，保存运行前配置、随机调度、原始回答和封存哈希。
- `eval/cross_source_heldout/tools/score_architecture_comparison.py`：按 Gold 检查正确性、引用完整性、Trace 合规和耗时；现已支持 `old_workflow` 与 `matched_reference_ablation` 两种参考臂命名。
- `eval/cross_source_heldout/tools/load_cs10.py`：将 CS10 结构化数据导入独立 PostgreSQL schema。
- `eval/cross_source_heldout/tools/prepare_cs10_index.py`：为 CS10 合同文档建立独立 pgvector 索引。
- `eval/cross_source_heldout/tools/validate_cs10_package.py`：检查题包、Gold、哈希和隔离条件。

## 四、CS08/CS09 的处理结论

- CS08：原始运行未进入事实计划路由，且 Gold 与评分器契约不兼容，标记为工具链失败，不计入效果。
- CS09：数据和 Gold 独立核验通过，但正式评分器当时不支持 `matched_reference_ablation` 臂名，标记为计分兼容性失败；评分器随后修复，诊断结果不作为正式效果。

## 五、当前最稳妥的汇报口径

> 我们把数据库查询、合同文档检索和跨源融合统一组织成“事实核验链路”：先确认工单、设备、合同之间的明确对应关系，再检查客户和双重有效期，关系成立后才检索合同条款并计算事件时长；如果关系不成立就有界早停，并把每项结论绑定到结构化记录或文档原文。当前在独立复核的合成留出集上完成了一轮可复现 A/B，结果支持该机制在受控场景下减少错误关联并提高证据完整度，但真实业务泛化仍需更大规模数据和人工盲审验证。
