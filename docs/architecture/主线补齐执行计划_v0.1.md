## 一、目标与本轮结束条件

目标是把现有问数、文档问答、跨源核验和前端串成完整产品入口，重点补齐中级任务 3、4、5 的工程缺口：

```text
用户问题与会话
  → 恢复待澄清问题或确认新的问题
  → 要素识别与改写
  → 判断需要哪些信息和哪条业务路径
  → 必要时先澄清业务口径
  → 表与字段候选定位、关系核查
  → 必要时澄清候选之间的真实业务歧义
  → 规划关联路径、统计粒度和计算口径
  → 生成 SQL、只读校验、关联与粒度检查
  → 执行并组织结果、真实来源和步骤记录
```

文档问题继续使用既有 RAG（检索增强生成，即先取文档证据再回答）；已支持的工单—合同问题继续使用事实核验链路。表定位与关联检查是 SQL 工具内部能力，文档问题不强行经过它们。跨源事实计划只有在调用自然语言转 SQL 的事实节点上复用增强能力，不改成一个无边界的通用规划器。

本轮目标状态为“代码和接入文档具备可审阅的实现，等待测试”。用户要求暂不测试，因此后续实施期间暂停单元测试、在线试问、真实数据库查询、模型调用、性能跑分和新题实验。可以阅读代码、核对签名与调用关系、检查改动清单和文档格式，但这些动作不能替代运行验收。

未恢复测试前，业务改动保存在实施分支，交付逐文件差异和未验证清单。代码完成不等于任务攻克、准确率达标或比赛验收；不将未验证业务改动合并到 `main`。

## 二、事实基线与范围

### 已有实现怎样复用

| 环节 | 已核对的代码事实 | 本计划补齐内容 |
|---|---|---|
| 要素改写 | `app/nl2sql/normalizer.py` 已接入 `Orchestrator.answer` | 复用改写与 `unresolved` 记录，不重复另写一个改写器 |
| 澄清 | `orchestrator.py` 有路由级反问；响应契约已有 `need_clarify` | 业务槽位校验、待澄清状态保存、补充信息合并和恢复执行 |
| 多轮 | 接口接收 `session_id`；前端保存本地历史；当前后端 `answer` 未恢复会话状态 | 增加有界会话状态与上下文解析，避免“有聊天记录”等同于“后端懂上下文” |
| 库结构 | `schema.py` 有表、字段、主键和外键；生成器当前使用整库 `render_ddl()` | 独立候选定位、限定材料渲染、带依据的关系补全 |
| SQL 生成 | `generator.py`、`pipeline.py` 已实现生成、校验、执行及错误重试 | 将定位和关联计划作为显式输入，复用现有生成器与执行器 |
| SQL 校验 | `validator.py` 检查只读、存在性并控制返回行数 | 额外检查连接路径和统计粒度；语法通过不等于业务口径正确 |
| 跨源 | 事实计划、执行器、证据账本已入 `main`；装配仍通过显式开关启用 | 兼容新增 SQL 内部能力，保留原场景和业务规则边界 |
| 前端 | 有对话、澄清提示、SQL/PDF 证据和调用步骤组件 | 让真实澄清恢复和新增步骤可展示，完善会话生命周期说明 |
| 实验资产 | 本地有表定位、语义资产等研究材料，其中部分未跟踪 | 按来源和边界挑选可用资产；不整批导入，更不读留出答案编规则 |

不能仅凭缺少 `linker.py` 文件名判定表定位完全不存在；本计划依据的是当前主入口向 SQL 生成器提供整库材料、缺少明确候选产物的实际行为。任务 5 已有基础多表查询能力，补齐对象是质量控制和正式接入。

### 范围决定

1. Chinook 保留为普通问数主库；AdventureWorks 用于数十表定位。首先沿用既有环境配置选择一个活动数据源，不新增前端任意切库功能，不从用户文本随意推断连接地址。
2. 澄清与多轮覆盖有明确业务定义的范围，支持补时间、补指标、补对象、修改筛选条件和同指标追问；不承诺任意开放域记忆。
3. 表定位采用现有元数据、别名和本地向量能力；首版不引入新图数据库或整套智能体框架。
4. 多表质量检查先覆盖外键关联、显式业务连接、聚合、常用嵌套查询和一对多粒度风险；更复杂的查询明确标记能力边界。
5. 知识增强生成（KAG）在主链路中仍有占位实现，本轮不新增真实图谱接入。涉及跨源的真实演示配置应显式选择已实现能力，不能把预置图谱结果当作真实来源。
6. 最终 Word/PDF 报告、源码 ZIP 和独立实验属于后续交付阶段，本轮先补配置与说明的依据，不把所有比赛材料也混入这次代码补齐。

## 四、步骤 0 固定内部接入设计

### 执行动作

1. 核对最新 `main`、当前分支和工作区差异；从已核对基准创建 `codex/mainline-completion` 实施分支。如当前有未提交改动，先逐文件登记，避免通过切分支覆盖；不得重置或清理用户文件。
2. 新增 `docs/architecture/主线补齐内部接入约定_v0.1.md`，定义内部产物：
   - `QueryIntent`：问题对象、指标、时间、维度、筛选、目标粒度、各项来源。
   - `ClarificationDecision`：可继续/需追问/超出范围，待补槽位和可解释选项。
   - `SessionState`：待澄清原问题、已确认条件、最近成功问数上下文、过期时间。
   - `LinkResult`：候选表/字段、得分分项、关系补全、歧义、元数据版本和降级状态。
   - `JoinPlan`：选定连接边、连接类型、目标粒度、指标表达式、风险与来源。
   - `SemanticCheckResult`：通过/需修复/无法可靠判定及结构化原因。
3. 上述模型优先放入拟新增的 `app/nl2sql/planning_models.py` 及会话私有模型；它们是内部约定，不向 `app/contracts.py` 添加顶层字段。
4. 约定步骤记录（Trace，即代码录下的工具输入、输出和耗时）使用现有 `TraceStep`；候选推断放 `output`，只有实际查询/检索证据放 `hit`。
5. 定义单次请求共享的尝试次数和时间预算，避免定位、规划、生成、修复各自独立重试造成调用倍增。具体默认值在接入约定中注明“工程初值，未做效率验证”。

### 交付条件

新旧内部签名、装配入口、步骤名称、失败投影和模块责任明确；公共 API 仍使用既有请求与响应。每一内部状态都指明谁创建、谁消费、何时清除。

## 五、步骤 1 澄清和会话闭环

主要文件：拟新增 `app/clarifier.py`、`app/memory.py`；修改 `app/orchestrator.py`；按需要新增独立业务语义配置，例如 `data/semantic/mainline_query_policy_v0.1.json`。

### 执行动作

1. 从已维护业务口径和元数据抽取必需信息。不是所有问题都必须带时间：查客户名称列表无需年份；问同比增长则必须知道指标、比较期和分母定义。规则按意图定义，避免一刀切反问。
2. 从标准化问句形成 `QueryIntent`。需要模型提取时沿用既有国产客户端，配置超时、重试和失败降级；模型提议须经内部模型与业务规则校验，不让模型自行确立默认口径。
3. 处理 `normalizer.unresolved`：真实多义需要澄清；仅未被改写的普通词不能一律转成拒答。候选差异只是检索不足时应先补材料，不让用户回答系统内部表名问题。
4. 生成面向用户的最小追问，例如询问“销售额同比还是客户数同比”；`need_clarify=True` 时不执行 SQL，返回原问题及待补条件的步骤记录。
5. 按 `session_id` 保存待澄清状态。用户补充后填入对应槽位，保留原指标、筛选和已确认口径，再标准化并继续处理；明确新问题或“取消”时清除挂起问题。补充仍不够时追问剩余必要项，不能把任意下一条输入硬拼回旧题。
6. 使用进程内、有锁、有过期与容量上限的会话存储作为初版。相同会话请求顺序处理，不同会话隔离；存储失败或状态过期时提示重新提供条件。注明单进程限制，不把它当成跨机器持久记忆。
7. 保存最近成功查询的结构化上下文，支持“改看去年”“只看美国客户”等范围内追问。失败查询、未确认澄清和未经证实的模型输出不写入已确认业务事实。限制历史长度。
8. 当前浏览器删除会话并不会通知后端。首版通过过期清理和新会话编号隔离；如果产品要求立即同步删除，再单独定义接口，不能在前端暗示后端状态已同步删除。

### 交付条件

代码中能追踪“原问题 → 待补项 → 用户补充 → 合并意图 → 恢复执行”的状态转移；追问和无法判定有不同原因；暂停时不执行查询；会话边界、并发、取消与过期处理有明确实现。此条件是代码审阅要求，不宣称流程已经在线运行成功。

## 六、步骤 2 精准表与字段定位

主要文件：拟新增 `app/nl2sql/linker.py`；修改 `schema.py`、`generator.py`、`pipeline.py` 和工具装配；复用 `infra/schema_meta*.json` 及已有本地向量接口。

### 执行动作

1. 为业务库构建只读元数据视图：表说明、字段说明、别名、主键、外键、样例值及来源版本。`schema_meta.json` 是导出物，不在其中手写业务解释；中文描述和业务口径使用独立叠加文件。
2. 明确活动数据库与元数据的绑定。目录需支持“数据库 + schema + 表 + 字段”的稳定标识；当前表名字典以裸表名索引，必须处理不同 schema 同名表的冲突，保留唯一名称下的兼容查询接口。同步存在性校验的全限定名称处理，不能只改提示词。
3. 将表说明和字段说明构成可检索材料，结合中文别名匹配、关键词匹配和向量召回。向量组件通过接口注入，避免在 `app/nl2sql` 导入时加载整套 RAG 或模型；索引构建作为显式准备操作，此轮不运行。
4. 以用户实体、指标、时间和筛选分别召回候选，保留分项得分与命中依据。高相似度只是候选证据，不能作为对象关联成立或业务概念等价的唯一依据。
5. 根据真实外键补齐连接候选，中间表可以没有直接语义命中。区分业务必需表、字段候选表和关系补全表；避免只取语义得分最高的一张表后丢掉合法路径。
6. 进行结构化候选选择：模型只能从存在的标识中选择；代码核对对象、字段、关系和候选覆盖。存在“销售 vs 采购”等业务歧义时返回步骤 1 的澄清；元数据缺说明时返回材料缺口，而非向用户伪造选项。
7. 增加限定目录渲染，将选中表、完整必要字段及连接关系交给生成器；校验仍使用完整权威目录。若 SQL 引用了未选中但真实存在的表，记录偏离并重新定位或进入有限扩展流程，不能绕过定位约束静默放行。
8. 首版预算建议：候选每轮至多 8 张语义表，关系补全后至多 12 张，自动扩展至多 1 次。均为工程初值；多 schema 和视图覆盖超出能力时明示。向量不可用时允许显式关键词降级；不能把降级输出描述成完整语义定位成功。

### 交付条件

`Nl2SqlPipeline` 有独立的 `LinkResult` 输入输出；数十表目录不会默认全文塞给 SQL 生成器；候选、排除依据、关系补全和降级状态都可追踪；本地索引与库配置的选择不依赖留出题或答案。

## 七、步骤 3 关联路径与统计粒度控制

主要文件：拟新增 `app/nl2sql/join_planner.py`、`app/nl2sql/semantic_validator.py`；修改 `generator.py`、`pipeline.py`；复用 `validator.py` 的只读闸门及现有执行器。

### 执行动作

1. 依据外键图和用户目标构建连接候选，记录每条边的表、列、方向和依据。最短路径不必然是业务正确路径；有多条合法路径且业务含义不同，回到澄清，不自动取第一条。
2. 无外键的合法业务连接，只接受明确维护且有出处的连接规则。禁止依靠同名字段或设备名称自行创建连接。连接规则不从研究报告的“标准答案 SQL”直接抄入。
3. 在 `JoinPlan` 明确基础记录粒度、输出分组、度量表达式、筛选发生位置和一对多关系。主键/外键可以证明部分基数；缺少唯一性约束时不能臆造一对一。
4. 将规划结果作为生成器的显式约束。支持普通 JOIN、预聚合、存在性筛选（EXISTS）、公用表表达式（CTE）和需要的嵌套查询；按需求选择，不要求所有问题都输出复杂 SQL。
5. 先执行既有 `sqlglot` 只读和存在性校验，再用同一 SQL 的抽象语法树（AST，即查询的结构化表示）核对连接条件、连接类型、分组与聚合粒度。合法语法不自动得到“业务语义正确”标签。
6. 对一对多连接后的父表金额累计检查重复计数风险；按明细求和并非天然错误。只有存在可说明的风险和粒度冲突时才阻断或请求修复；不能用 `DISTINCT` 或 `SUM(DISTINCT amount)` 一律消重。
7. 显式保留零记录对象需求、左连接空值语义、日期范围和过滤位置；不要为了强制外键路径把合法左连接改为内连接。关联路径检查需按查询作用域处理别名、CTE 与子查询。
8. 首版无法可靠解析的复杂派生关系返回“校验能力不足”，注明节点与原因；不能仅因校验器不支持就说“数据库没有数据”，也不宣称该查询已完成语义校验。
9. 关联/粒度错误复用现有有限修复循环，提供结构化失败原因。所有重新生成的 SQL 再过完整闸门；总尝试预算与现有生成次数统一记账，禁止新增无限循环。
10. 结果引用区分源行与派生汇总。汇总结果应展示实际 SQL、来源表字段和返回值；没有真实主键时不把排名或结果首列伪装成数据库行主键。

### 交付条件

关联计划、生成 SQL、只读校验、语义检查、实际执行互相对应；执行入口只接收已经通过必要检查的 SQL；未知口径和不支持结构分别记录；单表查询仍走简化路径。

## 八、步骤 4 统一主入口并衔接新架构

主要文件：`app/orchestrator.py`、`app/tools/nl2sql.py`、`app/nl2sql/pipeline.py`、`app/main.py`；必要时修改跨源装配处。

### 执行动作

1. 增加意图、澄清、会话和定位组件的依赖注入与惰性装配。配置缺失时给出明确状态，不能静默换库或混用不同目录。
2. 普通问数走“会话恢复 → 改写 → 语义校验 → 定位 → 关联计划 → SQL 生成/校验/执行”；单表省略不必要关联规划。
3. 文档问答继续复用既有文档入口。会话续问指向上一份文档时，只传递已确认文档标识与用户条件，不把上一轮回答正文当成新检索证据。
4. 工单—合同事实链保持现有对象对应、双有效期、客户、事件和文档核验。对 SQL 增强组件提供兼容开关，历史冻结源码和封存回答不改写；今后新代码表现另记版本。
5. 内部下游也能提出澄清：扩展私有 `Nl2SqlOutcome` 和 `ToolResult.data` 状态表达，由编排层投影到现有 `AskResponse.need_clarify`。不能最后统一写死 `need_clarify=False` 而吞掉字段/关联歧义。
6. 处理共享单例中的请求状态：`Nl2SqlTool._last_sql` 不能成为并发请求的可靠来源；实际 SQL 从本次结果投影，会话与引用也来自本次请求。
7. 新步骤统一通过 `merge_trace` 排序，引用从实际步骤汇总。不要复制同一改写/澄清步骤两次；无真实命中的规划步骤 `hit=None`。
8. 错误正文明确区分：需用户补充、业务无法确定、定位/校验能力不足、数据为空、服务异常。只有实际数据库零行或实际检索结果才能支持“未找到数据”。

### 交付条件
