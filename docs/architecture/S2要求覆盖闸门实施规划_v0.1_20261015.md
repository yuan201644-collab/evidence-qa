## 0. 一句话

S1 让残缺问句**更早被问出来**；S2 要让**条件在 SQL 里真的生效**——用户说"巴西"，SQL 里就必须有巴西，没有就不许执行。

---

## 1. 为什么 S2 必须单独一轮做

### 1.1 它和 S1 的风险面根本不同

| | S1（已交付） | S2（本规划） |
|---|---|---|
| 位置 | 澄清前 | 生成后、**执行前** |
| 行为 | 只**加**追问 | 会**拦**正确或不正确的 SQL |
| 失败后果 | 多问一句（烦） | 该答的答不出来（**回归**） |
| 影响面 | 澄清器一个分支 | 全库所有问数路径，含 T4/T5 |

S1 写错最多是"多问一次"；S2 写错会让**本来能答对的题答不出来**。母方案 §5.4 自己写明了：

> `:270` 先覆盖既有 T4/T5 正确样例使用的结构；**不能用全拒绝复杂 SQL 的办法实现"安全"**。

而 T4 是 AdventureWorks（71 表、76 万行）、T5 是 20/20 的既有能力。这是本项目最不能碰坏的两块。

### 1.2 母方案 §5.4 是"编译器级"工程量

§5.4.2 要求：

> `:267` 使用 sqlglot 的作用域、表别名和列来源解析；逐个核对 `WHERE`、`HAVING`、必要的 `ON`、条件聚合和子查询中的有效条件。
> `:269` `LEFT JOIN` 的 `ON` 与 `WHERE` 条件不天然等价；外连接、空值及否定语义必须单独判断。
> `:270` 覆盖 CTE、嵌套、`EXISTS`、窗口等结构。
> `:271` 支持确定可证的等价形式，如别名变化、`AND` 条件交换、相同含义的区间表达。

这实质是**写一个 SQL 语义等价性判定器的一个子集**。"证明某个条件确实约束了目标行"和"证明两种写法等价"，都是需要穷举作用域、基数、空值语义的问题，不是加几条 if 能收口的。

### 2.1 盲区实证（母方案 P02/P03/P04 的代码定位）

- `semantic_validator.py:124-125`：单表查询直接 `return SemanticCheckResult("pass", "single_table", "单表查询无需关联路径检查")` —— **一条谓词都不看**。「发票」漏年份、「巴西」丢国家都在这里穿过。
- `:35` 恒假检查只挡 `WHERE` 恒假，**不挡 `WHERE ... OR TRUE`**（`_constant_predicate` 判不了含 `OR` 的恒真式）。
- `:40` `_requested_aggregate_missing` 只查"有没有聚合表达式"，**不查聚合类型对不对**（平均变合计穿过）。
- 校验器收到的 `question` 只用于 `_growth_rate_scale_issue` / `_requested_aggregate_missing` 两处**关键词**判定，没有结构化要求可比对。

**结论**：要在现有校验器上加"要求覆盖"检查，等于给它加一整套新的判定维度。这就是 S2 的实体。

## 3. 必须收口的口径（母方案遗留矛盾）

### 3.1 三态 vs 二态（我评审的 P1，**必须先定，否则写不下去**）

母方案内部打架：
- `:271`「无法证明等价时保留明确原因，**不声称一定错误或已经通过**」→ 承认有第三态
- `:363` S2 门槛要求「**正确等价 SQL 通过**」→ 只有通过/不通过

但代码里其实**已经有第三态**：`SemanticCheckStatus = Literal["pass", "repair", "unknown"]`（`planning_models.py:14`）。

**定论**：沿用既有三态，不新造。语义映射：

| 现有状态 | S2 含义 | 处置 |
|---|---|---|
| `pass` | 已证明要求被满足 | 放行执行 |
| `repair` | 已证明要求**未**满足 | 回灌重写；用尽则**不执行** |
| `unknown` | **无法证明**（结构不支持/信息不足） | 见下 §3.2 |

### 3.2 `unknown` 的处置必须按模式分开（否则一定出事故）

同一句"无法证明"，在演示和评测里该做完全不同的事：

| 模式 | `unknown` 处置 | 理由 |
|---|---|---|
| `enforce`（演示/验收） | 不执行，如实说明"无法确认条件已生效" | 宁可不答，不答错 |
| `warn`（默认） | 执行，但 trace 标 `requirement_gate_status=unknown`，核验卡显示"部分条件未能确认" | 不阻断现有能力 |
| `off` | 不检查 | 紧急回退 |

**默认必须是 `warn`**（我评审的 P3）。理由：T4/T5 是已验收能力，S2 引入的 `unknown` 一旦默认拦截，等于把既有战绩作废。等 L1/L2 层测试证明 `unknown` 在 T4/T5 场景下为 0，再由负责人决定是否转 `enforce`。

开关名建议 `NL2SQL_REQUIREMENT_GATE`，取值 `off|warn|enforce`，默认 `warn`。

**⚠ 与母方案 §5.4 `:248` 的冲突**：母方案说"不受 `NL2SQL_SEMANTIC_PLANNING_ENABLED` 控制"。这一点我同意（关掉表定位不等于允许丢条件），但**前提是闸门自己能独立拿到表元数据**。`semantic_planning_enabled=False` 时 `join_plan` 为 `None`（`pipeline.py:268`），闸门只能靠 `catalog` + 清单工作。S2 的检查项必须据此分成两档：

- **不依赖 join_plan**：时间、数值、否定、排名、分组、作用域 —— 这些只比对 SQL AST 与清单
- **依赖 join_plan**：关联粒度、基数口径 —— 这档在 planning 关闭时降级为 `unknown`

### S2-1 结构能力台账（1 天）

**目标**：先回答"闸门认识哪些 SQL 结构"，而不是先写检查。

产出一个模块级常量表，逐项声明"这种结构闸门能不能读懂"：

```
# app/nl2sql/requirement_validator.py
_SUPPORTED_SCOPES = {
    "simple_where":        supported,   # 单表 WHERE
    "join_where":          supported,   # 显式 JOIN + WHERE
    "having":              supported,
    "conditional_agg":     supported,   # CASE WHEN 里带条件
    "subquery_in_where":   supported,
    "exists":              partial,     # 只认顶层相关性
    "cte":                 partial,
    "window":              partial,
    "left_join_null":      unsupported, # ON 与 WHERE 不等价，暂不判
    "union":               unsupported,
}
```

**为什么先做这个**：母方案 §5.4.2 `:270` 说"覆盖 CTE/嵌套/EXISTS/窗口"，但没说覆盖到什么程度算够。台账把"能不能读懂"变成**显式可查的表**，于是：

- 遇到 `unsupported` 结构 → 返回 `unknown`（不是 `repair`），行为可预测
- 每加一种结构 → 台账 +1，同时补正确写法与绕过写法测试（母方案 §9.3 `:659-661` 的要求）
- 报告里可以说清"闸门当前认识 N 种结构，未覆盖 M 种"——比"大致支持"可信

**这一步不做，后面所有检查都会在复杂 SQL 上给出无法解释的判定。**

---

### S2-2 单表条件覆盖（1.5 天，**收益最大的一步**）

只做 P02/P03/P04 那三类，全部**不依赖 join_plan**：

| 检查 | 清单来源 | SQL 侧依据 | 拦截的错 |
|---|---|---|---|
| 时间条件覆盖 | `of_kind("time")` | AST 里目标表的时间列是否被 WHERE 约束 | 「发票」漏年份 |
| 取值筛选覆盖 | `of_kind("value_filter")` | 规范化取值（如"巴西"→`Brazil`）是否出现在约束目标对象的谓词里 | 「巴西」丢国家 |
| 数值与否定 | `of_kind("numeric_range")`/`("negation")` | 比较方向、开闭边界、否定语义 | `>100` 变 `>=100`、`不在`变`在` |

**取值规范化怎么做**：不能只匹配字面。用 `app/routing_signals.py` 的既有词表 + 列 `description` 做同义展开（"巴西"/"Brazil"/"BRA"），查 `catalog` 里目标列的说明。**拿不到规范化映射时返回 `unknown`，不要返回 `repair`** —— 否则"用户说了巴西、库里存的是 Brazil"会被误判成漏条件。

**验收**：SC-02/03/05/08/10/26/27/31/32 九项中与单表相关的全部拦住；T5 20/20 **一项不退**。

---

### S2-3 聚合与排名口径（1 天）

| 检查 | 拦截的错 |
|---|---|
| 聚合类型一致 | `of_kind("measure")` 说"平均"，SQL 里是 `SUM` → `repair` |
| 去重依据 | 客户数用 `COUNT(*)` 而非 `COUNT(DISTINCT customer_id)`（一客多发票场景） |
| 排名方向与前 N | `ranking` 说"最高"/"前3"，SQL 是 `ORDER BY ... ASC` 或 `LIMIT 1000` |
| **`LIMIT 1000` 不算前 N** | 母方案 `:272` 明写。自动补的 LIMIT 已在 `pipeline.py:542-546` 识别（`automatic_limit`），闸门必须拿这个标记排除，否则每条"前3"都会被自动补的 1000 满足 |

**`LIMIT 1000` 那条是最容易假通过的地方**——自动补 LIMIT 是现有安全机制，如果闸门把"SQL 里有 LIMIT"当成"用户要的前 N 已满足"，等于给所有排名题发假通行证。

---

### S2-4 条件作用域（1.5 天，**最难**）

母方案 `:261`：条件只在无关子查询/注释出现、`OR TRUE`。

- `OR TRUE` 恒真式：扩 `_constant_predicate` 处理 `OR`，或保守地"含有顶层 OR 且一侧为常量真 → `unknown`"
- 条件必须约束**目标行**：`JOIN ... ON cond` 里的条件不约束被 LEFT JOIN 的表（`:269`）
- 子查询作用域：条件在无关子查询里 → 不等于生效

**这一步是母方案 §5.4.2 全部要求里最重的**。建议**先只做 `OR TRUE` 与"条件出现在注释里"两种**（这两种可静态判定、无歧义），其余推给 `unknown`。理由：作用域等价性是开放问题，`unknown` 比一个会误判的 `repair` 安全得多。

## 5. 验收门槛

### 5.1 硬门槛（不达标不算完成）

1. **零回归**：T4、T5 分数**不低于 S2-0 基线**，逐题对照
2. **九项真拦**：SC-02/03/05/08/10/26/27/31/32 全部按预期拦截
3. **等价不误杀**：母方案 §8.3 的正确写法清单全部 `pass`
4. **`unknown` 可解释**：每个 `unknown` 都能说出"因为 X 结构不在台账里"，不允许出现"不知道为什么"
5. **未执行即未执行**：被拦的 SQL 不得出现在答案里冒充已查询（母方案 `:279`）

### 5.2 每个检查项的最低证据

| 检查项 | 必须有的三条测试 |
|---|---|
| 时间覆盖 | ①漏年份被拦 ②正确年份通过 ③等价区间写法通过 |
| 取值筛选 | ①丢国家被拦 ②规范化取值通过 ③别名写法通过 |
| 否定 | ①`不在`变`在`被拦 ②正确否定通过 |
| 聚合 | ①平均变合计被拦 ②正确聚合通过 |
| 排名 | ①`LIMIT 1000` 不算前 N ②`ORDER BY` 反向被拦 ③正确前 N 通过 |
| 作用域 | ①`OR TRUE` 被拦 ②条件在无关子查询被拦 ③正确作用域通过 |
