# 跨源问答新旧流程对照预注册 v0.4

版本日期：2026-10-04  
适用范围：源码可信度审计后、v0.11 留出包内容或 Gold 被实现者/运行者查看前的新一轮实验（此前 v0.8–v0.10 均经独立审查判为无效，保留但不运行）。  
关系：本版在 v0.3 基础上作前置方法学修订；未有本轮正式回答或计分结果，故不存在看结果后改判据。v0.3 原件保留，仅供追溯。

## 1. 研究问题与可支持结论

比较旧流程和新事实核验流程在同一批冻结合成跨源问题上的端到端配对表现。两臂使用完全相同的问题、结构化数据、文档语料、数据库快照、检索索引、模型端点及逐次调用参数。题目交错调度；每题每臂只运行一次。模型调用数、重试数、数据库/检索调用数及耗时是系统成本结果，不人为强行设成相同；因此本实验比较的是两套完整流程，不作单一模块因果归因。

唯一主指标为“严格证据支持成功率”：每个候选回答只有同时满足“人工最终正确性=正确”且“人工最终证据=充分”才计 1，否则计 0；运行错误、超时、空答均计 0。报告新流程与旧流程各自计数、逐题配对转移表，以及配对差（新流程成功题数减旧流程成功题数，除以总题数）。不得只报汇总百分比，不以事后挑选的子组替代主指标。

次要指标单独列出，不合成总分：正确性四类分布、证据四类分布、过度拒答题数、错误肯定/关系错配/无证据断言题数、可回答题上的正确数、应拒答题上的恰当拒答数、自动 trace 合规、模型/SQL/RAG/重排调用和重试次数、运行失败与端到端耗时分布。所有题型口径以包外 Gold 和运行前冻结的判分映射为准；不得在见到输出后新增排除题、改主指标或改题型。

只允许结论表述为“在这批冻结的合成题上观察到……”。小样本只报告描述性配对计数，不称统计显著、总体准确率提升、真实业务有效或赛题验收完成。

## 2. 题集、代码和运行冻结

1. 留出集不少于 16 题，正式运行器实施同一最低门槛；上限 64 题。问题行只允许 `case_id`、`question`，以及可选的冗余 `work_order_id`；若省略冗余编号，运行器仅从题面提取唯一一个格式合规的工单号并记录，零个/多个编号均拒绝。数据作者不参与实现，Gold 核验者与作者分离；核验者从包内表格、合同原文独立重建关系、时限、结论与引用子串。题包不得含 Gold、标准答案、预期状态、组别、密钥或作者解释。每条 Gold 必须显式填写且只填写一个 `expected_retrieval_state`：`clause_present_expected`、`bounded_not_found`、`retrieval_not_required`。早停题的 `expected_doc_ids` 与 `required_doc_snippets` 必须为空且不得要求合同文档引用；有界未命中题的文档 ID/文档片段也必须为空，并按判分代码声明两次实际尝试的策略/状态/候选数；条款存在题则用 `required_doc_snippets` 列出真正支持结论的合同文档原文子串，并列出对应 `expected_doc_ids`。SQL 与文档引用必须来源分型为 `required_sql_snippets` 和 `required_doc_snippets`；禁止来源不明的 `required_ref_snippets`，且文档片段只在指定预期文档的引用中匹配。`clause_present_expected` 不得声明预期早停，实际 trace 也不能同时包含白名单早停原因与文档检索。每条 Gold 还必须显式填写布尔值 `absence_evidence_required`；凡结论依赖数据库中的“没有匹配行/未找到记录”等负面事实，设为 `true` 并同时填写 `required_absence_refs`（表、字段及零结果引用片段）和 `required_absence_checks`（表名及精确过滤条件），否则设为 `false` 且两数组均为空。Gold 预验证器须在整批评分前拒绝字段缺失、两侧字段只填一侧、表集合不一致或检索状态约束冲突。题目、Gold、检索期待三者不得互相矛盾。
2. 运行前冻结协议、运行包、源码/依赖、模型可识别信息、只读数据库和索引快照、时间锚点、环境参数、随机调度种子及配置。协议、运行包、源码和登记分别计算 SHA-256；登记与其哈希保存在项目工作区之外。Git 工作区可为脏，但相关源码逐文件哈希必须进入登记，并且运行前后完全一致。
3. 若运行者/实现者在正式运行前看到 Gold、独立核验的答案细节或人工试跑结果，并据此改代码/参数，该包即降为回归集；确认性试验须换新的独立包并重做复核与冻结。
4. Gold 不进入运行进程。运行器只读显式指定的运行包，输出原始回答、来源、trace、耗时和错误；完成后封存并将 sealed manifest 哈希锚定在工作区外。封存后，评分器才接受显式题集、Gold 与三份外部哈希锚点，并在运行目录外输出评分文件。任何哈希/计数/配对校验失败均保留原运行并标记无效，不覆盖或选择性重跑。

## 3. 人工匿名评审与判分细则

1. 两位未参与实现、出题或 Gold 制作的评审者，使用两个分别随机化、候选级打乱且不显示配对关系的匿名表，独立评阅全部候选。匿名表只显示随机的 A/B 标签，不显示其对应流程组别、trace、Gold、密钥或运行先后。评审者可查看相同的冻结运行包（问题、CSV/结构说明、合同原文），但不可查看 Gold、另一人的意见或组别密钥。回答风格仍可能泄露流程臂，故称“匿名标签评审”，不宣称完全盲法。
2. 正确性标签：
   - 正确：最终业务结论和关键理由均与独立核对的冻结源数据/合同原文一致；有依据的恰当拒答也可正确。
   - 部分正确：结论方向成立，但关键事实、计算或理由有实质遗漏/错误。
   - 错误：结论与源材料矛盾，或面对可确定题作不恰当拒答，或面对关系未确立题作无依据肯定。
   - 无法判断：源包本身仍无法消歧，且回答准确表达该限制；若源包可确定而回答拒答，按错误或部分正确判，不记“无法判断”。
3. 证据标签：
   - 充分：所有决定结论的关键事实均有可定位且直接支持的 SQL/文档证据；拒答也有支持早停/缺失判断的证据。
   - 部分充分：主要结论证据可核，但存在非决定性引用缺口或不完整定位。
   - 不充分：至少一项决定结论的事实缺少支持证据。
   - 引用不匹配：引用片段不存在于所指来源、与原文不符或实际支持相反结论。此类标签单列，不并入“充分”。
4. “过度拒答”只标在未给确定业务结论、而冻结源包足以支持结论的回答；不确定则标“无法判断”，并在备注说明。未过度拒答不代表结论正确，正确性与证据仍分别判分。
5. 安全早停原因代码仅允许：`mapping_unresolved`、`equipment_master_missing`、`mapping_basis_unapproved`、`validity_window_not_cover`、`key_event_missing`、`customer_scope_conflict`、`event_time_reversed`、`ambiguous_active_contracts`。多份有效合同无法唯一确定适用范围时使用 `ambiguous_active_contracts`，运行器必须在 trace 中显式记录该原因代码。白名单以冻结源码中的 `EARLY_STOP_ALLOWED_REASONS` 为准；题集、判分实现和协议若不一致，不运行。
6. 两位评审者对每个候选的正确性、证据或过度拒答标签不一致时，第三位未参与前两轮的评审者仅审阅该争议项和同一冻结源包，独立给出最终标签；不提供前两人的标签或流程组别。保留两份原始意见、第三人意见及最终标签，不以讨论协商替代记录。
7. 报告正确性、证据、过度拒答的两评审逐类原始计数、完全一致率及未加权 Cohen κ（仅描述性，注明小样本和类别不平衡限制；若因类别分布导致 κ 无定义则如实记为无定义），另报告需要第三人裁决的数量及裁决前后分布。完成全部评分后，两位评审各自记录是否猜出匿名 A/B 映射及置信度；汇报该盲法检查，但不据此事后剔除评审或答案。
8. 每位评审必须用各自独立调用盲审表生成器所产的候选级随机表、对应空白 JSONL 评分模板及盲法检查模板；不得把同一模板复制给两人。模板逐行携带匿名表 SHA-256，评分器须验证评分、盲法检查与密钥绑定，并拒绝相同匿名表哈希或相同 A/B 映射。评分汇总固定使用 `score_architecture_blind_review.py`：按各自包外密钥映射回同一 `case_id × arm`，对一致项取共同标签，对任一维度有分歧的候选必须且只能有一条第三人完整裁决。保存两份原始填写、裁决 JSONL、密钥（工作区外）及机器生成汇总文件与哈希；不手工重编码/挑选候选。

## 4. 运行成本与可比性

两臂的模型端点、温度、每次调用超时/重试参数、数据库/索引和只读权限保持一致。新事实核验流程中的数据库操作时限由运行器明确固定为 5000 毫秒，文档检索最多两次；该工具级限制属于新流程设计，不等同于两臂总算力/Token 配额相同。不同架构按其既定流程可能产生不同数量的模型、SQL、检索和重排调用，这正是端到端运行成本的一部分；逐题完整报告调用数、重试数、超时/错误及耗时分布。不能把效果差异单独归因于“事实依赖”或其他单项机制，也不能声称在同等 Token 预算下比较。若远程模型未披露修订号或 Token 账单，明确记为不可得/未测。

## 5. 审计边界与中止条件

独立技术审计者另行核对已封存 trace：SQL 只读、精确对象关系、适用期限与客户、引用与工具证据对应、缺失元数据来源、允许早停原因及调用限制。技术审计不接触 Gold 配对密钥；匿名答案评审不看 trace。

出现运行包/Gold/代码哈希不符、数据库或索引快照漂移、题目与 Gold 配对异常、Gold 或密钥进入运行进程、封存不完整、源码运行前后变化、任何选择性重跑/删题，均将本轮标为无效或探索性；保留材料并说明原因，不用修补运行结果的方式“补救”。
