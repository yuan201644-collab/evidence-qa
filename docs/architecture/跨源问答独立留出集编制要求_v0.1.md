# 跨源问答独立留出集编制要求 v0.1

版本：v0.1  
日期：2026-10-08  
用途：交给未参与本轮跨源架构实现、调参和既有题集制作的组员，独立编制下一批配对实验题目。  
依据：`docs/architecture/跨源问答新旧流程对照预注册_v0.8.md` 及其继承的 v0.4–v0.7 规则。

## 1. 目标和不可越过的边界

目标是建立一批此前没有用于开发、调参或回答的跨源问答题，用相同问题、数据、文档、模型和资源条件比较“匹配参考流程”与“新事实核验流程”。实验要检验的核心是：事实依赖、对象关联、口径核验、证据关联和有界早停，能否减少错误肯定，同时避免把本可回答的问题过度拒答。

这批数据可以是合成数据，但必须明确标注为合成。实验最多支持“在本批冻结题目和配置上观察到……”，不能据此宣称真实业务效果、跨行业泛化、法律解释正确或比赛验收完成。若题目、Gold 或答案已被实现者用于改代码或参数，该批只能作开发回归，不能再称未见留出集。

## 2. 人员分工与独立性

至少区分以下角色，姓名/代号、职责和接触日期写入编制记录：

| 角色 | 可以接触 | 不得做的事 |
|---|---|---|
| 出题与数据作者 | 题目、运行数据、合同文档、Gold | 不得参与本轮架构实现/调参；不得依据旧题、旧 Gold、既有模型回答或失败清单改造题目；不得担任本批 Gold 独立复核人 |
| Gold 独立复核人 | 冻结运行包、Gold、协议 | 不得查看模型回答、A/B 组别密钥或盲审结果；逐题独立重建数据事实和判据，不以作者脚本自检代替复核 |
| 运行者/保管人 | 冻结运行包、运行配置；原始回答封存前不得接触 Gold 或组别密钥 | 不得读 Gold、调题、选题、选择性重跑或按答案修改实现 |
| 答案评审人 | 匿名候选回答及同一无 Gold 冻结运行包 | 不得查看 Gold、流程标签、配对密钥、其他评审意见；不得参与实现、出题或 Gold 制作 |

确认性主结果须按 v0.8 采用两名未参与实现、出题和 Gold 制作的真人评审，对两臂全部匿名回答逐条独立评分；任何正确性、证据或过度拒答标签分歧均按预注册交第三人盲态裁决。若只能使用 AI 评审，结果必须标为探索性，AI 评分不得冒称真人独立评审。

作者应提交简短独立性声明：未查看旧批次 Gold/答案、未参与本轮实现和调参、未查看本批 A/B 输出；如有任何一项不满足，须如实披露并将题包标为已曝光/开发集。

## 3. 题目和数据怎么设计

### 3.1 新颖性与可比性

- 新建一个与既有题包不同的业务场景、实体、编号、合同文本和关系记录；不得只替换编号、日期或数值，也不得把旧题改写后宣称新题。
- 保持被比较的核心任务和系统接口可比：问题仍要求从工单/事件等结构化记录出发，确认对象与适用合同，再读取合同文档中的服务恢复时限，给出有证据的结论或有依据地停止。
- 为避免把“换数据模式”与“换架构”混为一谈，优先沿用现有运行器支持的五类数据关系（工单、设备、设备—合同映射、合同、工单事件）和文档检索接口。确需改表结构、工具契约、早停码或题目字段时，先确认运行器、比较器和 v0.8 协议都支持，修改后重新测试、冻结；不得边出题边扩展运行器。
- 不使用未经授权的真实合同、客户或个人信息。使用真实数据时须有授权、脱敏记录和来源说明；默认使用合成数据，并在文件及报告中明确标注。

### 3.2 题数和覆盖

- 题数必须在运行前协议中固定；按继承规则不少于 16 题、不多于 64 题。建议以 32 题作为便于与近期实验比较的工作量，但这不是统计功效保证；不得看过回答后增删题目。
- 覆盖需同时含“材料足以判定”和“证据不足/关系不成立时应停止”两大类，不能把题目全部做成负例。建议预先规划并列出题目覆盖矩阵，至少考虑：
  - 可判定的时限内、恰好等于上限、超过上限；
  - 唯一受控映射、无映射/悬空映射、非受控映射、同名但编号不同的干扰对象；
  - 映射有效期与合同有效期分别失效、未生效、端点日期；
  - 客户或文档范围冲突、多份同时有效合同；
  - 合同状态不可用；关键事件缺失、时间倒序；
  - 合同明确约定时限、明确未约定恢复时限、条款冲突未消解；响应/到场时限不得偷换成恢复时限。
- 这些是候选覆盖维度，不要求每题叠加多个陷阱。复合负例应注明每个阻断事实及预期停止点；要用简单正例验证系统没有只学会拒答。问题措辞不得泄露预期结论、映射关系或答案标签。
- 所有规则（时区、时间起止事件、闭/开区间、合同状态含义、映射依据白名单、多合同如何处理）都要在协议中作为本题集的操作化约定明确写出，不能伪装成法律或行业通则。Gold 和数据必须严格遵守同一套规则。

### 3.3 一题一事实链

每个 `case_id` 对应唯一工单和一条可复核的事实链。作者应从冻结源数据逐题确认：

1. 工单对应哪台设备；
2. 是否有明确的设备—合同关系，依据是否受控；
3. 设备客户、合同客户和文档适用范围是否一致；
4. 映射有效期与合同有效期是否分别覆盖题目规定的业务日期；
5. 合同状态是否允许按本题操作化规则判定；
6. 哪些事件是计时起点/终点，是否缺失或倒序；
7. 哪份实际文档规定恢复时限，是否存在冲突或明确未约定；
8. 若可计算，耗时、单位、时区和与阈值比较结果是什么。

除预先定义的“不确定”题外，每个问题都应有唯一 Gold 状态。不得用名称相似作为对象关联依据；也不得将检索候选本身当作已确立事实。

## 4. 运行包与 Gold 隔离

运行包只放系统作答所需材料：问题、结构化数据、schema/字段说明、合同文档、文档清单、装载所需文件、运行说明及运行文件哈希清单。问题记录遵守当前运行器契约：`case_id`、`question`，以及运行器明确支持时才可带冗余 `work_order_id`。

运行包严禁出现 Gold、答案、预期状态、正确耗时/阈值、题型组别、A/B 标签映射、配对密钥、作者解释或能直接还原结论的文件名/元数据。运行包目录与 Gold 目录必须物理分离；Gold 和组别密钥由保管人单独保存，不交运行者。分别生成运行包、Gold、协议和源文件的 SHA-256 清单；在工作区外登记冻结摘要。任何修订都建立新版本、重算哈希并重新复核，不覆盖旧版本。

每题 Gold 按当前评分器 schema 填写并通过机器校验，至少覆盖：`expected_status`、恰好一个 `expected_retrieval_state`、预期文档、必需 SQL/文档证据、适用时限指标、早停原因及缺失证据判据。SQL 证据须能回到真实表、行主键、字段和值；文档片段须是指定文档中的逐字连续原文。

检索状态使用当前协议规定的值：`clause_present_expected`、`bounded_not_found`、`retrieval_not_required`。明确“合同未约定”必须由合同原文中明确声明支持；“本次有限检索没找到”只能表示 `bounded_not_found`，不能据此断言原合同没有该条款。条款冲突题须列出冲突双方的文档证据，并把无法消解写成预期状态；不得挑一条方便的条款做 Gold。

若结论依赖“没有该行/没有该事件”等数据库负面事实：Gold 必须要求执行层生成 `absence_checks` 元数据（表名、精确过滤字段和值、实际行数为 0），并同时列出相符的负证据引用判据。不得把模型在自然语言里声称“零行”当成数据库证据。

早停许可必须与冻结代码中的 `EARLY_STOP_ALLOWED_REASONS` 完全一致。当前白名单为 `mapping_unresolved`、`equipment_master_missing`、`mapping_basis_unapproved`、`validity_window_not_cover`、`contract_status_inactive`、`key_event_missing`、`customer_scope_conflict`、`event_time_reversed`、`ambiguous_active_contracts`；正式冻结前须再次核对实现、评分器、单测和协议，任何不一致都阻断运行。仅列入白名单的真实阻断条件可以免除后续来源查询，不能用“最小证据”任意跳过必要检索。

## 5. 独立复核必须交付什么

Gold 复核人不得运行作者的 Gold 生成函数作为主要依据。应从题目、原始 CSV、合同原文和 schema 独立重建每题，并给出逐项复核记录，至少检查：

- 题目与 Gold 一一对应、编号唯一；所有引用的表/行/字段/文档均存在；主外键关系和行数正确；
- 每题设备—合同候选、客户范围、映射依据、合同状态、映射/合同两类有效期、事件时间与时长均独立复算；
- 每个合同片段逐字存在于指定文档；每个 SQL 证据来自正确表和正确主键；
- 零行判据用原始数据按过滤条件实际重算；`absence_checks` 与引用不可互相矛盾；
- 检索状态、早停原因、预期引用、必需指标和答案状态互相一致，早停不要求未执行的后续检索；
- 运行包没有答案/Gold/组别泄漏，哈希清单与实际目录完全匹配；
- 整批 Gold 能被当前正式评分器的 schema gate 接受，不能通过过滤困难行取得“部分通过”。

报告必须给出 PASS/FAIL、阻断项、非阻断观察、复核范围、未查看的材料和哈希。任一关键事实无法唯一复算、引用不匹配、数据与 Gold 矛盾、泄漏或哈希错误，均不得进入正式运行；修订后须形成新版本并由复核人重审。

## 6. 运行前冻结与运行后评审

在首次答案生成之前，冻结并在工作区外登记：本要求对应的实验协议、运行包、Gold、比较器及盲评评分器代码/测试、依赖、模型可识别信息与参数、只读数据库和文档索引快照、时间锚点、运行预算、随机调度计划及所有 SHA-256。两臂必须共享问题、数据、文档、模型条件和可用工具；唯一预注册差别按 v0.8 固定为是否启用事实核验约束。温度、调用超时/重试、数据库只读限制、文档检索上限等均提前写明。

运行器不得读取 Gold。两臂全部回答完成后，先核对题目×流程臂槽位完整、原始回答数与哈希，再封存并从工作区外锚定封存清单；封存失败、运行错误、超时、空答均保留并按协议计分，不删题、不只重跑单臂。封存之后才允许保管人向评分环节开放 Gold。

主指标严格遵循 v0.8：人工最终正确性为“正确”且人工最终证据为“充分”才算通过；两臂使用同一盲评标签、判分规则和裁决程序。自动状态、引用和 Trace（工具调用轨迹）分数只作诊断；旧流程没有结构化状态不能被自动比较器直接判为语义错误。带时区 ISO-8601 时间戳只在双方均显式含时区时按绝对时刻比较；无时区时间不得推断时区。不得对自动诊断分数做确认性显著性推断。

## 7. 交给运行者的交付清单

作者与独立复核人通过后，交付以下材料；Gold 和密钥按权限单独交保管人：

| 交付物 | 是否给运行者 | 说明 |
|---|---:|---|
| 冻结运行包及 `runtime_manifest` | 是 | 题目、数据、文档和逐文件 SHA-256；不得含答案 |
| 运行前预注册协议 | 是 | 题数、题型覆盖、唯一主指标、统计/失败处理和运行配置 |
| 独立复核报告 | 是 | 结论、阻断项清零证明及复核范围 |
| Gold 文件与 Gold 哈希 | 否 | 只交给 Gold 保管人；运行封存前不得开放 |
| A/B 配对密钥与映射 | 否 | 独立保管；盲审完成前不向评审人或运行者开放 |
| 作者独立性声明、数据来源说明 | 是 | 明确合成/真实数据、作者角色和是否接触旧材料 |
| 工作区外冻结登记与封存锚点 | 按职责 | 运行前登记摘要；运行后追加封存摘要，不放入运行包 |

运行者收到运行包和复核报告后，应先做哈希、装载、只读权限及评分器预检；预检失败就停止，不得边跑边修包。

## 8. 可直接采用的完成判定

只有以下条件全部满足，才将包标为“可进入正式配对运行”：

- [ ] 作者独立性与数据来源已披露；题目不是旧题换号或基于旧输出修订。
- [ ] 题数、覆盖矩阵、状态/时区/有效期/早停口径已在运行前协议中固定。
- [ ] 运行包不含 Gold、答案、组别或密钥；Gold 与运行包已物理分离。
- [ ] Gold 全题独立复算通过；引用、负证据、检索状态和早停原因均可证伪。
- [ ] 当前运行器、比较器和盲评评分器的单测/schema gate 全批通过；没有排除题后声称整批通过。
- [ ] 运行包、Gold、协议、代码/测试、数据库/索引和调度已哈希并在工作区外登记。
- [ ] Gold 保管人确认运行者未获得 Gold；真人评审与裁决安排已确认，或报告明确预先限定为探索性 AI 评审。

任一项未完成，状态只能是“候选/待修复”，不能开始正式运行。
