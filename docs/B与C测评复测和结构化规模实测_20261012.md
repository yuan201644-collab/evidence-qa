## 结构化规模测试

### 数据与方法

- 数据源：C 组规模数据生成器对应提交 `1de728c209ced00a263538189a6b16ce98c7a4b5`；确定性生成的销售数据位于 `chinook` 数据库的独立 `scale` schema，三张表分别为 1,000、10,000、100,000 行。三个表的内容 MD5 与数据清单一致。
- 每档 10 道固定问题，覆盖行数统计、分组计数、金额聚合、日期筛选、月度聚合、Top-N、均值/极值等；同一问题逻辑应用于三个规模。
- 每轮 30 次请求，共三轮 90 次。轮次之间重启了测试专用 API 服务；数据库和操作系统缓存没有清空。正式轮次使用当前工作区服务及 DeepSeek-V4.1-Flash 配置。
- 采集器只读取问题包并保存原始响应；冻结后才由评分器读取参考 SQL。评分器核对运行时 trace 中实际成功执行的 SQL，并在只读事务中与参考 SQL 对比；评分数据库三档内容指纹每轮均复核通过。
- 另行测量三档 `sale_date` 索引的删除后重建时间。此项不含建表、灌数，不代表冷操作系统或冷 PostgreSQL 缓存耗时。

### 三轮结果

端到端耗时以毫秒记录；每轮每档 10 个问题，先在轮内计算 P50 / P95 / 最大值，再对三轮对应统计量取中位数并报告范围。P95 样本量较小，只作描述。

| 数据规模 | SQL 执行 | 严格结果匹配 | 语义结果匹配 | 端到端 P50 中位数（范围） | 端到端 P95 中位数（范围） | 最大值中位数（范围） | 索引重建中位数（范围） |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1 千行 | 30/30 | 27/30 | 30/30 | 2.76 s（2.55–2.98） | 4.08 s（3.36–5.23） | 4.62 s（3.41–6.62） | 11.68 ms（9.77–12.82） |
| 1 万行 | 29/30 | 27/30 | 29/30 | 2.61 s（2.54–2.71） | 3.22 s（3.05–3.49） | 3.25 s（3.14–3.83） | 13.15 ms（11.83–19.76） |

合计：HTTP 200 为 90/90；成功执行 SQL 为 88/90；严格匹配为 82/90；仅对按月问题的月份键统一日期与文本格式后，语义匹配为 88/90。未观察到 HTTP/传输错误。

### 差异解释与限制

1. **两次 SQL 未能成功执行**：S10K-Q04、S100K-Q03 的模型生成 SQL 省略了 `scale.` schema 前缀，重试后仍未得到可执行查询；PostgreSQL 默认搜索路径找不到这些表。接口虽为 HTTP 200，trace 中保留了工具执行错误。前端错误呈现修复已覆盖这种响应形态。
2. **六次严格差异**：三轮各有三道 Q08 月度聚合，系统返回 `YYYY-MM` 文本，参考查询返回该月首日日期值。月份与金额一致，所以严格口径不匹配、语义口径匹配；未把严格分数改写成语义分数。
3. 端到端耗时包含 API、NL2SQL 处理、数据库执行和模型服务等待，不是数据库单独耗时。三档耗时没有呈现“行数越多越慢”的单调关系，因此不能用这组数据声称数据库扩容性能趋势；模型与网络耗时可能占主导。
4. 轮次之间重启的是 API 服务，不是数据库；缓存状态不等同。首轮开始前做过接口烟测，轮次执行次序按固定题包排列，无法排除服务预热、网络波动和顺序效应。
5. 首次执行 `verify_infra.py` 时，基表数与字段数检查把 `public` 中的 RAG 支持表 `chunk_vectors`、`doc_meta` 也计入 Chinook，得到 19 项通过、2 项失败。已修正检查脚本：现在只核对 Chinook 固定 11 张表及其 64 个字段，并将外键统计限制在该表集合；同时连接信息改为脱敏输出。复跑后 **21/21 通过**。规模表在独立 `scale` schema，不是首次差异的来源。
