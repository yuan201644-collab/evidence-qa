## 三、版式调整的实测收益

同一份正文，只改排版、不动一个字：

| 版本 | 页数 | 改动 |
|---|---|---|
| 改动前 | 24 | H1 章标题各自另起一页，插图宽 6.9 in |
| 取消章分页，H1 段前距 24 pt | 22 | — |
| **取消章分页，H1 用样式默认段前距 15 pt（已采纳）** | **21** | 见下 |
| 已采纳版式 + 五张截图整幅插入（6.9 in） | 24 | 截图吃 3 页 |
| 已采纳版式 + 五张截图改小图（宽 3.3 in） | **22** | 截图只吃 1 页 |
| **再收紧：行距 1.25 → 1.15，表内字号 10.5 → 9.5 pt（已采纳，两份报告同时生效）** | **设计报告 20 / 说明书 26** | 见下 |
| **已收紧版式 + 五张截图按 3×2 联系表插入（宽 6.9 in）** | **设计报告 20** | 截图未再增页 |

**行距不是有效杠杆，字号才是。** 行距从 1.25 一路压到单倍 1.00、段后压到 2 pt，总共只省 1 页，此后完全饱和——
因为正文文字只占约四分之一版面，页数由**表格与插图的总面积**主导。真正有效的是把表格单元格字号从 10.5 pt 收到 9.5 pt
（说明书 29 → 26 页，一份文档省 3 页），行距 1.15 只是随之附带。

已采纳的两处版式改动**写在生成脚本里，不是一次性实验**：
`设计报告/生成设计报告.py` 与 `技术实现说明书/生成技术实现说明书.py` 的第 167 行 `pf.line_spacing = 1.15`
与第 259 行表内 `run.font.size = Pt(9.5)`，两份保持同一版式。

**排版方式的可替代方案对比（同为空缺前提下的实测）**：

| 截图排布 | 宽 | 页数（设计报告，未收紧版式） |
|---|---|---|
| 五张独立成段 | 5.5 in | 24 |
| 五张独立成段 | 4.5 in | 23 |
| 每两张一组 | 3.3 in | 22 |
| **合成 3×2 联系表（已采纳）** | **6.9 in** | **21**（收紧后 20，不再增页） |
| 合成 2×3 联系表 | 4.6 in | 22 |

联系表优于独立插图的原因：单张图能占满版心宽度，合并后只剩一处的段前段后与图注开销。
**代价必须写明**：联系表每格仅约 2.2 in 宽，界面截图的文字细节基本不可读，其作用是「证明有这些界面」而不是「让人看清界面」。
| 上一行再把全部插图收窄到 5.6 in | 22 | **无收益**，收窄腾出的空间被后文吸收 |

截图代价是实测值（占位图按界面截图常见 16:9，1600×900）：**整幅插入比小图多吃 2 页**。

**渲染校正**：小图方案原本设想「每行两张并排」，插入后用 pdfium 光栅化查看第 16 页，
实际渲染为**纵向堆叠**（两张 3.3 in 宽的图上下排列、共用一条图注），并未并排。
页数收益（比整幅少 2 页）是实测的，与是否并排无关；附带代价是界面截图在 3.3 in 宽下细节可读性下降。

注意最后一行：截图落地后，把插图从 6.9 in 收窄到 5.6 in 不再省页（在无截图的版本上它曾省 1 页），故该手段不能替代删减。

段前距换算曲线（章节视觉分隔是靠段前距承担的，此处逐值实测）：

| H1 段前距 | 页数 |
|---|---|
| 15 pt（样式默认，已采纳） | **21** |
| 18 pt | 22 |
| 21 pt | 22 |
| 24 pt | 22 |

即 **15 pt 与 18 pt 之间有一页的台阶**：为章节多留 3 pt 间距，代价是一页。

**已采纳的改动**落在 `docs/初赛报告初稿_20261012_v0.1/生成报告初稿.py` 的 `markdown()`：
删除对 H1 设置 `paragraph_format.page_break_before` 的两行，也不覆盖段前距，其余段落格式保持原样。
该函数同时服务两份文档，故 `技术实现说明书` 一并受益。

## 七、核算方法与自校验

分页器无法用 Word COM（本机 Word 16.0 可启动实例，但 `Documents.Open` 对任何 docx 均返回 `HRESULT 0x800A13E9`，包括既有的 `设计报告_v0.1.docx`），故改用 LibreOffice 渲染后从 PDF 字节流读取 `/Type /Page` 计数。

**自校验**：对同一个 2026-10-12 版 docx，LibreOffice 渲染结果为 **18 页**，`生成清单.json` 记录的 Word 实测也是 **18 页**——两套分页器对该文档结果一致，故本次新数字可信。

复现步骤：

```
# 1) 生成核对稿（不覆盖既有 docx，不重绘 figures，缺失图用占位图兜底）
python agent_temp/pb/build_both.py              # 两份定稿版式核对稿 -> agent_temp/report_qa/
python agent_temp/pb/build_cumulative.py        # 逐章累加稿（仅旧版式下有效）
python agent_temp/pb/build_gap_sweep.py         # H1 段前距换算曲线

# 2) 渲染（LibreOffice Kit；输出路径不可复用，已存在的 PDF 会报 EEXIST）
node <kit>/cli.js convert --input <docx> --output <pdf>

# 3) 计页
python agent_temp/pb/pdf_pages.py <pdf> ...
```

相关文件：核对稿与各变体在 `agent_temp/report_qa/`；脚本在 `agent_temp/pb/`。
