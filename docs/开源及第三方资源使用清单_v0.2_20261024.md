### 0.2 版本口径

本清单**不采用依赖声明中的版本范围**，一律取 2026-10-22 实际运行环境中观测到的版本，延续技术实现说明书 §8.1 的口径（"最终安装版本应从锁文件和运行环境采集，不能把范围依赖当作已安装版本"）。版本来源有三处：

1. **后端运行时**：`项目主体/.venv`（Python 3.11.16），由 `uv sync` 依 `pyproject.toml` + `uv.lock` 安装，逐个包用 `importlib.metadata` 读出实际版本与许可证字段（附录 A 即该次读取的完整结果）。
2. **前端**：`项目主体/web/package.json` 的锁定版本 + `package-lock.json`。
3. **平台与基础设施**：校园服务器上 `release-openspg-*` 四个容器的实测镜像与二进制版本。

### 0.3 标注约定

- **已核**：许可证来自包元数据、许可证原文文件或模型卡原文，逐条读取。
- **待核**：本机网络不可达上游（HuggingFace 连接超时），尚未取得许可证原文，已在 §9 列为待办，不在此处推定。

## 7 重点合规风险与处置

### 7.1 PyMuPDF 的 AGPL-3.0（**已处置：2026-10-24 采用方案 A**）

**事实**：`pymupdf==1.28.2` 采用"AGPL-3.0 或 Artifex 商业许可"双许可。本项目以库形式导入使用，用于 PDF 文本层与版式提取、表格块识别（`app/rag/ingest/loader.py`）。

**为什么这是真问题**：AGPL-3.0 第 13 条把"通过网络交互使用"也纳入源码提供义务。本作品恰好是一个 Web 问答服务——不处置就直接公开，等于把一个 AGPL 组件放进了对外提供服务的链路里。而赛题评审说明第 4 条把"许可证重大违规"列为一票否决项。

**处置决定**：**本作品整体以 `AGPL-3.0-or-later` 发布。**

| 项 | 落地情况 |
|---|---|
| 许可证文本 | 根目录 `LICENSE`，34,523 B / 661 行，取自 FSF 官方原文 `https://www.gnu.org/licenses/agpl-3.0.txt`，未改动 |
| 构建元数据 | `pyproject.toml` 增加 `license = { text = "AGPL-3.0-or-later" }`，并在邻近注释写明选择该许可的原因与 `contrib/` 的例外 |
| 第 13 条义务（网络交互） | 作品对外提供服务时，对应源码即为已公开的完整仓库（含前端源码、构建产物说明、部署脚本），用户可自行获取；不需要额外"源码请求"通道 |
| 子目录例外 | `contrib/` 保持 **Apache-2.0**（`contrib/LICENSE` + `contrib/NOTICE`），以便向 Apache-2.0 的上游 KAG 提交补丁；Apache-2.0 → AGPL-3.0 为单向兼容，不冲突 |
| 上游兼容性 | 混合链路为「PyMuPDF（AGPL-3.0）→ 本项目（AGPL-3.0）」，同许可，无跨许可冲突 |

**为什么选 A 而不是 B/C**：距提交截止 6 天。方案 B（换 `pypdf` / `pdfplumber`）需要重做版式块提取、表格重建与像素→点坐标映射，并对全量语料回归，工程量 2–3 天且风险不可控；方案 C（Artifex 商业许可）在评审期内不一定拿得到凭证。方案 A 只需改许可与报告口径，且"把 AGPL 义务显式履行到位"本身就是「AI 与开源融合」这一项要求看的证据（该评分点要求"完整说明资源来源、版本、许可证/授权类型、自研边界、关键许可义务和融合方式"）。

**备选路径仍然保留**：若后续需要闭源商用，可按方案 B 替换解析库，届时把主仓库许可改回宽松许可并保留 `contrib/` 的 Apache-2.0。此路径已评估，未采用。

**已在报告中引述**：技术报告第七章"许可合规"一节直接引用本小节，说明"为何选择同许可而非换库"。

### 7.2 MinIO 的 AGPL-3.0

MinIO 是 OpenSPG 官方 compose 里的对象存储。本项目**未修改其代码、未对外提供 MinIO 服务**，只在服务器内部由 OpenSPG Server 调用其 S3 接口存放上传语料。AGPL 的义务触发点是"修改后分发"或"作为网络服务向第三方提供该程序的功能"，本场景两者都不成立。

**结论**：合规。已在表 5-4 记录，报告中一句话带过即可，不必展开。

### 7.3 Neo4j（GPLv3）与 MariaDB（GPLv2）：为什么不算衍生

两者都是 GPL 系强 copyleft，容易被误判。判定依据是**使用方式**而非"是否用到"：

- 本项目通过 **Bolt 协议 / SQL 协议** 与它们通信，二者是独立进程；
- 未链接其库、未修改其源码、未分发其二进制；
- 因此属于 GPL 公认的"独立程序经通用协议交互"，不产生衍生作品。

**结论**：合规。写进报告时用"独立服务、网络协议调用、未修改未衍生"三句话说明即可，不要含糊成"用了 GPL 软件"。

### 7.4 psycopg 的 LGPL-3.0

以**未修改的二进制形式动态链接**使用，符合 LGPL 的典型许可场景，不要求本作品开源。仅在"修改 psycopg 自身"时才需开放其修改。本项目未修改。

### 7.5 第三方 API 服务的凭据与内容边界

- `.env` 内含真实 `LLM_API_KEY` / `DEEPSEEK_API_KEY`，已列入 `.gitignore`，**从未进入 git 历史**（建仓后逐次核验）；
- 提交材料（报告、视频、PPT、仓库）**不得出现任何密钥**。`.env.example` 只保留键名与占位值；
- 调用第三方模型产生的内容，其权利归属按各服务商条款确定，不得当然认定为团队自主知识产权（对应规则三（七））。技术报告需说明这一边界。
