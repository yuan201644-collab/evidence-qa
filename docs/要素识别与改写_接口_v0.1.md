## 二、它放在哪、为什么不放在编排层

### 2.1 归属已由既有文档确定

`docs/功能清单与技术框架_v1.md` §3.4 的目录结构里写着：

```
│   ├── orchestrator.py     # 编排层
│   ├── nl2sql/             # 结构化链路
│   │   ├── normalizer.py   #   要素识别与改写     ← 中级任务 1
```

`orchestrator.py` 与 `nl2sql/` 是**并列的两个位置**。所以本模块的归属是 `app/nl2sql/normalizer.py`，不放在编排层。**此结论经负责人 2026-09-22 确认，维持文档已定目录。**

### 2.2 为什么不放在编排层

编排层要做的是"调度"，本模块要做的是"理解"，两者不是一个层次的东西：

| | 编排层 `route()` | 要素识别与改写 |
|---|---|---|
| 回答的问题 | **该调哪个工具** | **用户到底在说什么** |
| 输出 | `RoutePlan{steps, reason, confidence}` | 标准问句 + 识别到的要素 |
| 改动的代价 | 动一下影响**整条链路** | 加一条别名即可，影响面极小 |
| 迭代频率 | 低（结构性问题才动） | 高（发现一个没覆盖的词就加一条） |

四条具体理由：

1. **职责不同**。把"理解"塞进"调度"，编排层会变成一个什么都干的胖子，违反项目硬规范里的"函数保持单一职责"（`AGENTS.md` §六.7）。
2. **节奏相反**。别名表是高频小幅增量，路由规则是低频高风险改动。混在一起的结果就是"改个别名要动编排层，每次都得跑全量回归"。
3. **顺序上是前置环节**。链路是「改写 → 路由 → 调工具」。若实现长在编排层，`route()` 会变成"先做一遍自然语言处理，再判断调谁"。
4. **评分口径**。题面要求"构建高可用性的**要素泛化模型**"。若落地成编排层里几行 `if-else`，评审看到的不是"模型"，中级任务 5 分与鲁棒性档位分都拿不满。

### 2.3 与 `routing_signals.py` 的分工 —— 最容易混淆的一处

`app/routing_signals.py`（B 于 2026-09-21 新增）**已经在做一种实体识别**：它从两边的元数据派生词表（文档侧读 `data/corpus/manifest.json`，结构化侧读 `infra/schema_meta*.json`），然后对用户问题做**子串匹配**，产出分数供路由使用。

本模块一旦做起来，系统里就有**两套实体识别**了。必须划清：

| | `routing_signals` | `normalizer`（本模块） |
|---|---|---|
| 目的 | 判断**走哪条链路** | 判断**用户说的到底是哪个东西** |
| 手段 | 子串匹配已知词表 | 别名 + 纠错 + 泛化 |
| 输出 | 分数 → `RoutePlan` | 标准问句 + 要素列表 |
| 维护的词表 | 从元数据**自动派生** | 人工维护的**别名表** |

**依赖顺序只有一个方向：本模块在前。**

因为 `routing_signals` 用的是子串匹配——用户说"帝都"，若本模块没先把它改写成"北京"，路由那边根本识别不出实体词。**顺序错了，后面全错。**

**约定**：`routing_signals` 只在**标准问句**上运行；别名表由本模块独占维护，不往 `routing_signals` 里加别名。

```
用户提问「这个平台上总共有多少个买家？」
        │
        ▼
┌──────────────────────────────┐
│  normalizer（本模块）         │  ← 编排层在路由【之前】调用

┌──────────────────────────────┐

               │
```

## 四、数据结构

以下类型定义在 `app/nl2sql/normalizer.py` 内，**不进 `app/contracts.py`**——`contracts.py` 是三人共用的契约（`Ref` / `TraceStep` / `ToolResult` / `AskRequest` / `AskResponse`），本模块的内部结构只有结构化链路与编排层用得到，加进契约会无谓地扩大契约面并触发三人同步流程。

### 4.1 退化类型 `ChangeKind`

```python
class ChangeKind(str, Enum):
    """改动类型。取值刻意与 eval/cases/robust_cases.jsonl 的 degradation 字段对齐，
    便于按退化类型分别对账。"""
    ALIAS = "alias"            # 业务别名：买家 → customer
    TYPO = "typo"              # 错别字：艺术佳 → 艺术家
    FULLWIDTH = "fullwidth"    # 全角/半角：２０２１ → 2021
    MIXED_LANG = "mixed_lang"  # 中英混排
    FILLER = "filler"          # 口语冗余：麻烦帮我查一下哈，就是那个……
    TIME = "time"              # 时间词标准化：去年 → 2025 年
```

**为什么没有 `ambiguous`**：`robust_cases.jsonl` 里有两条 `degradation="ambiguous"` 的用例（`rob-10`「增长率是多少？」、`rob-11`「帮我看下最多的那个。」），考的是**主动澄清**，属中级任务 3，不是本模块的职责。

本模块遇到无法消解的输入时，**必须什么都不改**，并把退化点如实记进 `NormalizeResult.unresolved`，交由澄清环节决定。理由：`rob-11` 的用例说明里明确写着"**任何直接生成 SQL 的行为都算失败**"——本模块若自行脑补改写，等于把这条用例判死。

### 4.2 一处改动 `TextChange`

```python
class TextChange(BaseModel):
    """一处改写的完整记录 —— 可解释性的最小单元。"""
    model_config = ConfigDict(extra="forbid")

    kind: ChangeKind
    before: str              # 原文片段："买家"
    after: str               # 改写后："customer"
    span: tuple[int, int]    # 在原文中的字符位置，供前端高亮
    reason: str              # 一句人话："别名表 customer 条目命中"
    source: str              # 依据标识："alias:customer" / "rule:fullwidth" / "lexicon:time"
```

**`source` 字段是溯源的关键。** 评审问"你凭什么把买家理解成客户"，答的是"别名表的 customer 条目"——这是可验证的既定事实，不是模型的自我叙述。这正好满足项目原则 2「可解释性用代码埋点，禁止用 LLM 思维链充当」。

### 4.3 识别到的要素 `NormalizedEntity`

```python
class NormalizedEntity(BaseModel):
    model_config = ConfigDict(extra="forbid")

    surface: str    # 用户原话："买家"
    canonical: str  # 标准名："customer"
    kind: str       # "table" / "column" / "value" / "doc"
    via: str        # "alias"（查别名表命中）/ "exact"（原样命中）/ "desc"（中文说明命中）
                    # / "semantic"（语义兜底命中 —— 见第十二节，只在前面三种都没命中时才可能出现）
```

`via` 用来区分"是真的做了泛化"还是"本来就叫这个"。**对账时必须按 `via` 分组，不得合并报数**：
`exact` 是原样命中（不算泛化）、`desc` 是元数据说明命中、`alias` 是查表命中、`semantic` 是语义兜底命中
—— 四者可靠性依次递减，`semantic` 最低，必须单独抽样人工核对（见 §12.5）。

### 4.4 时间表达式 `TimeExpression`

```python
class TimeExpression(BaseModel):
    model_config = ConfigDict(extra="forbid")

    surface: str    # 用户原话："去年"
    kind: str       # "day" / "month" / "quarter" / "year" / "range"
    offset: int     # 相对基准的偏移：-1 = 去年，0 = 今年
    start: str      # 归一化区间起点（ISO 日期，如 "2025-01-01"）
    end: str        # 归一化区间终点，**左闭右开**
    anchor: str     # 计算时用的时间基准，随结果一起留存
```

详见第六节。

### 4.5 主输出 `NormalizeResult`

```python
class NormalizeResult(BaseModel):
    model_config = ConfigDict(extra="forbid")

    original: str                          # 原句，原样留存（不改写它，方便对账与展示）
    normalized: str                        # 标准问句 —— 交给路由与下游工具
    changes: list[TextChange] = []         # 改了哪些地方
    entities: list[NormalizedEntity] = []  # 识别到哪些要素
    times: list[TimeExpression] = []       # 识别到哪些时间表达式
    unresolved: list[str] = []             # 没能消解的退化点（交给澄清环节）
    degraded_kinds: list[ChangeKind] = []  # 本句涉及哪些退化类型（对账 degradation 用）
    elapsed_ms: float = 0.0
```

## 六、时间词标准化

题面第 34 行 F10 点名要求"**别名、错别字、时间词标准化**"三样。前两样现有用例已覆盖，时间词这一样目前**一条用例都没有**，需要补。

### 6.1 为什么必须显式传"时间基准"

"去年""上个月"这类词是**相对**的，必须有一个基准时间才能换算成具体区间。如果每次跑分都取系统当前时间，那今天跑和明天跑结果就可能不同，评测**不可复现**——这与项目"跑分结果必须含 `git_commit`"的可复现要求相冲突。

**约定**：

- `normalize()` 的 `time_anchor` 参数**不传时**取当前时间（生产环境行为）；
- **跑分时必须显式传入固定值**，并把该值写进跑分 JSON（与 `git_commit` 并列）；
- 建议由 `eval/runner.py` 统一从一个环境变量取（如 `APP_TIME_ANCHOR`），避免各处各写一个。

`TimeExpression.anchor` 字段把这个基准**随结果一起留存**下来，所以任何一条历史结果都能追溯到它当时用的是哪个基准。

### 6.2 数据范围约束（实测，2026-09-22）

设计用例前必须知道这件事，否则会写出**答案恒为 0** 的无效用例。

从 `infra/initdb/02_chinook.sql` 第 4464 行起实测统计 `invoice.invoice_date`：

| 项 | 值 |
|---|---|
| 最早 | 2021-01-01 |
| 最晚 | 2025-12-22 |
| 总条数 | 412 |
| 年份分布 | 2021 年 83 条、2022 年 83 条、2023 年 83 条、2024 年 83 条、2025 年 80 条 |

**推论**：若基准取 2026-09-22，则"**今年**"= 2026 年 → **0 条**；"去年" = 2025 年 → 80 条。

→ ✅ **已定（2026-09-22，负责人拍板）：评测固定基准 = `2024-06-15`。** 理由：该日落在数据区间内，"去年 / 上个月 / 上季度"都能查到非空结果，用例才有区分度。此值须随跑分结果一起落盘（见第十一节第 4 条）。

### 6.2.1 基准 `2024-06-15` 下各时间区间真值（实测）

| 说法 | 归一化区间（左闭右开） | 条数 | 备注 |
|---|---|---|---|
| 去年 | `[2023-01-01, 2024-01-01)` | 83 | 无歧义 |
| 前年 | `[2022-01-01, 2023-01-01)` | 83 | 无歧义 |
| 上个月 | `[2024-05-01, 2024-06-01)` | 7 | 无歧义 |
| 上季度 | `[2024-01-01, 2024-04-01)` | 21 | 无歧义 |
| 今年 | `[2024-01-01, 2025-01-01)` | 83 | 取整期（§6.2.2 已定） |
| 本月 | `[2024-06-01, 2024-07-01)` | 7 | 取整期（§6.2.2 已定） |
| 本季度 | `[2024-04-01, 2024-07-01)` | 21 | 取整期（§6.2.2 已定） |

> 「至今」读法下的对照值（**未采用**，仅备查）：今年 37 / 本月 2 / 本季度 16。取舍理由见 §6.2.2。

### 6.2.2 ✅ 已定：含"今"的区间取「整期（日历对齐）」

**2026-09-22 负责人拍板：采用「整期」。** 即「本月」「本季度」「今年」一律指**基准日所属的那一个完整自然期**，与基准日落在期内的哪一天无关：

```
本月   → [2024-06-01, 2024-07-01)   → 7 条
本季度 → [2024-04-01, 2024-07-01)   → 21 条
今年   → [2024-01-01, 2025-01-01)   → 83 条
```

**为什么这当初是个必须拍板的岔口**：基准日 `2024-06-15` 落在月中，两种读法差得很大——

| 说法 | 整期（**已采用**） | 至今（未采用，仅列出备查） |
|---|---|---|
| 本月 | **7** | 2 |
| 本季度 | **21** | 16 |
| 今年 | **83** | 37 |

选整期的三条理由：① 不必额外定义"基准日当天的数据算不算"；② 与现有 6 条时间类 `gold_sql` 的左闭右开**整期**写法同构；③ 判定规则少，实现与判分都不容易产生分歧。

⚠️ 一个必须知道的现象：**本数据在 2024-06 有 5 张发票日期在 6-15 之后**（6-25 两张、6-26、6-27、6-30）。按整期算，「本月」包含这 5 张。这是"基准是虚构的、数据是真实的"带来的正常现象，**不是数据错误**，但演示时要能解释。

### 6.3 左闭右开约定

归一化产出的区间一律**左闭右开**（`[start, end)`），与现有 `gold_sql` 的写法保持一致：

```sql
WHERE invoice_date >= DATE '2021-01-01' AND invoice_date < DATE '2022-01-01'
```

这样归一化的输出可以**直接落到 SQL 的 WHERE 条件**上，不需要下游再做一次边界换算。

## 七、值级别名

### 7.1 为什么需要这一层

表名、列名之外，**字段的取值**同样有不标准表达。实测现有取值（`infra/schema_meta.json`）：

| 字段 | 库里实际存的值 | 用户可能怎么说 |
|---|---|---|
| `customer.country` | `USA` / `Brazil` / `Germany` / `Czech Republic` … | 「美国」「美利坚」「捷克」 |
| `employee.title` | `General Manager` / `Sales Support Agent` / `IT Staff` … | 「总经理」「客服」「销售支持」 |
| `genre.name` | `Heavy Metal` / `Electronica/Dance` / `R&B/Soul` … | 「重金属」「电子舞曲」 |

不做这一层，"美国客户的销售额是多少"这类问法就认得出来才怪。

### 7.2 结构

```python
class AliasTable(BaseModel):
    model_config = ConfigDict(extra="forbid")

    version: str
    updated_at: str
    tables: dict[str, list[str]]              # "customer" -> ["买家", "顾客", "消费方"]
    table_mentions: dict[str, list[str]]      # 只记录实体、不改写原词，如 invoice -> ["订单数"]
    columns: dict[str, list[str]]             # "customer.city" -> ["所在城市"]
    values: dict[str, dict[str, list[str]]]   # "customer.country" -> {"USA": ["美国", "美利坚"]}
    docs: dict[str, list[str]]                # "KB-001" -> ["维保合同", "设备维保合同"]
```

`tables` 中的俗称会改写为规范表名；`table_mentions` 只建立表实体映射并保留原文，适合同时承载指标含义的说法（例如 `订单数`）。两者不能混用：把“订单数”直接改写成 `invoice` 会丢失应使用 `COUNT` 而非金额求和的指标语义。

`docs` 一节服务**文档侧**（RAG 链路）。本模块在编排层入口统一调用，要同时服务两条链路，所以文档别名也归它管。

### 7.3 取值从哪来

`values` 的**键**（`USA` / `Sales Support Agent` 这些）应由 C 从库里抽出真实取值来定，不要手写猜测——写错一个字母，映射就永远命中不了。

## 八、与编排层的衔接

### 8.1 调用位置（已核到行）

`app/orchestrator.py` 第 218 行的 `answer()` 内，插在**第 220 行 `plan = route(...)` 之前**：

```python
def answer(self, question: str, session_id: str = "default") -> AskResponse:
    norm = normalize(question)                 # ① 先改写
    question = norm.normalized                 # ② 标准问句往下走
    plan = route(question, self.registry)      # ③ 路由看到的是标准句
```

### 8.2 三个必须遵守的点

1. **`_execute(question, plan)` 要用改写后的问句**，不能还用原句。
2. **改写记录作为一步 `TraceStep` 进入总链**：`tool="normalizer"`、`input` 放原句、`output` 放 `NormalizeResult`、**`hit=None`**。
3. ⚠️ **澄清分支（第 223–230 行）目前是 `return AskResponse(trace=[], ...)`**。若已经改写过，这个分支**也必须带上 normalizer 那一步**，否则出现"改了但没留痕"，可解释性断链。

### 8.3 为什么 `hit=None`、为什么不用改契约

已核实 `app/contracts.py` 的实际结构：

| 事实 | 出处 | 影响 |
|---|---|---|
| `TraceStep.hit` 的类型是 `list[RefT] \| None`，`RefT` 只能是 `SqlRef` 或 `DocRef` | `contracts.py:153`、`contracts.py:175` | 改写记录**塞不进 `hit`** |
| `TraceStep.output` 的类型是 `dict[str, Any]` | `contracts.py:173` | ✅ 改写记录放这里 |
| `merge_trace()` 只重排 `step_id`，其余字段原样保留 | `contracts.py:238-241` | `tool="normalizer"` 会被保留 |
| `collect_refs()` 只遍历 `step.hit` | `contracts.py:256-257` | `hit=None` 时**完全不影响 refs 不变量** |

**结论：不动 `app/contracts.py`，不加字段，不升契约版本。**

顺带说明一个设计取舍：别名表算不算一种"引用"（`Ref`）？**不算。** `refs` 的语义是"**答案从哪来**"，而别名表是"**理解依据**"。把理解依据混进 `refs`，会让"答案来源"这个语义变浑。所以它留在 `output` 里，前端从 `trace` 里读即可展示"你问的是 X，我理解为 Y"。

## 九、判分口径

### 9.1 一个不能用的口径

`robust_cases.jsonl` 每条都带 `canonical_question`（标准问句）字段，看起来很像是现成的期望输出：

```
question   : 这个平台上总共有多少个买家？
canonical  : 客户总数是多少？
```

**但它不能用来做字符串比对。** 因为它是**人工重写的语义等价问句**，不是"消解退化点之后应该得到的字符串"——机械地把「买家」换成「客户」，得到的是「这个平台上总共有多少个客户？」，与 `canonical_question` **不相等**。

### 9.2 实际采用的三层口径

| 层次 | 判据 | 期望值来自 | 能自动判 |
|---|---|---|---|
| ① 要素级 | `entities` 里的标准名 == 用例的 `tables` | `robust_cases.jsonl` 的 `tables` 字段 | ✅ |
| ② 类型级 | `degraded_kinds` == 用例的 `degradation` | `robust_cases.jsonl` 的 `degradation` 字段 | ✅ |
| ③ 端到端 | 走完整链路后**结果集** == `gold_sql` 的结果集 | `robust_cases.jsonl` 的 `gold_sql` | ✅ |

第 ③ 层与项目既有评测口径一致（`docs/评测口径_v0.1.md`：「**比结果集不比 SQL 文本**」），不需要新造判分规则。

### 9.3 举证时建议按退化类型分别报数

题面要求举证"**高可用性**"。一个笼统的"改写准确率 85%"说服力一般；按退化类型拆开报，直接对应用例题面上的退化清单：

```
业务别名  3/3      错别字  3/3      全角字符  1/1
中英混排  1/1      口语冗余 1/1
```

## 十、别名表的存放位置

### 10.1 不能写进 `schema_meta.json`

已核实 `infra/` 下各文件的性质：

| 文件 | 性质 | 能否往里填别名 |
|---|---|---|
| `infra/schema_meta.json` | **生成物**（`generator: export_schema_meta.py`、`generated_at: 2026-09-18T08:54:04+00:00`） | ❌ 重跑即抹掉，且**不会报错** |
| `infra/schema_meta.adventureworks.json` | 生成物 | ❌ |
| `infra/schema_meta.descriptions.zh.json` | **人工维护的输入**（`export_schema_meta.py` 第 42 行 `DEFAULT_DESC`、第 321 行 `--descriptions` 参数读的文件） | ⚠️ 技术上安全，但语义是"中文业务说明"，塞别名属混用 |

**schema 一旦变化就会重跑生成脚本**，那时手填的别名会静默消失。

### 10.2 采用独立文件

新建 **`infra/schema_meta.aliases.zh.json`**，与生成物完全分离。本模块直接读它，**不碰 C 的生成脚本**。

若将来要让它并入主文件，可照 `--descriptions` 的模式给 `export_schema_meta.py` 加一个 `--aliases` 参数——那需要 C 配合改脚本，属于后续可选升级，不在本期范围内。

## 十二、覆盖策略：三层识别 + 语义兜底（2026-09-24 追加）

### 12.1 为什么要补这一节

题面任务 1 的原文要求是「**在不限定具体实体类型的前提下**，构建高可用性的要素泛化模型」。
而本模块 v0.1 原设计只有两层识别，**两层都是"枚举"性质**：

- 元数据派生（`desc`）只覆盖「库里已命名的结构」
- 人工别名表（`alias`）只覆盖「人工收录过的俗称」

两者叠加**仍必然漏，且漏的方式是静默的**：不改写、不报错，下游按错的走。
更要紧的是题面还有**任务 2**（第 129-132 行）：「可扩展的要素提取：设计一套**不依赖 Few-Shot Prompting** 的方案，
以保证**面对新增业务领域时系统能低成本、快速扩展**」——**任务 2 其实是对任务 1 实现方式的约束**。
纯枚举方案在"不限定类型"与"扩展成本低"这两条上都不达标，所以必须补一层**能泛化的兜底**。

### 12.2 三层分工（顺序即优先级）

| 层 | 机制 | 覆盖来源 | 维护成本 | 对应 `via` |
|---|---|---|---|---|
| A | 元数据派生词表 + 子串匹配 | 库的结构本身 | 零 | `exact` / `desc` |
| B | 人工别名表（`infra/schema_meta.aliases.zh.json`） | 人工收录的业务俗称 | 高（一词一条） | `alias` |
| **C** | **语义兜底：向量召回候选 → 回库校验 → 采纳** | **语义近似，可泛化** | **零（模型算）** | **`semantic`** |

**C 层只在 A、B 都没命中时才启用。顺序不可交换**——A/B 是确定性命中，能命中就不该让模型参与。

### 12.3 C 层的四条硬约束

1. **模型只产候选，不下结论。** 它的输出是一组 `(canonical, kind, score)`，**不是**改写后的文本。
2. **候选必须回库校验**（全确定性）：候选指向的表/字段必须真的存在于 `infra/schema_meta.json`；
   若是取值，必须真的在库里。校验不过**直接丢弃**。
   → 这一条是「**用模型做理解**」与「**用模型的话当证据**」的分界线（项目原则 2）。
3. **相似度阈值**：低于阈值不采纳（阈值需实测标定，首版建议 0.62，随对账修正）。
4. **歧义不采纳**：top-1 与 top-2 的分数差小于裕度时**不采纳**。
   依据是 §4.1 的同一理由——「改错比不改更糟」。宁可留在 `unresolved` 交给澄清环节（中级任务 3）。

### 12.4 工程实现（已实测的规模结论，2026-09-24）

**候选集只有 75 条**：实测 `infra/schema_meta.descriptions.zh.json`，表级说明 11 条 + 字段级说明 64 条（Chinook）。
所以：

- **不需要建第二个向量库，也不必用 pgvector**：启动时 `embed_many()` 一次性编码成 75×1024 的矩阵常驻内存
  （约 300KB），查询时算 75 次余弦相似度即可。`AdventureWorks`（68 表）候选集到几百条，同一做法仍够用。
- ⚠️ **必须共享 RAG 侧的 `BgeEmbedder` 实例**（`app/rag/retrieval/indexer.py:36`）：
  bge-m3 单套常驻内存约 2GB，各起一份会翻倍并触发 OOM（`app/tools/doc_search.py` 已记录同类风险）。
- **依赖方向**：由编排层在装配时把 embedder **注入** `normalize()`，**`normalizer` 不 import `app.rag`** ——
  这样结构化链路对非结构化链路保持零 import 依赖（与 §8.1 的调用位置设计一致）。

### 12.5 判分与举证

第九节的三层口径不变，但**对账时须按 `via` 拆分**：`alias`/`exact`/`desc` 是确定性来源，
`semantic` 是概率性来源，**不得合并报数**。建议增报两项：

- `semantic` 的**采纳率**（候选通过回库校验并采纳的比例）
- `semantic` 采纳样本的**人工抽样准确率**

**这一层天然就是决赛质量分的对照素材**：决赛「中级任务攻克质量 10 分」的判据是
「**相对于基础方案的改进幅度与有效性**」。于是：
「基础方案 = A+B 两层」与「改进方案 = A+B+C 三层」的**覆盖率差值**，就是可量化的"改进幅度"。

### 12.6 口径纪律（若最终不实现 C 层）

若 C 层最终未实现，**对外不得声称"不限定实体类型"**（那是题面要求，做不到就不声称）。改为：

> 「覆盖已收录的业务别名与六类退化类型，并对**未覆盖项做显式留痕**（`unresolved`）。」

`unresolved` 字段本身就是"承认覆盖有限"的诚实设计，把它当亮点讲，比硬声称"不限定"更经得起追问。
