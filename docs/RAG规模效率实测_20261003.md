# RAG 非结构化文档规模效率实测（2026-10-03）

## 结论与适用范围

- 在本机 PostgreSQL 16.15 + pgvector 0.8.6、CPU 模型环境下，14 / 126 / 509 页样本的冷索引耗时三轮中位数为 **31.50 / 194.72 / 758.56 秒**（各轮范围见下表），生成 **47 / 380 / 1523** 个切片。端到端每档 3 轮、共 **90/90 次成功**；各档 p50 中位数为 **15.89 / 18.97 / 14.76 秒**。
- 同一 pgvector 索引上，把融合召回 Top-K 从 20 降到 10，三轮配对的检索 p50 降幅中位数为 **32.3% / 46.9% / 43.2%**；但最终 Top-5 证据集合在三档每轮分别有 **2 / 8 / 8 题**变化。因此**不修改生产默认 K=20**；Top-5 重合度不是答案准确率，若要改 K 必须另跑质量评测。
- 规模样本是同源扩写，实际页数不是精确的 10 / 100 / 500。它只用于效率轴，不参与命中率、忠实度等质量分。

原始逐题计时见 [`eval/reports/scale_20261003/`](../eval/reports/scale_20261003/)；以下秒数均为实测，不把 JSONL 自报延迟当作效率证据。

## 环境、语料和方法

| 项 | 口径 |
|---|---|
| 机器 / 模型 | 同一台 Windows 机器；BGE-m3（1024 维）与 bge-reranker-v2-m3 在 CPU 上运行；没有 GPU 数据 |
| 当前向量后端 | PostgreSQL 16.15 + pgvector 0.8.6；独立的 `rag_scale_*` schema，未向生产 `public.chunk_vectors` 混入规模样本 |
| 参数 | 融合召回 K=20，重排后 K=5；优化对照仅在基准进程中临时使用 K=10 |
| 查询 | 固定 10 条，三档相同；pgvector 配对测量交替执行 K20/K10，减少顺序漂移 |
| 预热 | 本地嵌入模型、重排模型在计时前预热；建索引计时不含模型首次加载 |
| 分位数 | 每轮每档 10 个逐题样本计算 p50、线性插值 p95、max；三轮结果对各轮统计量取中位数，另列范围，不把 30 个样本混合成一轮 |

规模 PDF 位于本机被忽略的 `agent_temp/scale_probe/`。哈希用于确认本次各阶段测的是同一批字节；生成器和原始规模 PDF 尚未入库，**异机复现仍需 C 提供生成器/样本**。

## 当前 pgvector 后端：冷索引与端到端

冷索引在全新的隔离 schema 中每档测三轮；端到端复用独立的持久化索引，每档执行三轮、每轮 10 次真实问答，并向当前 `LLM_API_BASE` 发送查询及检索上下文。两项测试不是同一轮计时，不应把其 p50 相减来估算 LLM 耗时。表中端到端数字是三轮每轮统计量的中位数。

| 指标 | 14 页 | 126 页 | 509 页 |
|---|---:|---:|---:|
| 冷索引总耗时中位数（范围） | 31.50 s（29.70–33.64） | 194.72 s（148.86–244.70） | 758.56 s（561.79–964.79） |
| 切片数 | 47 | 380 | 1523 |
| 端到端 p50 中位数（范围） | 15.89 s（9.57–17.93） | 18.97 s（12.67–20.28） | 14.76 s（11.67–19.14） |
| 端到端 p95 中位数（范围） | 38.39 s（34.98–39.07） | 35.65 s（26.26–38.48） | 45.08 s（41.42–50.72） |
| 端到端 max 中位数（范围） | 39.07 s（35.18–42.21） | 39.62 s（29.40–44.26） | 50.80 s（41.52–51.09） |
| 端到端成功数 | 30/30 | 30/30 | 30/30 |

数据库交叉核对：三轮冷索引各使用独立 schema，每个完整 schema 均有 **1950 条向量、3 份文档**；端到端复用的隔离索引也有 1950 条向量。生产 `public` 仍是 **75 条向量、15 份文档**。三轮 pgvector 运行中的 PDF 哈希与切片数逐项一致。

## 同索引、同查询的 Top-K 配对对照（pgvector）

此项只测本地 `retrieve_and_rank`，不调用 LLM。每档先对两个 K 各预热一次，再对 10 题交替执行 K20/K10；表中“证据变化”是最终 Top-5 **集合**不同的题数，未评价回答质量。

| 指标（三轮统计量的中位数） | 14 页 | 126 页 | 509 页 |
|---|---:|---:|---:|
| K20 检索 p50（范围） | 11.69 s（7.45–12.27） | 8.51 s（8.45–14.34） | 14.13 s（8.37–14.61） |
| K20 检索 p95 | 14.02 s | 9.14 s | 16.49 s |
| K10 检索 p50（范围） | 8.31 s（4.64–8.32） | 4.51 s（4.47–8.07） | 8.30 s（4.49–8.32） |
| K10 检索 p95 | 8.84 s | 4.72 s | 8.75 s |
| K10 相对 K20 的 p50 降幅中位数 | 32.3% | 46.9% | 43.2% |
| Top-5 平均重合数 | 4.8 / 5 | 3.3 / 5 | 3.5 / 5 |
| 每轮最终证据集合变化题数 | 2/10 | 8/10 | 8/10 |

三轮的 K20 样本中，BM25＋pgvector 融合召回的逐轮平均值中位数约 **0.08–0.12 秒**，CPU 重排约 **7.56–13.22 秒**；瓶颈是重排，而非 PostgreSQL 向量查询。小档在不同轮次的绝对时延也有明显变化，不能据此声称“规模越大越快”。

## 历史内存向量库三轮基线（仅作同机参考）

三轮顺序分别为 `10→100→500`、`100→500→10`、`500→10→100`。每档每轮 10 次端到端调用，合计 **90/90 成功**。下表是三轮各自统计量的中位数；**不是**当前 PostgreSQL 后端的成绩。

| 指标 | 14 页 | 126 页 | 509 页 |
|---|---:|---:|---:|
| 建索引中位数 | 16.48 s | 138.18 s | 529.96 s |
| 检索 p50 中位数 | 6.47 s | 8.17 s | 7.83 s |
| 检索 p95 中位数 | 7.64 s | 8.85 s | 8.97 s |
| 检索 max 中位数 | 7.73 s | 9.16 s | 9.01 s |
| 端到端 p50 中位数 | 10.32 s | 12.11 s | 12.12 s |
| 端到端 p95 中位数 | 33.68 s | 27.03 s | 35.01 s |
| 端到端 max 中位数 | 35.94 s | 28.95 s | 40.50 s |

三轮的索引耗时范围分别为 **15.73–46.88 / 132.14–282.02 / 517.77–616.05 秒**。每轮第一个被测规模都偏慢，即使已预热模型，也存在顺序/负载效应。不能把 pgvector 单轮与内存三轮的差值解释成纯粹的“数据库开销”。

## 异常、限制与后续

1. 第一次 pgvector 配对运行中，上一档的数据库读事务未释放，挡住下一档 `ALTER TABLE`；该次 **126 页索引 1103.7 秒无效**。已在基准脚本的档间释放事务，并用全新 schema 重测三轮；该次异常运行 JSON 保留供审计，不纳入三轮统计。
2. pgvector 冷索引、检索配对、端到端均已各完成 **3 轮**。端到端每轮每档 10 题，p95/max 仅有 30 个样本，长尾估计仍有限。冷索引的三轮范围较宽：14 / 126 / 509 页分别为 **29.70–33.64 / 148.86–244.70 / 561.79–964.79 秒**。只记录了基准进程的资源活动和数据库等待状态，没有记录操作系统级的完整后台负载；这些绝对值不应视为稳定服务承诺。端到端时延还受 LLM 网络波动影响。
3. Top-5 集合重合度不等于召回命中率，更不等于答案忠实度。若要将 K20→K10，必须用 `eval` 的正式质量用例做配对回归，经 A 确认后再改生产参数；本轮**没有改默认值**。
4. 三轮原始 JSON 已入库，但规模 PDF 与生成器未入库，当前只具备数据审计、尚不具备完整异机复现。C 仍需补生成器或同哈希样本；若正式说明书要求可复现实验，还应在能记录系统负载的条件下重跑并附机器信息。
