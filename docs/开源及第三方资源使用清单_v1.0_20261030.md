## 8 重点合规风险与处置

### 8.1 PyMuPDF 的 AGPL-3.0（本作品唯一的强 copyleft 处置点）

PyMuPDF 以 AGPL-3.0 / Artifex 商业许可双许可发布。我方以库链接方式在服务端使用它做 PDF 解析，**属于 AGPL 意义上的"通过网络提供服务"**。处置采用方案 A：**本作品整体以 AGPL-3.0-or-later 发布**，根目录 `LICENSE` 为 FSF 原文，对外提供服务时提供完整对应源码；`contrib/` 子目录独立以 Apache-2.0 提供，以便上游社区采纳补丁（Apache-2.0 与 AGPL-3.0 在本项目中为**并列的两个目录**，不发生混合）。

### 8.2 KAG 的 Apache-2.0 与派生标注

我方对 KAG 的改动分三类：① **不改上游文件**（R1 用子类 + 注册表覆盖）；② **提供补丁文件**（R4 的 5 行、R6 的 +21 行，均以 `.diff` 形式随仓库）；③ **只定位不修改**（R5）。`contrib/NOTICE` 已列明派生关系与改动范围；未以原作者名义背书。

### 8.3 Neo4j / MariaDB / MinIO：为什么不算衍生

三者均为**独立进程**，我方通过 `neo4j://`、MySQL 协议与 S3 协议调用，不链接其代码、不修改其二进制、不再分发其镜像。GPLv2/GPLv3 的传染性以"分发"为触发条件，AGPL 第 13 条以"修改并通过网络提供该程序"为触发条件，本作品两种情形均不成立。

### 8.4 第三方 API 服务的凭据与内容边界

三处 API（DeepSeek、智谱、SiliconFlow）的 Key 只落在本机 `.env` / `.llm_platform.json`，均已 `.gitignore`；仓库、报告、视频、佐证材料中**不含任何明文凭据**（提交前已逐文件扫描）。调用内容为公示语料片段与结构化字段，不含个人信息。

### 8.5 数据的再分发边界
