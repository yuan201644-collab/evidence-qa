## 一、这份文档解决什么问题

三个人的模块都要依赖同一批数据结构：A 的后端产出它们、B 的前端读取它们、C 的评测校验它们。
字段名一旦不一致，就只能在联调时才发现，三个人一起返工。

**本文档是字段的唯一真相。** 改字段 = 改本文档 + 改 `app/contracts.py` + 群里说一声。

### 字段的来源（重要）

本设计的字段**不是凭空定的**，其中两类字段名早已写在项目文档里：

| 结构 | 字段名出处 | 能否改动 |
|---|---|---|
| `AskRequest` / `AskResponse` | `docs/功能清单与技术框架_v1.md` 第 97 行 | ❌ 不能（文档已定） |
| `ToolResult` | `docs/功能清单与技术框架_v1.md` 第 98 行 | ❌ 不能（文档已定） |
| `TraceStep` | 功能清单第 132 行的文字描述 | ⚠️ 字段名本次新定，改动需同步 |
| `Ref` 家族（`BaseRef` / `SqlRef` / `DocRef`） | **本文档新定** | ⚠️ 本次新定，改动需同步 |

功能清单是入仓文件、三个人都能看到，**所以「文档就是约定」**。

## 二、四个结构总览

```
                         ┌─────────────────────────────┐
     用户提问 ──────────▶│  AskRequest                 │
                         │    question, session_id     │
                         └──────────────┬──────────────┘
                                        │ 编排层调度工具
                                        ▼
                         ┌─────────────────────────────┐
                         │  ToolResult（每个工具一个）  │
                         │    data, trace, refs        │
                         └──────────────┬──────────────┘
                                        │ 汇总
                                        ▼
                         ┌─────────────────────────────┐
     答案返回 ◀──────────│  AskResponse                │
                         │    answer, trace, refs,     │
                         │    sql, need_clarify        │
                         └─────────────────────────────┘

  被上面两个结构共用的零件：
     TraceStep  ── 一步工具调用的事实记录（可解释性的载体）
       └─ hit: list[BaseRef]
     BaseRef    ── 一条引用（答案从哪来）
       ├─ SqlRef（问数据库）
       └─ DocRef（问文档）
```

## 三、`Ref` 家族：引用

### 3.1 为什么用「继承」

引用要同时服务两个完全不同的场景：

- **问数据库** → 要说明「哪张表、哪个字段、哪一行」
- **问文档** → 要说明「哪份文档、哪一页、哪个章节」

这两种信息长得完全不同，但有**两件事是共同的**：

1. 都要标明「我是哪一种引用」（否则前端不知道该怎么读）
2. 都要带「引用原文片段」（**这是评测硬要求，见下**）

所以设计成：**基类放共同字段，子类各加自己的字段**。

### 3.2 基类 `BaseRef`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `kind` | `str` | ✅ | 类型标记：`"sql"` 或 `"doc"`。**用于让程序区分是哪个子类** |
| `snippet` | `str` | ✅ | **引用原文片段**，必须非空 |

> **为什么 `snippet` 必须非空**
> `docs/评测口径_v0.1.md` 第 200 行规定：RAG 单文档每条通过，**必须带出处引用（引用片段非空、且指向实际检索到的文档）**，
> 并注明「没有引用的答案即使内容对，也不算这条通过」。
> 把 `snippet` 放在基类，是为了让这条要求**只有一处定义**，改一次两类都生效。

### 3.3 子类 `SqlRef`（问数据库）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `table` | `str` | ✅ | 命中哪张表 |
| `column` | `str \| None` | 否 | 命中哪个字段（整行引用时可为空） |
| `row_pk` | `str \| None` | 否 | 命中哪一行（主键值，用于前端高亮） |

### 3.4 子类 `DocRef`（问文档）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `doc_id` | `str` | ✅ | 命中哪份文档（**内部标识**，可能是 `"1"` 这种不可读的值；**不放文档名**） |
| `doc_title` | `str \| None` | 否 | **对外显示名**，如 `"员工报销制度"`。引用卡片显示用（v0.3 新增） |
| `page` | `int \| None` | 否 | 第几页（**一个 ref 只对应一页**，见下） |
| `section_path` | `str \| None` | 否 | 章节路径，如 `"第 3 章 > 3.2 报销标准"`。**对应中级任务 7 的层级识别** |
| `char_start` | `int \| None` | 否 | 文本级偏移：片段在「全文虚拟拼接」中的起始字符下标（从 0 起算） |
| `char_end` | `int \| None` | 否 | 文本级偏移：结束字符下标（**不含**该位置） |
| `bboxes` | `list[tuple[float,float,float,float]]` | 否 | **几何级定位**：要渲染高亮的矩形集合，每项 `(x0, y0, x1, y1)`（v0.3 新增） |
| `page_width` | `float \| None` | 否 | 本页原始宽度（point）。`bboxes` 的换算基准（v0.3 新增） |
| `page_height` | `float \| None` | 否 | 本页原始高度（point）。`bboxes` 的换算基准（v0.3 新增） |

> `section_path` 用字符串而不是列表，是为了「切片时方便、展示时直观」。
> 层级识别（中级任务 7）产出的就是这个路径。

#### 3.4.1 两套坐标，用途不同，**别混**（v0.3 重点）

`DocRef` 里同时有**两组定位信息**，它们服务的目的完全不同。这是 v0.3 最核心的一条澄清。

| | 文本级定位 | 几何级定位 |
|---|---|---|
| **字段** | `char_start` / `char_end` | `bboxes` + `page_width` / `page_height` |
| **坐标系** | 「**全文按块阅读顺序虚拟拼接**」后的字符序号 | PDF 原生坐标系（**原点左上、单位 point**） |
| **能干什么** | 排序、去重、在文本流里定位上下文 | **前端画高亮框** |
| **不能干什么** | ❌ **不能做像素高亮**（它根本不是坐标） | ❌ 不能用来跨页排序（跨页各算各的） |

> ⚠️ **v0.2 的描述有误，v0.3 更正**：v0.2 写的是「有了字符偏移，前端才能精确高亮」。
> 这句话不准确 —— 字符偏移是**文本流里的下标**，从中**反推不出页面上的位置**。
> 真正能画高亮的是 `bboxes`。`char_start` / `char_end` 的正确用途是「文本级定位」。
> （这个矛盾是 B 指出来的，原话：「`chunker` 那边明确说它是全文虚拟拼接偏移、非像素定位、不能做精确高亮」。）

#### 3.4.2 为什么 `bboxes` 必须配 `page_width` / `page_height`（v0.3 最容易被漏的一条）

`bboxes` 里的数字是 **PDF 原生坐标（单位 point，1 point = 1/72 英寸，原点在页面左上）**。
它**不是**像素，也**不是**比例。前端要把这个框画到网页画布上，必须做一次换算：

```
渲染像素 = bbox_point × (画布像素宽 ÷ 页面原始宽)
```

**没有 `page_width` / `page_height`，`bboxes` 就是一组无法解释的数字** —— 光加框，前端照样画不出来。

> ⚠️ **为什么这两个字段放在 `DocRef` 里、而不是做成文档级统一值**
> **同一个 PDF 里不同页可以有不同尺寸**（混排 A4 / A3 是完全合法的）。
> 所以页面尺寸必须**跟着 `page` 走**，一页一对，不能用文档级的一个值代表全书。

> ⚠️ **`bboxes` 的元素类型锁死为「恰好 4 个 float」**
> 用 `list[tuple[float, float, float, float]]` 而不是 `list[list]`。
> 前者写成 `(1,2,3)` 或 `(1,2,3,4,5)` 会**当场报错**；后者悄悄放进去，前端拿到才发现画不出框。
> 错误要在**建对象时**暴露，不要拖到渲染时。

#### 3.4.3 约定：**一个 `DocRef` 只对应一页**

跨页的引用（比如一段话从第 3 页延续到第 4 页）由 **B 侧按页拆成多个 `DocRef`**，
而不是在一个 `DocRef` 里塞两组 `bboxes`。

**为什么要立这条**：`page` 是单个整数（不是列表），`page_width` / `page_height` 也只有一对。
如果允许一个 ref 跨页，这两个字段就**无法表达**「第 3 页宽 595、第 4 页宽 842」这种情况，
前端也就没法换算。**一页一 ref 是让契约保持简单的关键约束。**

> **当前实现天然满足**：B 的 `chunker.py` 合并切片时已要求「同页」，
> 所以现在的链路本来就不会跨页。**这条约定是为将来放宽合并预留的** ——
> 届时只需按页拆 ref，契约本身不用再动。

> 决策过程：B 提了两个方案，方案甲「一 DocRef 一页、跨页拆多个」、方案乙「一个 ref 带页列表」。
> **双方同意采用甲** —— 乙会让 `page` / `page_width` / `page_height` 三个字段都变成列表，
> 复杂度和前端解析成本都高一个量级，收益却只是少几条 ref。

#### 3.4.4 `doc_title` 与 `doc_id` 的分工

| 字段 | 用途 | 特点 |
|---|---|---|
| `doc_id` | **内部标识**，程序用它去查文档 | 可能是 `"1"` 这种不可读的值 |
| `doc_title` | **对外显示名**，前端引用卡片显示 | 人可读，如 `"员工报销制度"` |

**取值政策（当前）**：**优先 `manifest.json`，取不到则退回文件名兜底**。
拿不到就留 `None`，前端可退回显示 `doc_id`。

> **为什么不让前端拿 `doc_id` 自己查登记表**
> v0.2 的设计是「前端拿 `doc_id` 去登记表查」。
> 问题：登记表在前端要额外维护一份，且「内部标识 → 显示名」的映射知识只存在于数据层，
> 前端不该复制一份。**让后端一次填好、前端直接显示，耦合最少。**

#### 3.4.5 为什么用 `bboxes` 而不是 `highlight_boxes`（记录一次讨论）

备选名有两个：`bboxes`（B 倾向）与 `highlight_boxes`（曾作为备选提出）。

**最终采用 `bboxes`**，理由：

1. **同源同义**：当前 `DocRef` 引的就是**整个 chunk**（`snippet = chunk.text[:200]`，
   `char_start` / `char_end` 都是整块范围），
   与 `Chunk.bboxes` **指向同一批框**。改名会凭空造出两个名字指向同一事物。
2. **语义分化是将来时**：只有当真的做「片段级高亮」（框只覆盖片段而非整块）时，
   `DocRef.bboxes` 与 `Chunk.bboxes` 的语义才会分家。**到那时再改名，成本才划算。**
3. **改名成本**：`extra="forbid"` 下改名是**破坏性变更**，要三人同步、要改 B 的两处构造点。
   为一个「预防性」的理由付这个成本不划算。

> 记录这段是为了避免将来有人问「为什么不叫 `highlight_boxes`，明明语义更清楚」。

### 3.5 ⚠️ 用继承必须写的一句话

`refs` 是一个「里面混装 `SqlRef` 和 `DocRef`」的列表。程序转成 JSON 时**需要被告知「按哪个字段区分」**，
否则子类字段会**静默消失**（不报错，但 `page`、`doc_id` 不见了）。

```python
RefT = Annotated[DocRef | SqlRef, Field(discriminator="kind")]
refs: list[RefT]
```

**不能**写成 `list[BaseRef] = Field(discriminator="kind")` —— pydantic v2 会报 `TypeError`，
明确提示「判别式要加在联合类型上，不是加在列表上」。这是本项目实测踩过的坑。

## 四、`TraceStep`：一步工具调用

**这是可解释性 5 分的唯一载体。** 评分要求「推理链路、工具调用链、数据来源、可溯源证据」，
这些必须是**代码埋点录下来的事实**，不许让模型自己叙述（模型会事后合理化，不可验证）。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `step_id` | `int` | ✅ | 第几步，从 1 开始 |
| `tool` | `str` | ✅ | 调了什么工具，如 `"nl2sql"` / `"rag_search"` |
| `input` | `dict` | ✅ | 传给工具的入参 |
| `output` | `dict` | ✅ | 工具返回的产出摘要 |
| `elapsed_ms` | `float` | ✅ | 这一步耗时（毫秒） |
| `hit` | `list[BaseRef] \| None` | 否 | 这一步命中了什么来源 |

> ### `hit` 为什么直接复用 `BaseRef`（关键设计）
> 「这一步命中了什么」和「答案引用了什么」在语义上是**同一件事**。
> 如果为 `hit` 另造一套结构，将来必然不同步（改了一处忘另一处）。
>
> **并且**：`AskResponse.refs` 就是**所有 `TraceStep.hit` 的并集去重**。
> 这个关系必须写在这里，否则将来会有人手动往 `refs` 里塞东西，导致它和 `trace` 对不上。

## 五、`ToolResult`：一个工具的返回值

字段名由 `docs/功能清单与技术框架_v1.md` 第 98 行定死：

```
tool(input) → ToolResult{data, trace, refs}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `data` | `Any` | 工具的原始产出。NL2SQL 是结果行、RAG 是检索片段 |
| `trace` | `list[TraceStep]` | 这个工具内部产生的步骤 |
| `refs` | `list[RefT]` | 这个工具的引用列表 |

> **不要加第四个字段。** 这是文档已定的三人约定。
>
> ⚠️ **编排层拼接规则**：编排层要把各工具的 `trace` 拼成总 trace。
> 拼接时**必须保证每一步都带 `tool` 字段**（`TraceStep` 本来就有），
> 否则多个工具的 trace 拼在一起后分不清哪步属于哪个工具。

## 六、HTTP 契约

字段名由功能清单第 97 行定死：

```
POST /api/ask  {question, session_id} → {answer, trace, refs, sql, need_clarify}
```

### 6.1 `AskRequest`（请求体）

| 字段 | 类型 | 说明 |
|---|---|---|
| `question` | `str` | 用户原话 |
| `session_id` | `str` | 会话标识，**多轮对话 5 分依赖它** |

> `session_id` 只定义「字段长什么样」，**不定义「会话状态存哪」**（内存 / Redis / 数据库）。
> 存储方案属于编排层的设计，在 `app/orchestrator.py` 与 `app/memory.py` 里定。

### 6.2 `AskResponse`（响应体）

| 字段 | 类型 | 说明 |
|---|---|---|
| `answer` | `str` | 最终答案。**需要澄清时，这里装的是反问句** |
| `trace` | `list[TraceStep]` | 完整调用链（各工具 trace 拼接） |
| `refs` | `list[RefT]` | 引用总表 —— **所有 `hit` 的并集去重** |
| `sql` | `str \| None` | 走结构化链路时才有 |
| `need_clarify` | `bool` | 是否需要用户补充信息（中级任务 3：主动澄清） |

> **为什么澄清时复用 `answer`**
> `need_clarify` 是个布尔值，但「反问句放哪」需要一个位置。三种选择：
> ① 复用 `answer`（**本方案**）② 新增 `clarify_question` 字段 ③ 塞进 `trace`。
>
> 选 ① 的理由：功能清单已把这 5 个字段定死，**加字段等于动三人已看到的约定**。
> 而且 ① 完全够用：前端看到 `need_clarify=true`，就把 `answer` 当问题展示。

## 八、对 B、C 的请求

### 给 B（非结构化链路 + 前端）

1. **溯源页**：`refs` 里每条带 `kind` 字段，读到 `"sql"` 展示表/字段，读到 `"doc"` 展示文档/页码。
2. **澄清交互**：收到 `need_clarify: true` 时，把 `answer` 当问题展示（不要另找字段）。
3. **几何高亮（v0.3 新增）**：`DocRef` 现在有 `bboxes` + `page_width` / `page_height`。
   **两个构造点都要改**（见下条），且 `page_width` / `page_height` 必须**按页取**，不能用文档级统一值。
4. **🔴 顺序不可反 —— 先 A 改契约，再 B 改构造点**：
   `contracts.py` 用了 `ConfigDict(extra="forbid")`（多传一个字段直接抛错）。
   所以在契约加上这 4 个字段之前，B 若先往构造点里传 `bboxes`，**代码会直接报校验错**。

### v0.3 变更理由

**起因**：B 在实现 RAG 检索时提出 ——「**光加 `bboxes`，前端还是画不出高亮**」。
B 指出 `bboxes` 是 PDF 原生坐标（原点左上、单位 point），
前端要换算成像素**必须知道页面原始尺寸**，否则 `bboxes` 只是一组无法解释的数字。

**A 的核实**：`grep rect|width|height` 扫过 `loader.py`，**确认零命中** ——
即当前链路里**根本没有任何地方取过页面尺寸**。B 的判断是对的，
这也是本轮**最有价值的一条意见**（A 起初只想着补 `bboxes`，没意识到它还缺换算基准）。

**顺带更正的矛盾**：v0.2 在 `DocRef.char_start` 的描述里写了「用于前端精确高亮」，
而 B 的 `chunker.py` 里写明它是「全文虚拟拼接偏移、非像素定位、不能做精确高亮」。
**两处冲突**。v0.3 统一为后者口径，并把「像素高亮」明确归给 `bboxes`。

**为什么 4 项一次加齐、而不是分两次**：
`extra="forbid"` 下每次加字段都是**破坏性变更**（要三人同步、B 要改两处构造点）。
4 个字段服务于**同一件事**（前端画高亮框 + 显示引用卡片），
分两次改就是让 B 改两遍构造点。**一次到位，只付一次成本。**

**关于「跨页拆分」为什么必须写进契约**：
`page` 是单个 int、`page_width` / `page_height` 只有一对。
若不立「一 ref 一页」的约定，跨页时这三个字段**无法表达**，前端没法换算。
当前 `chunker` 合并已要求同页、天然满足，但**约定必须写在纸面上**，
否则将来有人放宽合并规则时，会无意中破坏契约。

**兼容性**：4 个新字段**全部可选、全部有默认值**
（`doc_title` / `page_width` / `page_height` 默认 `None`，`bboxes` 默认空列表）。
因此：
- B 尚未改构造点之前，**现有代码行为完全不变**
- C 的评测逻辑不受影响（新增字段不参与判定）
- v0.2 的调用方（如有）行为不变

**`bboxes` 的默认值写法**：用 `Field(default_factory=list)`，
不用裸的可变默认值。（实测 pydantic v2 对可变默认值会为每实例深拷贝，
裸写其实也是安全的；但 `default_factory` 是通行惯例，避免读者误判为共享陷阱。）
