# 契约设计 v0.4：逐事实核验响应增量

> 状态：实现分支中的契约版本；基于 v0.3 增量扩展。合并前需由 B、C 按本文件及实施记录复核。
> 日期：2026-10-14
> 既有引用、工具轨迹、问答字段和 v0.3 内容继续有效，见 [`契约设计_v0.3.md`](契约设计_v0.3.md)。

## 1. 变更目的与边界

新增可选 `AskResponse.fact_review`，用于在工单—合同服务时限事实计划中，展示账本事实状态、任务终态、已记录的结构化检查结果及其在最终响应 `refs` 中的来源位置。它不是答案逐句事实核查，不扩展普通数据库问答、普通文档问答、澄清或 KAG 路径，也不改变事实计划的业务判定。

## 2. 请求协商与兼容

调用方使用请求头 `X-AskData-Fact-Review: 1` 明确请求新字段。

- 未带该头：`/api/ask` 与 `/api/ask/stream` 最终响应都省略 `fact_review` 键，保持 v0.3 的 JSON 键集合。
- 值为 `1`：仅当本轮走到有明确模式的跨源事实计划时附加 `fact_review`；普通问答不返回空壳字段。
- 其他值：返回 HTTP 400，不静默降级。
- 流式接口只在 `complete.response` 里附加最终事实账本；阶段事件仍按真实执行进度发送，不提前表示核验结果。
- 新前端发送该头。若连接到尚未升级的旧后端、后端忽略未知请求头且未返回 `fact_review`，前端继续展示普通回答，不显示空卡片。

此机制保持“不协商即旧响应”的兼容边界。它不证明外部严格响应模型在显式协商后能接受新增键；使用新字段的调用方须按 v0.4 更新。

## 3. `fact_review` 数据结构

```json
{
  "schema_version": "1",
  "coverage": "cross_source_work_order_sla",
  "verification_mode": "strict",
  "scope_note": "仅展示事实计划记录的事实状态与证据关联，不代表答案中的其他表述均已核验。",
  "items": [
    {
      "fact_id": "sla_verdict",
      "label": "修复时限判断",
      "summary": "修复耗时 7 小时，合同限时 8 小时，符合合同限时。",
      "status": "supported",
      "execution_status": "completed",
      "evidence_link_status": "complete",
      "checks": [{"code": "service_restored_within_limit", "result": "passed"}],
      "evidence_ref_indices": [0, 1],
      "reason_code": null,
      "reason": null
    }
  ]
}
```

### 字段口径

| 字段 | 定义 |
|---|---|
| `schema_version` | 本对象形状版本，当前为字符串 `"1"`；不替代整体 `AskResponse` 契约版本。 |
| `coverage` | 当前只允许 `cross_source_work_order_sla`。 |
| `verification_mode` | 由事实计划执行结果显式携带的 `strict` 或 `ablation`；未知 / 缺失时不生成对象。 |
| `items[].status` | 来自同一轮 `FactRecord.state`：`candidate`、`supported`、`contradicted`、`insufficient`、`ambiguous`。 |
| `execution_status` | `fact_task_not_run` → `not_run`；`fact_task_failure` → `failed`；正常形成记录且无上述终态 → `completed`。`completed` 只代表处理到达终态，不代表查询成功或事实充分。记录缺失 / 终态冲突安全降为 `failed`。 |
| `evidence_link_status` | `complete` / `partial` / `unavailable` 表示账本证据是否能唯一、精确绑定至同一响应的 `refs`。 |
| `evidence_ref_indices` | 0-based 最终 `refs` 下标；先完成引用定序与去重再投影，并与该 `refs` 列表同包返回。 |
| `checks` | 只投影真实结构化结果；例如 `metric_checks[].within_limit`。`customer_scope_checked`、`event_order_checked`、`mapping_and_contract_windows_checked_separately` 等开关不得伪装成通过。 |
| `summary` | 可选摘要，仅按任务类型从允许字段确定性生成；禁止透传通用 `FactRecord.value`，尤其不得透传答案整段。 |
| `reason_code` / `reason` | 允许清单中的稳定诊断类别与固定中文说明；不包含原始异常、SQL、提示词或秘密。 |

### 证据定位规则

- SQL 引用必须带非空表名与行主键；文档引用必须带文档编号及完整字符起止偏移。只靠表名 / 字段名或文档编号 / 页码 / 章节等粗定位不生成证据索引。
- 候选最终引用只能唯一匹配一条时才写入下标。重复候选、越界、定位信息不足、证据折叠或来源无法区分时降为 `partial` / `unavailable`；不按片段相似度猜配。
- `complete` 要求该事实的全部不同证据均唯一命中最终 `refs`，且没有未映射来源；`unavailable` 包括账本无证据或无可靠命中。

### 展示边界

只有 `verification_mode=strict`、`execution_status=completed`、`status=supported`、`evidence_link_status=complete` 且至少一条有效来源索引同时成立，前端才显示“严格核验通过”。`supported` 只描述账本事实，不自动等同于“满足合同”；消融模式、证据不全、任务未执行或失败均不得显示通过。卡片只描述事实项，不给答案句子加“已核验”标签。

## 4. 版本变更记录

- v0.1–v0.3：既有引用、文档坐标与几何高亮扩展，分别见对应历史契约文档及代码记录。
- v0.4：新增可协商的事实账本响应、显式严格 / 消融模式、任务执行状态、精确证据索引；无协商时维持既有响应键集合。
