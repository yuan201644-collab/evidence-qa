## 1. 本次范围与完成标准

按两轮实施，先交付清楚可用的问答页面，再接通真实的逐事实核验记录。

- 第一轮：调整首页信息层级、回答区阅读顺序和证据入口。首页分成“问数 / 问答 / 跨源问题”三个业务板块，跨源板块重点呈现；使用现有接口，保留现有问答、追问、分页、导出和原文定位能力。
- 第二轮：扩展统一事实—证据展示契约，并分别接入数据库问数、文档问答和已有工单—合同跨源流程。展示范围由各路径实际产生的结构化记录决定；文档检索到引用不能自动包装成答案事实已验证。
- KAG 纳入本轮规划的可选扩展：项目 RAG 保持默认；用户手动选择“深度检索”时，可由 KAG 支线补充候选证据，再交给项目核验与回答器。当前仅预留文档接口、展示位置和验收条件；真实接入由项目负责人指定的 KAG 支线执行者完成。自动缺口触发属于后续独立验证项，Stage22 没有验证该策略。

用户验收标准：第一次打开能直接开始提问；看完回答能找到决定结论的事实；点击事实能核对对应证据；遇到缺口能知道还缺什么、可以怎样补充。

本规划不要求所有问题强行走跨源流程。单源问题使用其实际查询、检索和检查结果；简单问题保持简洁，大结果集继续用表格展示。

| 阶段 | 任务 | 产物与完成门槛 |
|---|---|---|
| A | 确认共同代码基线 | 可复现候选分支、改动归属说明、运行环境记录 |

## 5. 阶段 A：建立共同代码基线

### A1. 只读核对

在 PowerShell 执行：

```powershell
Set-Location -LiteralPath 'C:\Users\86133\WorkBuddy\多模态数据驱动的可解释精准问数问答智能体'
git status --short --branch
git diff --cached --stat
git fetch origin
git log -5 --oneline origin/main
git rev-list --left-right --count origin/main...HEAD
git diff --stat
git ls-files --others --exclude-standard
```

逐项登记未提交改动的归属、用途和依赖。尤其核对账号、公网网关、欢迎页动画和回答进度修改，不得整体暂存后以“前端改版”名义上传。

### A2. 建立隔离实施分支

原工作区有多人修改时，优先从最新 `origin/main` 建独立工作树（worktree，即同一仓库的另一份工作目录）。以下命令仅在正式执行时使用，目标目录及分支名必须先确认不存在：

```powershell
git worktree list
git branch --list 'codex/fact-evidence-workbench-v01'
Test-Path -LiteralPath '.\agent_temp\fact-evidence-workbench-v01'
git worktree add -b codex/fact-evidence-workbench-v01 .\agent_temp\fact-evidence-workbench-v01 origin/main
```

如目标已存在，先检查它的用途，再选新路径。不要删除已有工作树、清空原工作区或自动打包所有未提交内容。

明确哪些本机改动确为本轮所需，逐项审阅后迁入候选分支。例如“隐藏测评入口”只有小范围显示改动，不应同时带入账号系统的全部变更。

### A3. 环境门槛

- 前端：使用项目锁文件安装依赖，检查 Node/npm 能运行；默认页面 `http://127.0.0.1:5173`。
- 后端：Python 3.11+，使用 `uv` 和项目现有依赖；默认接口 `http://127.0.0.1:8000`。
- 受控界面检查：需要本机 Edge 或 Playwright 可用的 Chromium，不依赖模型和业务数据库。
- 真实链路检查：需要候选版本对应的数据库、文档索引、本地模型与在线模型配置；从本机环境读取凭据，不写入文档或提交。
- 独立工作树不会自动带入被 Git 忽略的 `.env`、模型权重、原工作区 `.venv` 或数据库内容。按候选版本的 `.env.example` 核对配置，安全提供运行参数或复用已明确的模型资源路径；由 `uv` 为该目录建立环境，不能假定复制目录后后端即可运行。
- 复用已有数据库容器时，记录数据库身份、数据范围及快照；不得为了前端检查重置团队正在测试的库。
- 若候选版本包含账号鉴权，检查脚本必须使用正常登录会话。当前本机 `test:ui:live` 和 HTTP 评分器是否支持相应认证，需要先核对；不得通过关闭鉴权绕过。
- 临时截图、录屏和调试文件放 `agent_temp/`；正式验证记录归档到 `docs/` 或既有评测目录。任务结束只清理本轮确定归属的临时文件。

**A 完成条件：**执行者知道自己测试的是哪份代码，B/C 和负责人可拿到同一提交及同一份环境说明。

## 6. 阶段 B：首页与导航减负

主要文件：`web/src/views/WorkspaceView.vue`、`Composer.vue`、`QuestionGallery.vue`；必要时同步界面偏好说明，不扩展账号或后台功能。

### B1. 顶栏

- 普通工作台隐藏“中级任务”和“系统评测”，管理员登录也遵守相同展示策略。
- 保留会话切换、帮助、设置和账号等必要入口。
- FEVA 架构说明移到次级“系统说明”入口，保留品牌名称和资产。
- “来源证据”只在有可查看的回答时作为上下文操作显示；数量明确对应当前选中回答，不能错指另一条历史消息。

### B2. 首页

页面阅读顺序调整为：一句用途说明 → 输入框 → 三类业务板块与例问（问数 / 问答 / 跨源问题）→ 当前材料范围 → 简短使用流程。

建议说明文案：“提出问题，系统为你查明事实、核对依据，并给出可追溯的答案。”正式实施时结合已接通能力调整，不承诺任意问题均已核验。

- 三个板块解释用户要完成的业务目标，不是让用户选择 SQL、RAG 或 KAG。自由提问仍由系统路由；点例问只填入输入框，不自动发送，也不强制固定底层工具。
- “问数”板块展示数据库类例问，“问答”板块展示文档类例问，“跨源问题”板块展示同时依赖业务数据和文档条款的复合例问。每条例问标注其可验证的材料范围，不用当前环境实际无法运行的样例作可点击演示。
- 桌面端建议前两张单源卡片并列，第三张“跨源问题”横跨内容区并作为重点卡片，使用品牌主色边框、轻量底色和“跨源核验”标记突出；不使用会被误认为实时执行进度的静态动画。
- 手机端纵向排列三张卡片，压缩单源卡片高度；跨源卡片保留突出色和适用范围，但不挤占提问输入区，也不依赖横向滚动。
- 候选例问：问数“平台上一共有多少位客户？”、“2023 年一整年一共开了多少张发票？”；问答“智能计算设备年度维保服务合同里，质保期是多久？”、“机房日常巡检的时间安排是怎样的？”；跨源“工单 WO-2026-0001 是否在合同修复时限内完成？修复耗时是多少？”。实施前须在最终候选环境逐条实跑，确认材料、路由和返回证据一致后才可作为可点击例问。
- 当前跨源完整核验只覆盖隔离演示环境中的工单—合同场景。只有跨源演示路由和对应演示数据可用时，才启用可点击例问；不可用时可保留板块介绍，但须标注“演示数据未连接”，不得呈现为已接通能力。
- 每个板块首屏至少展示一条已实跑通过的例问；更多例问可折叠。点击示例只预填，不自动发问，保留用户编辑权。
- 首页输入框不得与底部输入框重复；进入会话后复用同一输入组件。
- 首次使用提示改为可关闭的轻量说明，不强制完成三页弹窗才能提问。
- 详细架构、英文模块名和研究支线信息收进系统说明。
- “当前可查询范围”使用实际数据源元信息；没有总览接口时，按实际已知来源展示，不伪造数量或“全部连接正常”。

### B3. 窄屏

390 像素宽度下，默认首页能看到用途、输入区及至少一个可用示例。其余说明可下滑查看。保留已合入的单行追问建议、按需查看依据和紧凑提示。

**B 完成条件：**桌面与手机都能直接开始问答，操作入口清楚，无技术模块目录抢占首页中心。

## 7. 阶段 C：使用现有接口整理回答结构

主要文件：`AnswerBubble.vue`、`CitationList.vue`、`TraceDrawer.vue`、`ResultSetTable.vue`、`EvidencePanel.vue`、`web/src/utils/trace.ts`。

此阶段仍使用既有 `answer`、`refs`、`trace`、`need_clarify`、`result_set` 等字段。

### C1. 阅读层级

1. 首先显示完整回答；不靠正则截出一段当作模型未提供的“结论摘要”。
2. 查询结果表格继续支持分页、导出与完整性提示。
3. 下方展示“回答依据”，每条可点击核对来源。
4. 工具调用、输入输出、耗时放进“处理详情”，默认收起。
5. 澄清显示“需要补充的信息”；执行错误显示未完成原因及重试入口。

### C2. 状态真实性

- 有引用不等于事实已核验；HTTP 200 不等于业务回答正确。
- 没有新的明确状态字段时，不从回答中的否定词自动判定“证据不足”或“核验失败”。
- `need_clarify` 只用于真实澄清；它与执行失败、材料不足分别处理。
- 第一轮没有逐事实记录的回答，不展示空的“关键事实”列表、虚构支持关系或总体核验通过标记。
- 工具累计耗时和端到端等待时间分别标注，不能相互替代。

**C 完成条件：**现有回答、来源和详情按用户阅读顺序排列，原有业务行为保留，旧消息仍可阅读。

## 8. 阶段 D：确认并接通事实展示数据

主要文件：`app/evidence_ledger.py`、`fact_executor.py`、`cross_source_fact_plan.py`、`orchestrator.py`、`contracts.py`、`app/progress.py`、`web/src/types/contracts.ts`、`web/src/stores/persistence.ts`。

### D1. 先核对真实数据

对已有工单—合同事实流程，追踪 `FactTask`、`FactRecord`、事实依赖、采用的证据和首个阻断原因从执行到最终回答的全过程。

当前完整事实记录是后端内部对象，公共 `AskResponse` 没有完整逐事实展示字段。不能只根据工具名称或回答语气，在前端反向猜测事实清单。

普通 SQL/RAG 路径目前仍主要按实际来源及调用记录展示，尚未统一投影为逐事实记录。扩展时须分别实现事实生产与检查适配器：数据库路径以实际意图、校验、执行和结果记录为依据；文档路径先记录可定位的原文证据与检索状态，只有确有独立事实匹配检查时才标记事实受支持。不能从最终答案文本反推事实，也不能把文档命中、SQL 成功或 HTTP 200 当成事实核验通过。

### D2. 推荐的数据设计（提案，不是已生效契约）

推荐给 `AskResponse` 增加默认可空的事实核验展示字段 `fact_review`。当前候选契约把 `coverage` 限定为 `cross_source_work_order_sla`，不能直接冒充三类路径的通用契约。扩展前先与 B/C 对齐并记录接口变更；建议升为 schema v2，明确覆盖值 `single_source_sql`、`single_source_document`、`cross_source_work_order_sla`，保持原有必填字段不变。未显式请求该字段的旧调用仍不返回它，旧前端继续按普通回答、来源和处理详情展示。

| 展示数据 | 用途与约束 |
|---|---|
| 版本与展示覆盖范围 | 区分数据库、文档、跨源三类实际路径，表明哪些事实确有记录，不能将部分覆盖宣传成答案全部已核验 |
| 事实标识及业务描述 | 同轮稳定标识；描述一项得出答案所需的业务事实 |
| 事实值及适用条件 | 值、单位、时间范围等来自真实记录，不额外编造 |
| 事实依赖 | 指向同轮已有事实，展示阻断影响 |
| 执行状态 | 区分尚未开始、进行中、已执行和未执行；未执行不等于已查但没找到 |
| 检查结果与原因 | 基于实际检查，说明核对了哪些条件、为什么受阻 |
| 对应证据 | 只关联最终响应或获授权展示的真实证据，确保同轮引用可解析 |
| 回答范围与未解决项 | 明确已回答和仍待确认的部分，缺口必须能追溯到真实记录 |

证据映射必须在引用合并、去重之后建立或重新校验。若采用引用下标，只能引用本次最终 `refs` 数组且验证范围；不能直接使用工具内部下标。采用稳定证据标识时，要同时约定前后端解析规则，避免切片或去重变化导致错指。

### D3. 业务状态映射

| 内部情况 | 推荐呈现 |
|---|---|
| 候选事实有注册来源但尚未完成检查 | 已取得来源，待核对 |
| 候选事实尚无注册来源 | 待核对；不显示“已取得来源” |
| `supported` | 已完成记录的检查，列出检查内容与依据 |
| `contradicted` | 不成立或存在反证，具体文字按真实业务含义确定 |
| `ambiguous` | 无法唯一确定，列出造成歧义的候选 |
| `insufficient` | 依据不足，说明缺口 |
| 执行记录表明任务未执行 | 未执行，显示前置阻断原因，不混入事实状态枚举 |

“耗时事实已核对，业务结果超过时限”是合法情形，不能显示成系统核验失败。`supported` 表示通过已实施的检查，不证明所有真实业务条件都已经校验。

| 问数 | “平台上一共有多少位客户？”、“2023 年一整年一共开了多少张发票？” | 指定候选数据库可连通；实际走数据库查询；结果及数据引用可查看 |
| 问答 | “智能计算设备年度维保服务合同里，质保期是多久？”、“机房日常巡检的时间安排是怎样的？” | 指定语料确实包含答案；实际走文档检索；引用能定位原文 |
| 跨源问题 | “工单 WO-2026-0001 是否在合同修复时限内完成？修复耗时是多少？” | 隔离演示库、工单—合同路由和文档索引均可用；确实完成数据库与合同原文核验；事实卡证据能分别打开对应来源 |

以上例问来自项目已有开发样例，不因此成为新留出题或效果证据。实施者需在选定候选版本上留存每条例问的实际请求、路由/trace 摘要、响应引用和截图；未通过的例问不得以“已验证”状态进入首页。跨源例问只有在隔离演示能力可用时才可点击运行；未启用时显示“演示数据未连接”，并保留能力范围说明。

### 14.4 三板块验收门

- 首屏可辨认三类问题，跨源板块视觉上优先于普通单源卡片，但输入框仍是首要操作。
- 对每个板块至少完成一条已验证例问的真实联调，确认题目、执行路径、回答和来源证据相符；跨源必须同时看到结构化与文档证据。
- 普通问数不应为了展示而调用文档；普通文档问答不应为了展示而调用数据库；跨源例问必须能观察到两类来源及其关联。发生路由不符时记为失败，不通过改标题或静态 UI 掩盖。
- 桌面、390 像素手机、亮/暗主题和减少动态效果环境下检查可读性、点按区域、卡片高度与输入框可达性。
- 三条路径结果卡的覆盖范围和状态文案必须与后端 `fact_review.coverage` 及真实检查一致；字段缺失时不显示空卡或“核验通过”。
