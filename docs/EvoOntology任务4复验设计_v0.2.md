# EvoOntology 任务4复验设计 v0.2

更新日期：2026-10-03。状态：**设计修订稿，尚未冻结、尚未执行**。

## 1. 这轮要回答什么

只回答一个中级任务问题：在 AdventureWorks 约 80 张表/视图、业务概念容易混淆的场景中，EvoOntology 的业务知识能不能帮助系统更准确地找出应该使用的表和字段？如果能，整本注入与按需检索哪种更合适？

本轮只测任务4，不据此推断任务1、3、5，也不把离线实验结果折算成赛事得分。当前 161 条记录归为 **v0.1 试跑数据**，仅用于发现问题；不补齐后并入正式分析。

## 2. v0.1 试跑审计结论

现有运行目录为 `eval/experiments/evont_next/run_task4_v0.1/`，记录 161 条：A 54、B 54、C 53；其中 160 条 SQL 执行成功、1 条失败。首 12 道题的指标只能描述这批题，不能代表稳定效果。

这批数据不能作为正式结论，原因如下：

1. A 臂有一条 SQL 因提取器丢掉 `WITH` 子句开头而解析失败。
2. C 臂虽运行了检索规划，但 SQL 生成时仍注入完整 80 对象结构，因此没有真正测“按需给模型看较小结构”。
3. 主指标从最终 SQL 反解析得到，是定位质量的代理指标；它不直接记录候选排序，也不惩罚多选无关表/字段。
4. 两次重复运行按两份独立样本计算；置信区间也按运行行重采样，忽略同一道题的相关性。
5. 当前双侧 McNemar 概率计算有误；执行顺序是固定交替，不是随机化。
6. `executed=True` 只表示 SQL 未报错，不代表结果语义正确；已有记录中有执行成功但结果全为 NULL 的例子。
7. 自动 gold 检查只校验字段存在与表字段归属，不能证明标准答案在业务语义上完整正确。

因此 v0.1 的初步差异可作线索，不能写成“已验证 Ontology 提升定位效果”。

## 3. 复验条件

| 条件 | 给模型的材料 | 用来回答 |
|---|---|---|
| A：无知识 | 原始完整数据库结构 | 基线定位能力 |
| B：整本知识 | 完整结构 + 冻结的业务知识条目 | 知识整体是否有帮助 |
| C：按需检索 | 检索器先从知识目录找条目，再只向定位模型提供命中知识和有限候选表的结构 | 按需检索能否减少上下文同时保持/改善定位 |

C 臂必须把最终传给定位模型的对象名单、字段数、知识条目编号写入逐题记录。若检索失败，该题记为失败，不允许静默退回完整结构。完整结构、系统提示和输出格式以外的差异都要记录。

为了避免混淆概念，B 对 A 的比较回答“加入整本业务知识是否有用”；C 对 B 的比较回答“按需检索流程相对整本注入的效果与成本”。C 包含额外检索规划步骤，因此此比较评价的是整体方案，不能单独归因于“检索”这一因素。

## 4. 题目与答案冻结

- 使用现有 32 道任务4题作为候选集，不自动假定 gold 正确。
- 首次正式请求前，由未参与出题/构建知识的人逐题核查业务问题、必要表、必要字段、可接受替代表达及歧义。核查记录独立保存；有争议题先修订或剔除，再冻结。
- 每题定义所需表集合和字段集合，并标注“必要”与“可接受替代”。不把仅因某个参考 SQL 写法出现的字段强行当成唯一正确答案。
- 冻结题集、gold、知识资产、提示模板、检索器、评分代码、模型标识、数据库结构摘要和随机种子，记录 SHA-256。
- 正式跑分期间不得根据输出修改题目、gold、知识条目或评分标准；发现错误则中止该版并升版重跑。

## 5. 任务与指标

主任务是**结构定位**。每个条件下要求系统输出有序候选表和候选字段清单及简短的可核查依据；不要求思维链。输出解析失败、超时或无候选均计为该题定位失败。

主指标：

- 必要字段召回率：命中的必要字段数 / 必要字段总数。
- 字段精确率：命中的必要字段数 / 输出字段数；空输出记 0。
- 必要表召回率和表精确率，按相同方式计算。
- top-1 / top-3 表命中率：所需核心表是否出现在排序前 1 / 3 位。
- C 臂额外报告传入定位模型的表数、字段数、知识条目数，以及模型请求数和词元数。

SQL 生成只作次要端到端检查：从冻结题集预先选定 8 题，三臂使用相同下游 SQL 提示和执行器，记录 SQL 是否通过安全校验、结果是否与人工核验 gold 一致。不能用“执行成功”替代结果正确率，也不以这 8 题推断主效果。

## 6. 样本与运行顺序

- 32 道独立问题是分析单位；同一道题若做重复运行，先对同题同臂取均值，再以题目为单位比较，不能把重复次数当新题数。
- 运行 A/B/C 三条件，按题目随机分配条件顺序，使用固定种子并记录实际顺序；不要固定让某臂总在中间。
- 正式跑前仅做小规模技术检查，确认输出可解析、记录完整、A/B/C 实际输入符合定义。技术检查题不进入正式集。
- 32 题可以支持一次小规模配对复验，但不足以承诺能检出很小差异。报告必须同时给原始计数、效果差、置信区间；区间过宽时结论写“证据不足”，不写“无效”。

## 7. 统计分析

- 连续型主指标以每题为单位计算 C−A、B−A 的配对差；用固定随机种子的**题目级配对 bootstrap**计算 95% 置信区间。
- 二分类命中指标以每道题为一个配对观测，使用标准双侧精确 McNemar 检验。重复运行先在题内汇总或按预先定义的二元规则折叠。
- 预注册的主要比较为 C 对 A 的必要字段召回率；B 对 A、C 对 B 和其他指标列为次要分析。报告所有比较，并对多个次要检验做多重比较校正或明确标为探索性。
- 统计脚本用已知小例子做单元验证：McNemar (b=5,c=0) 应得到双侧 p=0.0625；bootstrap 相同种子必须给相同结果；复制同题重复行不得增加独立样本数。

## 8. 决策标准

- **观察到增益**：C 对 A 的预注册主指标为正，95% 区间不跨 0，且定位精确率没有明显恶化；再查看端到端 8 题是否出现明显正确性回退。
- **未观察到明确增益**：区间覆盖 0。结论为“本样本下证据不足”，不直接声称 Ontology 无用。
- **发现代价或回退**：若 C 的定位效果接近 A/B，但上下文、请求数或延迟更高，应如实呈现成本；若候选精确率或 SQL 正确率下降，不建议接入主链路。
- 只有语义 gold 经独立复核、输入差异符合三臂定义、评分程序通过小例验证，才启动正式模型请求。
