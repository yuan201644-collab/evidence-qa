## 一、问题诊断

### 1.1 反馈的实质

导师的原话是「技术的罗列堆叠，缺少整体创新性架构」。对照我们现有材料的架构页（五层分层：交互→编排→工具→数据→模型），问题可以精确定位：

> **五层分层是通用分层，任何 Web 应用都能画成这五层。** 它回答了"我们用什么"，没有回答"为什么非这样不可"。每项技术各配一句理由，但理由之间没有结构关系——这正是"罗列堆叠"的观感来源。

### 1.2 一个可操作的检验法

> **「去掉任何一环，故事会不会塌」**：技术栈列表里删掉一项（比如把 pgvector 换成 faiss），叙事毫发无损——说明它只是选型，不是架构；而一条真正的处理流程里，去掉任何一步链路都会断裂。

我们现有架构图**过不了**这个检验；参考 PPT 的核心架构页（编号 ①–⑦ 的处理流水线）**过得了**。

### 1.3 参考项目是怎么做的

其核心架构页的主角不是技术栈，而是一条带编号的处理流程（DAG，有向无环图）：①意图识别 → ②数据类型分类 → ③实体抽取 → ④查询改写 → ⑤六类并行检索 → ⑥证据组装与评分 → ⑦报告生成。FastAPI、Milvus、BGE 只是图中的注脚。

## 二、参考 PPT 分析：学什么，不学什么

### 2.1 值得学的四点

| # | 做法 | 效果 |
|---|---|---|
| 1 | 架构页画成**编号 DAG 流程**，每步标输入输出 | 每一步的存在都有一个理由（朴素做法会怎么失败），技术退为注脚 |
| 2 | **设计原则显性化**：规则优先大模型兜底 / 六类并行保障召回 / 本地视觉降本降误判 / 全流程可观测可复核 | 每条原则统摄一组技术选择，选型从"我们用了 X"变成"因为原则 Y 所以选 X" |
| 3 | **业务闭环**：用户审核反馈触发独立重检索与报告修订，审核意见全程可追溯 | 不是 demo 跑完即止，有协同回路 |
| 4 | **数字与边界诚实**：687.5 万记录、命中得分 0.999/1.000/0.85；难点页分「已能处理 / 暂不能处理」两栏 | 可信度来自承认做不到什么 |

### 2.2 不要照搬的三点

1. **JWT、管理后台、React、监控面板**——那是横向工程项目的完备性，不是创新，竞赛评分表里也没有对应项；
2. **六类并行检索**——那是他们的问题形态（六类知识产权）。我们的问题形态是**双源异构（算/查）**，对应的架构主角是**跨源融合**，这恰是题面点名、参考项目没有的；
3. 学**叙事骨架**（DAG + 原则 + 闭环 + 诚实边界），不抄内容。

## 三、改进方案：一条 DAG + 四条原则 + 贯穿的评测契约

### 3.1 主流程七步（每步的存在理由）

> 判读说明：「现状」分两档——**已实现**（有代码/实验佐证）与**设计已定**（契约或决策记录已定稿，代码未落）。

| 步 | 环节 | 朴素做法的失败模式（＝这步为什么必须存在） | 现状 | 挂钩评分 |
|---|---|---|---|---|
| ① | 要素识别与改写 | 「帝都」不先改写成标准问句，路由认不出实体、SQL 无对应字段——**后面全错**。实测用例 rob-02：「买家」一词不在任何表名字段里 | 设计已定（`docs/要素识别与改写_接口_v0.1.md`，`app/nl2sql/` 未落码） | 中级任务 1 / 鲁棒性 10 |
| ② | 算 / 查分野路由 | 全塞给大模型：问数类**编数字**、问答类**无依据**。按**数据形态**裁决走哪条链（D1） | **已实现**（`app/orchestrator.py:97`） | 可解释性 5 / Demo 5 |
| ③ | 维度校验与澄清 | 「增长率是多少？」缺时间范围仍硬猜 → 一条看似合理的错误 SQL（题面：金融政务不可接受） | 契约已留（`contracts.py:225` need_clarify），逻辑待做 | 中级任务 3 |
| ④a | 问数支：表定位 → SQL 生成 → 只读校验 → 执行 | 语义干扰选错表（AdventureWorks 80 表）；模型直连库有泄露与写库风险（题面：一个错误的 JOIN 可能导致全量数据泄露） | 设计已定（sqlglot 校验 + 只读白名单 + 方言参数化） | 中级任务 4 / 执行准确率 10 |
| ④b | 问答支：分解 → 多轮检索 → 实体绑定验证 → 跨轮重排 → 生成 | 静态子查询不注入首跳实体 → 第二跳永远落空。**实测**：旧版 11/30 → 绑定约束改造后 **30/30**，耗时 12.1s → 6.2s | **已实现**（`app/rag/multihop.py`，四臂对照验证） | 忠实度 10 / 中级任务 7 |
| ⑤ | 统一引用与确定性埋点 | 两条链路各出一套证据格式 → 前端两套展示、用户对不上；靠模型自述做可解释则**不可验证** | **已实现**（`contracts.py:161/213`，契约测试 23 条全绿） | 可解释性 5 |
| ⑥ | 冲突显式暴露 | 文档间不一致时和稀泥 → 忠实度虚高。实测语料：合同「4 小时内到场」vs 承诺函「6 小时内到达现场」（rag-h-03） | 设计已定（D4），实现待做 | 忠实度 10 |
| ⑦ | 评测契约收口 | 「感觉变好了」不可验证；初赛 40 分客观分没有评测集就无从举证 | **已实现**（`eval/`，oracle 全量回放通过） | 全部客观分的举证 |

### 3.2 四条设计原则（每条统摄一组选型）

| 原则 | 一句话 | 统摄的选择 |
|---|---|---|
| **模型不碰执行权** | 数值由 SQL 与检索确定性得出，模型只把结果说成人话 | sqlglot 语法树校验、只读白名单、国产模型仅做理解与表达 |
| **改写先于路由** | 顺序错了全链路错 | normalizer 独立成模块、编排层入口先调一次、别名表独立维护 |
| **证据约束的多跳** | 第一跳实体必须能指回本轮已检索的片段才允许传递，指不回就退回单轮 | 自研多跳（而非整体引入 KAG）、`entity_bind` 埋点、两跳引用合并 |
| **有引用 ≠ 正确** | 引用编号有效不代表结论正确，忠实度必须单独判 | 三条件判分、禁答实体、规则自动判 + 人工复核 |

> 原则 3 的证据链要讲全：KAG 图谱臂与向量臂同为 25/30（图谱无增益），而 KAG 整体远强于改造前的项目链路（25 对 11）——差距在**规划**而非图谱，故移植规划、不搬图谱。这是「按 KAG 的规划思路改造后，在这套合成桥接题集上取得优于 KAG 两臂的结果」的完整出处。

### 3.3 保留的既有叙事

- **题目逐词拆解**（问数 / 问答 / 精准 / 可解释 四主词，各配题面原文）——保留，作为开场；
- **分数组成 45/55 洞察**（题目名称能直接对应的只有 45 分，另 55 分只在评分表里）——保留，作为"必须吃透评分表"的论据；
- **四层「准」**（听准 / 找准 / 做准 / 答准）——与 3.1 的七步对齐后可合并讲述；
- **五层分层图**——不删除，**降级为「部署视图」放附录**：它回答"怎么部署"，不回答"为什么这样设计"。

## 四、诚实边界（材料中必须保留的标记）

架构图与汇报材料保留两档现状标记（实线＝已实现 / 虚线＝设计已定），并遵守：

1. 四臂对照结果是 **30 道合成桥接题、单次运行（r1）**，实验方案要求每题每臂 3 次交错——最终判定要等跑满；
2. 判定口径为**字面关键词命中**与**文档编号级召回**，未做答案盲审与字符区间核对；
3. 合成题集与改造方案同源（都针对桥接实体型多跳），**不能直接外推到真实业务语料**；
4. 「系统效率 5 分」要求交复杂度分析 + 两种数据规模对比——目前**未做**，属于标题里看不出来的 55 分之一。
