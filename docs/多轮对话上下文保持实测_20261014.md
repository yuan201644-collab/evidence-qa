# 多轮对话上下文保持实测（2026-10-14）

## 结论与适用范围

- 在冻结题目与冻结代码版本下，跑一次完整多轮评测：**20 轮通过 19 轮（19/20）**，按「一条用例 5 轮全部通过才算通过」的口径为 **3/4 条用例通过**。
- 失败集中在 **mt-03 第 2 轮**：「他总共消费了多少？」模型**重查了客户档案表**（只少取一个 `address` 列），**没有去查 `invoice` 表**，因此没答出该轮唯一期望值 `37.62`。
- 该失败**已定性为真实功能缺口，不是模型偶发**：`app/nl2sql/followup.py` 的 `resolve_followup()` 只识别五类**显式**操作（`按…分组` 的替换/增加、`平均/均值`、`最多/最大/最高/最长/最小/最低/最短`），「他总共消费了多少？」这类**换度量、换查询对象**的自然追问**不被识别**（实测七种同义说法全部返回 `None`），于是拿不到 `followup_context`，AST 校验与失败回灌**都不会启动**。修复属于**扩功能**而非修缺陷，本轮**未改动该模块**，缺口与建议原样记录在下方「已知限制」。
- **不得对外使用 20/20**。本报告是当前唯一有冻结题目指纹与逐轮原始产物的多轮成绩；此前工作区中的三次运行（`agent_temp/runtime/multiturn-live-*.json`）分别为 17/20、16/20、16/20（详见「历史运行对照」），且三次对应的题目版本不同，**互相之间不可比**。
- 本报告只覆盖**对话链路保持能力**（追问是否接上上文、答案是否答到本轮要点），**不等价于** `eval/runner.py` 的 NL2SQL / RAG 准确率口径，两者不可换算。

### 唯一失败：mt-03 第 2 轮

- 问题：「他总共消费了多少？」（承接第 1 轮「客户 Frank Harris 是谁？」，`depends_on_context: true`）
- 期望：答案包含 `37.62`（Frank Harris 的发票总额）
- 实际答案：`查询结果：customer_id：16、customer_name：Frank Harris、company：Google Inc.、address：1600 Amphitheatre Par…`——**仍是客户档案，未涉及任何金额**
- 实际 SQL：
  ```sql
  SELECT customer_id, first_name || ' ' || last_name AS customer_name, company, address,
         city, state, country, postal_code, phone, email, support_rep_id
  FROM customer
  WHERE first_name = 'Frank' AND last_name = 'Harris'
  ORDER BY customer_id LIMIT 1000
  ```
- 接续标记：**已接上文**（`normalizer` 输出含「用户补充或修改」接缝）——即上下文**接上了**，但**接上之后答错了对象**。这正是本用例设计要区分的两类失败：不是「忘了上文」，是「接上了却没换查询对象」。

同一用例其余四轮通过，且第 3 轮「改成看发票张数」正确返回 `invoice_count：7`，说明**同类下钻在换度量被显式写成「改成X」时是能完成的**，进一步印证失败点是**追问识别**而非查询能力。

## 根因（已实测确认）

`app/nl2sql/followup.py` 的 `resolve_followup(question, query_state)` 是纯规则匹配，返回 `FollowupInstruction`（五种操作 `replace_group` / `add_group` / `average_measure` / `rank_top` / `replace_measure`）或 `None`。只有非 `None` 时，`app/orchestrator.py` 才会带上 `followup_context`，`app/nl2sql/pipeline.py` 才会跑 `validate_followup_sql` 并在失败时回灌重试。

实测该函数对下列说法**全部返回 `None`**：

| 输入 | 返回 |
|---|---|
| `他总共消费了多少？` | `None` |
| `他消费了多少` | `None` |
| `总共消费了多少` | `None` |
| `他的消费总额` | `None` |
| `那总共消费了多少` | `None` |
| `他花了多少钱` | `None` |
| `他总共消费了多少` | `None` |

即「换度量 / 换查询对象」这一类追问，只有在写成「改成看发票张数」这种**带显式替换动词**的形式时才会被 `_MEASURE_RE` 捕获；自然口语化的换度量说法**没有对应规则**，落到模型自由发挥，本轮就答回了上一轮的表。

**这不是本轮引入的问题**，也**不是** `validate_followup_sql` 的缺陷：该校验函数本身工作正常（实测「叠加维度不替换」会被 `old_dimension_retained` 拦下，「正确替换」通过），只是**根本未被调用**。

## 已知限制与下一步建议

1. **多轮覆盖率有缺口（主要限制）**：换度量 / 换查询对象类追问未识别。建议方向是给 `resolve_followup` 增补一类「度量替换」识别（例如从「消费额 / 总额 / 花了多少 / 张数 / 数量」等高频度量词反查目标列），使其与既有五类走同一套 AST 校验与回灌路径。**本轮未实施**：该模块由队友维护，属扩功能改动，需与其当前工作协调后另行提交。
2. **链路存在非确定性**：同一用例在不同运行间结果不同（mt-03 历史三次为 5/5、4/5、4/5），因此**单次 19/20 不应被当成稳定水平**。要给出可信区间需固定题目多跑若干轮，本报告未做多轮重复。
3. **样本量小**：4 条用例 × 5 轮 = 20 轮，一题失败即移动 5 个百分点，不适合做细粒度趋势判断。
4. **不覆盖准确率**：本口径只看「是否接上上文 + 是否答到本轮要点」，与 NL2SQL / RAG 的准确率、忠实度是两套独立指标。
