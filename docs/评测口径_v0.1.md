## 一、评测集格式

### 1.1 文件位置

| 文件 | 用途 | 条数 |
|---|---|---|
| `eval/cases/nl2sql.jsonl` | 基础 NL2SQL 单表 | 10（硬下限）+ 建议 15 |
| `eval/cases/rag.jsonl` | 基础 RAG 单文档 | 10（硬下限）+ 建议 15 |
| `eval/cases/robust_cases.jsonl` | 鲁棒性（口径 / 空结果 / 报错） | 建议 10 |
| `eval/cases/multi_turn.jsonl` | 多轮追问（对应多轮 5 分） | 建议 5 |

**一行一个 JSON 对象**（JSONL 格式）。文件必须能被 `uv run python -c "import json;[json.loads(l) for l in open(...)]"` 无损解析。

### 1.2 NL2SQL 用例字段

```json
{"id": "sql-001", "question": "卖出金额最高的前 5 位客户是谁？", "db": "chinook", "gold_sql": "SELECT c.CustomerId, SUM(i.Total) AS total FROM Customer c JOIN Invoice i ON i.CustomerId = c.CustomerId GROUP BY c.CustomerId ORDER BY total DESC LIMIT 5", "tags": ["单表", "聚合", "排序"]}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 全局唯一，格式 `<类型>-<三位序号>`，如 `sql-001` |
| `question` | 是 | 用户原话，**写口语**，不要写成 SQL 的翻译 |
| `db` | 是 | `chinook` / `adventureworks`（默认 `chinook`） |
| `gold_sql` | 是 | 标准答案 SQL。**评测时以它执行出的结果集为准**，不是以它的文本为准 |
| `tags` | 否 | 用于分类统计，如 `["单表"]`、`["多表", "JOIN"]` |

### 1.3 RAG 用例字段

```json
{"id": "rag-001", "question": "文档里说的报销上限是多少？", "doc": "某文档.pdf", "gold_points": ["单次报销上限 5000 元"], "forbidden_points": ["上限 10000 元"], "tags": ["事实抽取"]}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 格式 `rag-<三位序号>` |
| `question` | 是 | 用户原话 |
| `doc` | 是 | 期望命中的文档名（用于算检索命中率） |
| `gold_points` | 是 | **答案必须包含的要点**，每条一个可独立判断的短句 |
| `forbidden_points` | 否 | **出现即扣分**的错误要点（用于抓"编造"） |
| `tags` | 否 | 用于分类统计 |

> RAG 用例不写"标准答案全文"——**生成的话术可以千变万化，但要点是有限的**。
> 所以判的是"要点在不在"，不是"句子像不像"。

## 二、NL2SQL 判定口径

### 2.1 判定原则：比结果集，不比 SQL 文本

**同一个问题可以有多种写法完全不同的正确 SQL。**（JOIN 顺序、子查询 vs 关联、列别名、大小写……）
所以**绝不比对 SQL 字符串**——那样会把一大堆正确答案判成错。

**判据**：把 `gold_sql` 和系统生成的 SQL 分别在数据库上执行，**比对两个结果集**。

### 2.2 结果集比对规则

| 项 | 规则 | 理由 |
|---|---|---|
| **列顺序** | **忽略** | 列写反了但数据对，是表达差异不是错误 |
| **列名 / 别名** | **忽略** | 系统叫 `total`，标准答案叫 `revenue`，是同一列 |
| **行的顺序** | **只有在 `gold_sql` 含 `ORDER BY` 时才比对**；不含则忽略 | 没有排序要求时，数据库返回顺序本来就不确定 |
| **列的数量** | **必须一致** | 多查一列或少查一列，是实质差异 |
| **行的数量** | **必须一致** | 多一行少一行，是实质差异 |
| **整数 / 字符串** | 严格相等 | — |
| **浮点数** | **相对容差 1e-6**（见 2.3） | 浮点累加误差 |
| **NULL** | 与 NULL 相等（`NULL == NULL` 判真） | SQL 语义里 NULL 不等于 NULL，但评测要的是"两边都是空" |
| **大小写 / 前后空格** | 字符串比较时忽略首尾空格；大小写**严格** | 首尾空格是数据录入噪音，大小写在姓名/编码里有意义 |
| **日期时间** | 归一化为 ISO 8601 后比对；只到日的忽略时分秒 | 避免 `2026-09-18` vs `2026-09-18 00:00:00` 误判 |

### 2.3 浮点容差

数值比较用**相对容差**：

```
|a - b| <= 1e-6 * max(1, |a|, |b|)   →  判相等
```

**为什么用相对而不是绝对：**
- 绝对容差（比如"差 0.01 内算对"）在大数上太严：`1445400.001` vs `1445400` 差 0.001 会被判错
- 相对容差自动适配数量级：小数看百分比，大数看百分比

**已知例外——金额类字段**：如果某列是金额，且两数差异在 **1 分钱以内**也算对（覆盖 `144.54` vs `144.54000000001` 这类数据库累加误差）。

### 2.4 结果判定与"不算数"的情况

单个用例的判定只有三种结果：

| 结果 | 条件 | 计分 |
|---|---|---|
| `correct` | 两结果集按 2.2 判定一致 | 算对 |
| `wrong` | 两结果集按 2.2 判定不一致 | 算错 |
| `error` | 生成 SQL 执行报错 / 超时 / 被安全闸门拦下 | **算错**（明确不计入"不算数"） |

**超时阈值**：单条 SQL 执行超过 `SQL_TIMEOUT_SECONDS`（`.env.example` 默认 30 秒）判 `error`。

**为什么 `error` 算错而不是剔除**：剔除掉报错的题会让准确率虚高（只报对自己会做的题），
而真实系统报错就是没答出来。**评的是系统，不是系统最好的那部分。**

### 2.5 准确率公式

```
执行准确率 = correct 条数 / 总条数
```

**分母是全部用例**（含 `error`），不是"能跑的那些"。

**已知例外——`unsupported`（暂不适用）**：
如果某条用例依赖的功能**明确排在后续里程碑**（如多表 JOIN 在 M2 才做），在 M2 之前该条可标记为 `unsupported` 并从分母中剔除，
**但必须在跑分输出里单列一行说明剔除了几条、为什么**，且**对外报分时不得剔除**。
这条例外的唯一用途是开发期的进度观察，不是对外口径。

## 三、RAG 判定口径

### 3.1 检索命中率（辅助指标）

```
检索命中率 = 命中期望文档的用例数 / 总用例数
```

`doc` 字段指定的文档是否出现在检索返回的 Top-K 里（K 取 `RERANK_TOP_K`，`.env.example` 默认 5）。
**这是辅助指标，不计入 40 分**，但用来定位"是检索错了还是生成错了"。

### 3.2 答案忠实度（正式指标）

**忠实度 = 答案的每一条实质陈述都能在检索到的原文里找到依据。**

判定分两层：**规则自动判 + 人工复核**。

#### 第一层：规则自动判（全量跑）

对每条用例逐个检查 `gold_points`：

| 检查项 | 方法 | 判定 |
|---|---|---|
| 要点是否出现 | 要点中的**关键实体**（数字、专有名词、金额、日期）出现在答案里 | 命中 |
| 是否出现禁用要点 | `forbidden_points` 里的关键实体出现在答案里 | 一票否决，该条判 0 |
| 是否凭空捏造 | 答案里的数字/金额/日期，**逐个回原文检索**，找不到出处 | 计入"疑似幻觉" |

**关键实体提取是规则化的**，不靠 AI 模型：数字、百分比、带单位的值、以及 `gold_points` 里标注的名词短语。
这样同一份答案今天判和明天判结果一样。

#### 第二层：人工复核（抽样 + 全部疑似）

以下三类**必须人工看一遍**，其余抽样 20%：

1. 规则判为"疑似幻觉"的
2. 规则判"要点未命中"但答案看起来相关的
3. `forbidden_points` 触发的

**为什么不用 AI 模型当裁判：** 同一份答案，换一次模型调用可能给出不同结论——
**对外报的分数不能是"跑的那一次运气好"**。而且 10 条题的规模，人工复核的负担是可接受的。

#### 忠实度公式

```
忠实度 = 通过判定的用例数 / 总用例数
```

**单条用例"通过"的条件**（三项同时满足）：

1. `gold_points` 全部命中
2. `forbidden_points` 一条都没出现
3. 无"疑似幻觉"（含人工复核确认的情况）

### 3.3 单文档 RAG 计数分（20 分里的 10 分）

基础 RAG 的 10 分是**每题 1 分**。单题"正确"的判据：

- `gold_points` 全部命中
- `forbidden_points` 一条都没出现
- **必须带出处引用**（引用片段非空、且指向实际检索到的文档）

> 第三条是"答案可解释性"在评测里的落地——**没有引用的答案即使内容对，也不算这条通过**。
> 因为题面明确要求"给出带出处的答案"，无引用等于没完成这个功能要求。

## 四、鲁棒性用例口径

`robust_cases.jsonl` 单独一套判定，因为**它的正确答案往往不是"查出数据"**。

| 类型 | 用例形态 | 正确表现 |
|---|---|---|
| **空结果** | 问一个数据里确实没有的东西 | 明确回答"没有找到"，**不得编造**出一条记录 |
| **口径歧义** | 问题有歧义（"最近的订单"没说几天内） | 触发澄清追问，而不是猜一个 |
| **超出范围** | 问库里没有的表/字段 | 明确说"数据里没有这个信息"，不得硬造 SQL |
| **危险请求** | 要求删表 / 改数据 | **被安全闸门拦下**，明确拒绝 |

**关键区分：区分"数据里没有"和"系统坏了"。**

- 数据里确实没有 → 系统正确回答"没有" → **算对**
- 因为 SQL 报错而返回空 → **算错**

这两者在实现上都会表现为"空结果"，**必须在评测脚本里靠 `error` 标记区分**：
凡是执行报错导致的空，一律记 `error` 而非 `correct`。

## 五、跑分输出

`eval/runner.py` 跑完必须输出一份 **JSON + 一份人类可读摘要**。

### 5.1 JSON 输出结构

```json
{"run_at": "2026-09-18T14:00:00+08:00", "git_commit": "bc786e3", "db": "chinook", "metrics": {"nl2sql_exec_accuracy": 0.9, "nl2sql_correct": 9, "nl2sql_total": 10, "rag_faithfulness": 0.9, "rag_correct": 9, "rag_total": 10, "retrieval_hit_rate": 0.95}, "unsupported": {"count": 0, "ids": []}, "cases": [{"id": "sql-001", "result": "correct", "elapsed_ms": 820}]}
```

**必须带 `git_commit`** —— 分数必须能对应到某一次具体的代码状态，否则"上周 92% 这周 87%"没法排查是改坏了还是运气。

### 5.2 对外报分的三条纪律

1. **报的是 `correct / total`，不是 `correct / (total - unsupported)`**
2. **报分必须同时报用例数**（"90%" 单说没有意义，"9/10 = 90%" 才有）
3. **口径改了一定要升版本号并全员通知** —— 口径变了分数就不可以横向比

## 六、口径变更流程

评测口径**不是**冻结物，但改动必须留痕：

1. 谁发现口径有问题，在群里说：**哪个用例、现在怎么判、应该怎么判、为什么**
2. **A、B、C 三人确认**（口径一动，三个人的分数同时变）
3. 改本文件 + 在本文件末尾「变更记录」加一行
4. **版本号 +1**

> ⚠️ **改口径之前必须先重跑一遍旧口径**，把旧分数记下来。
> 否则口径一改，新旧分数不可比，调优的方向感就没了。
