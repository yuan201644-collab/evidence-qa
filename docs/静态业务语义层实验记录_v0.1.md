# 静态业务语义层实验记录 v0.1

更新日期：2026-10-02。

**结论：本轮不支持把全部静态业务规则加入正式问答提示。** 新验证题没有准确率收益，原有题集的执行匹配成绩略低，总词元用量增加25.4%。这只约束本次静态全量注入方案，不能据此否定按需查询、大库表定位或EvoOntology的完整方法。

## 实验对象与固定条件

业务语义层（semantic layer）是连接用户业务词、数据库字段与计算口径的说明层。此次只验证整理后额外注入规则是否有效。

| 项目 | 固定条件 |
|---|---|
| 当前系统组 | 原有查询流水线，保留已有表字段中文说明和生成提示 |
| 静态规则组 | 同一流水线，通过已有 `hint` 参数全量加入9条规则 |
| 模型 | 本机现有配置 `deepseek-v4.1-flash`，未更换模型或密钥 |
| 请求参数 | 温度0，单次超时60秒，HTTP重试2次，生成最多3次，输出上限16000词元 |
| 时间基准 | 2024-06-15，两组一致 |
| 数据库 | 原有Chinook，真实PostgreSQL 16.15，只读事务 |
| 题集 | 原有15题检查退步；新编16题验证口径，均在调用模型前冻结 |
| 重复 | 每组每题两轮，交替先后顺序，独立请求，不共用会话 |
| 唯一干预 | 额外业务规则；不增加工具，不调整题目或评分，不修改正式业务代码 |

标准查询与预测查询均经现有sqlglot校验；标准查询两次执行一致且非空。运行前后相关源码和完整业务数据摘要一致。模型输入不含标准查询、答案或错误查询示例。不保存模型思维链。

总词元增加 `(163132 / 130064 - 1) × 100% = 25.4%`。这是接口返回的用量，不是费用；有输入缓存命中，不据此推算账单。原有题耗时中位数2246.5/2111.3毫秒，新题1876.4/2085.5毫秒，方向不一致，不宣称加速或减速。

逐轮表现：原有题第一轮当前系统15/15、规则组14/15；第二轮两组均14/15。新增题每组每轮均16/16。

## 变化题目的复核

1. `nl2sql-h-03`：规则组两轮都把员工姓名拆为名、姓两列，原判定期望一个姓名列，因此从标准3列变成4列而失败。员工范围、金额、排序口径一致。保持已有判据，不把这个输出形式差异描述成业务计算错误，也不依据这两次失败断言规则必然有害。
2. `nl2sql-m-01`：第二轮当前系统列出了全部8名员工，标准结果是3名客服代表；规则组限制了客服职位，判定通过。这次改善没有在第一轮构成差异，不能称为稳定提升。
3. 新编题没有“失败转成功”或“成功转失败”。`sem-14`国家口径、`sem-15`标准价与成交价、`sem-16`购买数量与明细计数在此数据上无法区分所列错误查询；单独标记，不作为已验证该能力的证据。

8组预测已经用现有 `eval/runner.py` 的读取与评分逻辑再次执行，全部与实验统计一致；标准答案执行自检15/15。这是判定器检查，不是模型成绩。

## 数据库恢复与探索记录

Docker最初因安装注册表项缺失启动失败，先用仓库已有SQLite副本完成探索。日期截断和时间字面量转换会干扰执行；恢复原库后，完整数据检查还发现少量文字差异，包括艺术家名称中的字符和客户城市的尾空格。严格同数据重放检查因此拒绝继续。

随后使用相同冻结规则、题集和模型配置，在真实PostgreSQL重新跑完整两组两轮。**最终结论只使用PostgreSQL运行，不合并SQLite运行成绩。** 本轮未改动已有SQLite导入脚本；两份数据不能仅凭表行数相同就视为完全相同。

## 结论边界与后续选项

- 本轮仅测底层查询流水线，不包含完整编排、前置要素识别、多轮澄清或文档检索。
- 新题与规则由同一执行者整理，未经独立盲审；新题常直接说明正确统计口径，且当前模型接近满分，无法验证陌生业务词上的收益。
- 针对初赛自然语言转查询执行准确率10分，本轮没有新增可举证收益。未验证中级任务4在数十张表中的定位，因此不能据此申报该项5分。
- 建议选项一：保留这9条规则作为可审阅的语义资产，暂不全量注入主链路；成本最低，符合本轮结果。
- 建议选项二：有真实语义错题或大库表定位失败后，再验证局部规则或按需查询；需另定未参与修改的验证题，不能把本轮题集继续称作未见测试集。
- 自动补丁和自演化不因本轮实验自动启动；需单独讨论收益、时间与任务归属。

以上是实验建议，不调整团队分工、契约或已定中级任务组合。
