# 契约设计 v0.5：三类问答统一事实记录

日期：2026-10-15
状态：实现分支中的候选契约；尚未通过测试、真实接口验收或 B/C 复核。
基于：[`契约设计_v0.4.md`](契约设计_v0.4.md) 的可选 `AskResponse.fact_review` 扩展。

## 1. 目的与边界

问数、文档问答和跨源问答共用一套请求级事实计划、证据账本及事实卡结构；各路径仍调用原有 SQL、RAG 或跨源处理器，不强行把单源问题改造成跨源问题。问数 / 文档路径当前投影的是实际执行、检索和引用定位记录，不代表答案语义已经逐项核实；缺少明确关系核验器的普通跨源路径将关系标为未执行、事实不足。

本版本不改变默认路由、SQL 生成与校验、RAG 检索和生成、跨源业务判定、登录隔离或多轮上下文。不接入 KAG；KAG 深度检索仍由支线实现者负责。

## 2. 请求协商与兼容

客户端以 `X-AskData-Fact-Review: 2` 请求 v2 扩展：

- `/api/ask` 与 `/api/ask/stream` 的最终响应使用同一 `fact_review` 形状；流式阶段事件不提前声称核验完成。
- 未带该头时，HTTP 响应不含 `fact_review`，并从 `refs` 及 `trace[].hit` 中移除 v2 的 SQL 查询结果定位字段，保持旧响应键与引用字段集合。
- 不支持的头值返回 HTTP 400。
- 事实账本与来源检查在编排请求中生成；该请求头只控制 v2 字段是否序列化，不控制执行路径。
- 若旧后端忽略未知请求头且不返回 `fact_review`，新前端保持原回答布局，不显示空事实卡。

该策略保护未协商的旧调用方，不证明任何外部严格客户端可消费 v2；需要读取 v2 的客户端必须接受新增枚举和可选 SQL 引用字段。

## 3. 字段

```json
{
  "schema_version": "2",
  "coverage": "structured_query",
  "verification_mode": "source_specific",
  "verification_scope": "query_execution_and_evidence",
  "scope_note": "记录查询执行与引用定位；尚未独立证明查询结果满足自然语言意图。",
  "items": [
    {
      "fact_id": "structured_query_target",
      "label": "本次数据查询目标",
      "summary": "指标：发票数量；时间：2023 年。",
      "status": "candidate",
      "execution_status": "completed",
      "evidence_link_status": "complete",
      "checks": [
        {"code": "readonly_sql_validation", "result": "passed"},
        {"code": "query_execution", "result": "passed"},
        {"code": "semantic_fact_support", "result": "not_run"}
      ],
      "evidence_ref_indices": [0],
      "reason_code": "source_fact_not_independently_verified",
      "reason": "本路线记录了实际查询/检索与证据定位，但未对答案语义作独立的逐项事实判定。"
    }
  ]
}
```

`FactReview` 的约束如下：

| 字段 | 取值与含义 |
|---|---|
| `schema_version` | 固定为字符串 `"2"`。 |
| `coverage` | `structured_query`、`document_qa`、`cross_source_work_order_sla` 或 `cross_source_unplanned`。 |
| `verification_mode` | `strict`、`ablation` 或 `source_specific`。`source_specific` 只表示来源执行记录，不得显示成严格事实级通过。 |
| `verification_scope` | `query_execution_and_evidence`、`document_retrieval_and_citation`、`fact_dependencies_and_business_checks` 或 `cross_source_execution_only`。 |
| `items[].status` | `candidate`、`supported`、`contradicted`、`insufficient`、`ambiguous`。单源来源记录默认是 `candidate`；不能因查询成功、检索命中或有引用而改为 `supported`。 |
| `execution_status` | `completed`、`not_run`、`failed`。`completed` 表示相应处理器正常返回，不表示 SQL 成功或事实成立。 |
| `evidence_link_status` | `complete`、`partial`、`unavailable`；必须按来源身份映射到同一响应 `refs`。 |
| `checks[].result` | `passed`、`failed`、`unknown`、`not_run`；只接受从结构化 trace / 核验器结果读取的实际结果。 |
| `evidence_ref_indices` | 0-based 最终 `refs` 下标，在引用选定、排序、去重后计算；`AskResponse` 会拒绝重复或越界索引。 |
| `reason_code` / `reason` | 固定允许清单；不透传 SQL、原始异常、提示词、密钥或通用 `FactRecord.value`。 |

### SQL 查询结果定位

`SqlRef.result_id` 是本次查询结果级的随机定位标识，仅在 v2 协商响应中出现；它不是数据库行主键，不能填入或替代 `row_pk`。有完整真实主键时仍使用 `row_pk`；无行主键但有 `result_id` 时，`collect_refs` 与 `Orchestrator._dedup_refs` 必须把结果标识纳入去重键，避免把不同查询的聚合证据合并。无两类定位符时仍沿用旧表/字段粒度，但这种引用不能用于精确事实证据关联。索引需唯一对应最终引用，不能按片段相似度猜配。

## 4. 三类路径如何使用同一结构

| 问题类型 | 进入原有路径 | 统一账本记录 | 当前不宣称 |
|---|---|---|---|
| 问数 | 原 NL2SQL、字段定位、关联规划、校验、修复与只读执行 | 从 QueryIntent 形成查询目标；记录校验、语义关联结果、执行终态、结果完整性及最终引用 | 仅凭 SQL 成功证明答案语义正确或数据完整 |
| 文档问答 | 原 RAG 解析、切片、检索、重排、多跳、生成与原文引用 | 记录文档回答目标、检索/生成终态与引用定位；多跳检索统计汇总全部检索轮次 | 仅凭召回命中、引用编号或生成成功证明原文支持答案每项事实 |
| 跨源 | 既有工单—合同事实计划继续做严格依赖与业务检查；其他跨源路由保持原样 | 严格计划投影其结构化结果；无关系检查器的组合路由记录各来源候选证据，并把关系核验标为 `not_run` / `insufficient` | 把 SQL 与文档并列命中直接说成关联已核实 |

任何事实摘要只由安全白名单字段确定性生成。答案原文不作为状态推断来源。

## 5. 严格通过展示条件

只有同时满足以下条件，前端才可显示“事实已核验 · 证据完整”：

1. `verification_mode="strict"`；
2. `execution_status="completed"`；
3. `status="supported"`；
4. `evidence_link_status="complete"` 且至少有一个有效 `evidence_ref_indices`。

`source_specific` 路径不满足第 1 条，界面用“事实处理与证据记录”等中性标题；答案正文不会获得逐句“已核验”标签。缺少 `fact_review` 时继续显示旧答案、引用和处理详情。
