# 架构叙事改进思路 v0.2

更新日期：2026-09-27  
状态：阶段A设计稿；本文描述的新增跨源任务/事实机制尚未实现，需团队确认场景后进入阶段B。

## 1. 核心判断

当前方案已有路由、SQL、文档检索、多跳检索、引用和工具调用记录等技术模块，但仅把它们画成一条长流水线，仍容易被理解为技术堆叠。叙事应聚焦一个可检验的问题：**系统怎样把一个复合问题拆成可核验的待答事实，安全地取得跨来源证据，并在证据不足或冲突时有界停止，而不是把候选检索结果直接拼成结论。**

“少一个模块就无法工作”不是创新性证据。较可信的创新论证至少要同时交代：具体机制改变了什么、针对哪类失败、与同条件基线相比改善了什么、付出什么时延/调用/维护代价，以及哪些情形不适用。此处是架构论证建议，不是赛事给定的创新评分规则。

建议叙事主线：

> 复合问题 → 明确待回答事实及依赖 → 按事实选择数据源 → 验证对象对应和统计口径 → 将每个事实绑定到可复核证据 → 形成完整、限定或拒答的答案；失败只定向补查并受预算约束。

该主线是目标架构，不代表现有系统已具备完整的跨源对象映射、事实级证据绑定或冲突裁决能力。

## 2. 架构表达：不同视图回答不同问题

原五层结构保留为系统组成/部署视图：交互层、编排层、工具层、数据层、模型层。它回答“组件放在哪里”，不单独承担创新叙事。另用三张流程视图说明运行机制：

1. 数据准备：文档/数据库元数据如何变成带来源定位的索引与实体候选。
2. 在线问答：事实依赖如何驱动工具选择、证据关联、校验与有界失败。
3. 离线评测：如何冻结数据与配置、运行真实系统、分开度量答案和证据，再按错误归因改进。

单次任务计划可以是有向无环图（DAG），表示依赖关系；包含重试、澄清和停止的完整运行流程存在回边，不能称为无环图。无依赖的事实可并行，但仅在并行能降低端到端时间且不会破坏共享预算/状态时采用。简单单源问答应走短路径，不为展示架构强制增加规划或多次模型调用。

## 3. 最小跨源核验机制（建议，待定场景）

建议把“跨源融合”定义为四个显式步骤，而不是同时调用 SQL 与 RAG：

### 3.1 对象对应

每个候选事实带业务对象类型、来源侧标识、标准对象标识、映射依据和有效时间。只有经明确外键/映射表、稳定业务编号或人工审核映射确认的对象关系，才可作为跨源桥接。姓名、标题、地址等字符串相同只产生候选，不足以证明同一对象。多对一、歧义别名、过期映射应分别记录，不静默选一个。

### 3.2 口径对齐

比较事实之前先对齐指标定义、事件类型、时间范围/时区、单位、聚合粒度、状态过滤条件和有效期。例如“响应时间”“到场时间”“修复时间”不是同一指标；“合同有效”还需判断查询日期与条款生效期。无法对齐时应限定结论或请求澄清，不能靠自然语言近似替换。

### 3.3 事实与证据关联

对最终答案拆分的每项主张分别保存值、标准对象、口径、来源定位、取数条件和校验状态。检索命中只是候选证据，工具调用记录也不等于最终引用。每个被回答事实应能追溯到一条或多条实际来源；引用覆盖完整度与答案文字正确性分别评估。

SQL 证据至少要能复核查询涉及的表、字段、过滤/时间条件、聚合定义与实际结果。聚合结果通常没有单行主键，不能为了填引用字段而伪造 `row_pk`；应记录查询上下文和结果行/列定位。文档证据记录文档标识、页码/章节/片段偏移等可得坐标。

### 3.4 有界失败

缺少必需桥接证据时，只补查相关前置任务；信息歧义时澄清；单位或时间口径冲突时对齐或停止；来源冲突时并列说明，除非有明确权威规则，否则不自行裁决；总预算或尝试上限耗尽时保留已确认部分并明确未确认部分。重试次数、总时限、模型调用预算是工程配置，需基线测量后由团队确认，不能写成赛题要求。

## 4. 一个候选贯穿示例

候选场景（尚待团队选择和核实数据授权/数据关系）：查询某设备在某日期的维修工单时长，并判断其是否满足适用合同中的修复时限。

1. 待答事实A：工单对应的设备及修复完成时间；从结构化库读取，保留工单号、设备业务标识、起止事件定义、过滤条件和时间范围。
2. 桥接事实B：工单设备与合同对象的对应关系；仅使用有来源的标识映射和有效期，不凭设备名称相似直接关联。
3. 待答事实C：该合同在查询日期适用的修复时限；从条款检索原文，记录文档/页码/章节和条款有效期。
4. 校验事实D：将A与C的口径、单位、起止事件和时间有效性对齐，再执行确定性比较；无法对齐则不输出“达标/超时”的确定结论。

示例用于说明机制，并非宣称当前数据中已经存在设备—工单—合同对应关系或该端到端能力。

## 5. 当前能力和边界

- 现有 `app/contracts.py` 的 `TraceStep`记录工具调用事实，`hit`表达工具命中来源；`AskResponse.refs`目前依据 trace 命中汇总。它们不是“答案中每个事实由哪些证据支持”的现成关系模型。
- 现有多跳检索是独立检索链路；不能据此宣称任务7（目录结构识别）已完成，也不能将多跳RAG等同于任务5（多表关联查询）。任务5对应结构化多表关联；任务7对应文档目录结构识别，需分别按题面验收。
- `GRAPH_BACKEND=kag` 当前仍注册模拟图关系工具，不是真实KAG接入。KAG只作为候选补充能力。
- 当前公共契约对全量命中汇总与编排器最终引用筛选存在语义需核对之处。阶段A只记录问题与适配选项，不改契约。
- 模型提出候选计划或候选实体，代码负责权限校验、只读SQL校验、工具执行和预算控制；证据不足时模型生成不能替代证据。

## 7. 赛事任务与评分叙事

内部确定的中级任务组合为1、3、4、5、7；初赛按项目指令口径，攻克1、4、7即可达到中级任务15分上限，仍应推进其余项以准备决赛。不能把任务7表述成多跳RAG：任务7是目录结构识别；任务5是多表关联。初赛相关评价还包括RAG基础与忠实度、可解释性、效率等项目，分别呈现引用证据、结构化调用事实和实测耗时。具体分值和档位以项目已收录题面/评分材料为准，不据架构图推测得分，也不存在独立的“创新架构”初赛分值。

## 8. 既定约束、建议和待确认

**既定约束**：五层系统组成视图保留；自研轻量编排；PostgreSQL、sqlglot只读校验；代码埋点而非思维链解释；未经同步不改单人公共契约；中级任务既定组合；KAG模拟适配不得冒充真实接入。

**建议方向**：任务/事实内部模型；对象映射有效期；口径对齐字段；逐事实证据关系；有界定向补查；把答案正确、事实支持、证据完整和时延分别评测。

**需团队确认后才能进入阶段B**：贯穿业务场景与数据授权；对象ID对应依据；业务指标和时间口径；事实模型放置于何处及现有前端消费方式；是否需要公共契约变更；重试和时限预算；评测题集与盲审安排。未确认前不新增业务数据/代码、不改默认后端或工作任务书。
