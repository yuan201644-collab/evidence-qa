> 状态：**阶段 0（数据采集与抽取）已完成**，阶段 1-6 待执行。

## 一、为什么要做这件事

### 1.1 起因

现有评测题集的语料是**自制的**（`data/corpus/`，15 份，由 `data/corpus/tools/build_corpus.py` 生成）。自制语料的理由写在生成器开头：版权可控、难点可控、可复现。但这带来两个问题：

1. **规模不足以支撑"系统测试与性能评估"**——15 份文档合计只有 15 页、7,996 字符，每份都是 1 页；
2. **赛题明确要求多规模对比**——题面 `docs/reference/赛题八_题面原文.txt:359-361` 原文：「②在**至少两种不同数据规模**下（如小规模 1 千行、中规模 1 万行）的实测或预估响应性能对比」。

老师给的口径（用户转述）：「测试用例自己提供即可，**数据库表和文档用例的规模（数据记录数/文档页数等）、复杂度（字段数、数据类型种类、文档中包含不同要素的类型等）和数量，要在《技术实现说明书》里的【系统测试与性能评估】章节描述**。」

### 1.2 决策

**已做的部分不删，另起规模数据。** 原有 15 份自制语料 + Chinook 的 74 道题保留，定位为「基础能力展示」；新建一套真实业务库，定位为「规模与跨源能力展示」。两套并存，报告中分别登记。

## 二、方向选型

### 2.1 三个候选方向

| 方向 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| A 政务与公共服务 | 政府公告属《著作权法》第五条排除项，版权风险最低；跨源结构天然；规模最好做 | 主题偏行政，与"金融/政务/工业"赛道方向中政务吻合 | **选为主** |
| B 金融监管与信息披露 | 年报"表格+正文"是跨源最佳素材 | 真实年报体积大、清洗成本高 | 选为辅（后续可选） |
| C 工业与设备运维 | 与现有语料连续 | 国标付费、版权风险高、缺结构化字段 | 不选 |

**用户决策**：「方向定政务 + 金融认可」（m04491），主题定为**政府采购监管**（方案甲）。

### 2.2 为什么是政府采购监管

1. **数据全真实且可公开获取**——中国政府采购网（www.ccgp.gov.cn）无登录、无验证码、无反爬；
2. **天然同源**——采购项目在"招标公告 → 更正公告 → 中标公告 → 成交公告 → 终止公告"之间用**同一个项目编号**串联，跨源键现成；
3. **对应赛题核心要求**——题面 `:92` 要求「准确识别问题所涉及的数据来源，是在结构化数据库的哪张表、哪个字段，还是在哪个知识库文档的哪一章节」；`:96-97` 的官方例子是「先从数据库找出冠军是谁，再去文档库检索他的经验分享」，结构完全一致。

## 四、字段抽取：五次迭代的教训

公告正文有**两种结构**，这是整个抽取过程中最关键、也踩坑最多的一点。

### 4.1 两种正文结构

**A 型（表格式）**——标签行与值行分离，中间可能夹空行，**字段可能为空值**：

```
采购项目名称
榆林高新十幼校园维修及设备购置项目

品目

采购单位
榆林高新区第十幼儿园
总成交金额
￥38.360100 万元（人民币）
```

**B 型（行内式，占多数）**——标签与值在同一行：

```
供应商名称：重药控股(大连)有限公司
供应商地址：辽宁省大连市甘井子区大连市甘井子区怡华园6-3号
中标（成交）金额：9,429,800（元）
评审总得分：88.46（分）
```

### 4.2 迭代记录

| 版本 | 做法 | 结果 | 教训 |
|---|---|---|---|
| v1 | 假设「标签:值」同行 | 表格型全失效；award 抽出「保证金 500 元」；budget 覆盖率 0.2% | 单一结构假设在真实数据上一定失败 |
| v2 | 按表头行 + 偏移取值 | supplier 42.2%，但抽出的是「供应商地址：xxx」 | 表头子串匹配会同时命中名称列与地址列 |
| v3 | 加列序切分 + 地址/公司名互斥 | 疑似地址 0 个，但 supplier 抽成「中标（成交）金额：645.8000000（万元）」 | 修一个坑掉进另一个坑 |
| v4 | 保留空行做「标签→下一非空行」映射，并判「下一非空行本身是标签 ⇒ 本字段为空」 | **金额全对**（`￥645.800000 万元` → 6,458,000.00）；budget 49.3%、award 33.3%；但 supplier 仍带前缀、way 0% | 只做 A 型结构只能吃一半数据 |
| v5 | **同时支持 A + B 两种结构**，inline 优先 | project_id 97.2%、buyer/agency/region 100%、way 21.6% | 结构识别对了，但字段仍有缺 |
| v6 | 补抽采购方式、供应商兜底、包组编号 | way 81.6%、project_id 100%；但品目明细只抽出 332 行且**全是「货物品牌」「服务范围」这类列名本身** | 表头被当成了数据 |
| **v7** | **识别「表头行块 = 数据行块」的列序对齐** | 抽出 **856 行真实品目明细**，样本全部为真标的 | 见下 |

### 4.3 v7 的关键发现

「主要标的信息」的内在结构是——**表头行数 == 数据行数 == 列数**：

```
序号 / 供应商名称 / 货物名称 / 货物品牌 / 货物型号 / 货物数量 / 货物单价(元)   ← 表头：7 行
1    / 上海北鼎…  / 同济大学…  / 上海崧坤…    / 定制    / 1套     / 6,458,000  ← 数据：7 行
```

v6 失败的原因是把这 7 行表头当成 7 条独立的「标签:值」，于是 `name` 字段取到了「货物品牌」。

**v7 的正确做法**：先数连续多少行命中列名白名单，得到宽度 w；**再取紧随其后的 w 行**，按位置逐列填值。抽取结果样本：

```
同济大学四平数据中心机房设备      | 上海崧坤，施耐德…  | 数量=1 套 | 单价=6,458,000
声学多普勒流速剖面仪              | 海南奥深科技…      | 数量=4 套 | 单价=448,800
X射线吸收谱仪                     | 安徽吸收谱         | 数量=1 台 | 单价=2,960,000
```

**残留列名 0 条。**

### 4.4 v7 的边界（必须如实记录）

| 项 | 数值 |
|---|---|
| 无「主要标的信息」区块的公告 | **2,007 份（73.2%）** |
| 能抽出表头式明细的公告 | 680 份 |
| 能抽出**行内式**明细的公告 | 36 份（服务类，如「分项二：牛津国际法数据库」） |
| 区块存在但抽不出 | 19 份 |
| **品目明细总行数** | **856 行** |

**这个数字曾被误报为 5,294 行**——那是对正文中孤立数字行的粗估，不是真实抽取结果。**以 856 行为准。**

### 5.1 project_id 脏值：试了三版清洗，结论是「不清洗」

`projects.project_id` 直接取自「项目编号」的匹配串原文，因此不干净：875 条含中文、
507 条是「X（招标文件编号：X）」的冗余形式、330 条超过 40 字符，另有「项目联系方式：」
「详见招标公告」这类明显不是编号的值。

直觉上应该清洗。**实测三版方案，结论相反 —— 清洗会让跨公告聚合变差。**

衡量口径不是"改写了多少条"，而是"能否把同一采购项目的多条公告可靠地聚到一起"。
用「同一 project_id 下 ≥2 条公告的组数」与「这些组内项目名是否一致」两个信号交叉验证：

| 方案 | 有编号项目 | 编号为空 | ≥2 条公告的组 | 组内项目名一致 | 一致率 |
|---|---|---|---|---|---|
| **不清洗（现采用）** | 2,659 | 0 | **70** | **70** | **100.0%** |
| v1 剥括注 + 不含中文才保留 | 2,250 | 409 | 83 | 73 | 88.0% |
| v2 剥括注 + 脏值判据收窄 + 拼接分标号 | 2,571 | 88 | 88 | 78 | 88.6% |

三版清洗都是**组数上升、一致率下降**：多出来的组里约 10 组是**错误合并** ——
把本属不同标段的公告（如 `0686-2611CC204845Z` 的 /01、/03、/04 三个分标，
以及 `OITC-G260571584/清采招第20260315号` 的多种写法）清成了同一个编号。

还有一版（v3「取最长拉丁编号候选」）更糟：`中大招（货）[2026]232号`、`泉建招字[2026]065号`
都被清成 `2026`，**64 个项目撞成同一个编号**，直接废弃。

**结论：不写库，保持原样。** 理由：

1. 不清洗的 project_id 虽然难看，但**原样保留了源站的区分度**，聚合是可靠的。
2. 数据的真实缺陷是"同一项目在不同公告里写法不同"，清洗只能靠猜，而猜错会把两个项目并成一个 ——
   比不聚合更严重，因为它会产生看似合理实则错误的答案。
3. 对题集的影响可接受：**70 个多公告项目足以支撑跨源题**（规划中的跨源融合 15 题），
   做不到的只是"编号变体自动归并"，而这不是赛题要考察的能力。

四版清洗方案的量化记录见 `agent_temp/pb/probe_ccgp/project_id_scheme_compare.json`
与 `project_id_clean_plan{,_v2,_v3}.json`。

**对外报告口径**：

> 结构化数据 **1.27 万行**（9 张表），另有 2,742 份公告原文作为知识库文档与跨源桥，
> 以及 26 条结构化的法规可判定条款。

## 六、知识库文档设计（三层结构）

### 6.1 为什么分三层

### 6.2 规则层实测

**已抓 24 份**：核心法规 7 份（26 页）+ 配套通知 17 份（22 页）。

| 法规 | 页数 | 用途 |
|---|---|---|
| 财政部令第 110 号 政府采购框架协议采购方式管理暂行办法 | 5 | 框架协议适用 |
| 财政部令第 101 号 政府采购信息发布管理办法 | 1 | 公告发布规范 |
| 财政部令第 94 号 政府采购质疑和投诉办法 | 3 | 质疑投诉流程 |
| 财政部令第 87 号 政府采购货物和服务招标投标管理办法 | 7 | **公开招标数额标准、程序** |
| 财政部令第 74 号 政府采购非招标采购方式管理办法 | 5 | **竞争性谈判/询价/单一来源适用情形** |
| 财政部令第 61 号 / 第 31 号 政府采购代理机构资格认定办法 | 各 3 | 代理机构资质 |

**关键判断**：法规原文**天然短**（每部 1-7 页），但**句句是规则**；而财政部文告**天然长**（每份 30-84 页）却**密度极低**——15 份 780 页里"政府采购"仅出现 **201 次**，平均 0.26 次/页；且「竞争性磋商/竞争性谈判/单一来源/询价/框架协议」各仅 1-2 次。

> **结论：规则层必须靠专门法规，不能靠文告。** 文告只作背景存档。

### 6.3 项目层向量化抽样方案（200 份）

**不做全量**，理由：

1. 2,742 份里大量是同一项目的不同阶段，同一句"项目名称：xxx"重复十几次，全量向量化会让检索结果互相挤占；
2. 切完约 1 万片，bge-m3 编码要数小时，而评测用不到；
3. **向量化范围应按"能不能出题"定，不是按"文件有多少"定。**

**分层抽样（每份都对得上一类可出题场景）**：

| 挑选标准 | 数量 | 可出的题 |
|---|---|---|
| 有「主要标的信息」的公告 | 80 | "某项目买了几台什么设备、单价多少"（需库+文档对齐） |
| 完整采购链项目（招标+更正+中标） | 40 | "这个项目改过几次、最终谁中标"（跨公告） |
| 中标金额异常（<1 万 或 >5000 万） | 30 | "异常低价如何处理"（对应《异常低价通知》） |
| 覆盖 31 个省级行政区 | 31 | "某省采购集中在哪些领域" |
| 跨期补充 | 19 | 时间维度 |
| **合计** | **200** | |

### 6.4 规则结构化（新增第 11 张表 `regulation_rules`）

规则层只有 48 页，但"合规判断"需要的是**数值比对**，不是"检索到就引用"。因此把核心条文抽成结构化规则表：

| 字段 | 含义 |
|---|---|
| `rule_id` | 规则编号 |
| `regulation` / `article` | 法规名 / 条号 |
| `condition` | 适用条件（对应数据库字段） |
| `threshold` | 阈值 |
| `conclusion` | 结论 |
| `source_snippet` | **原文片段，用于溯源** |

示例：

| rule_id | regulation | article | condition | threshold | conclusion |
|---|---|---|---|---|---|
| R001 | 87号令 | 第五条 | procurement_way=公开招标 | 2,000,000 | 达到即须公开招标 |
| R002 | 74号令 | 第三条 | procurement_way=竞争性谈判 | — | 适用情形：技术复杂/时间紧迫 |

> **必须标注**：25-30 条规则为**人工从法规原文整理**，报告里不得写成自动抽取。

### 6.5 跨源桥

`documents` 表同时挂 `project_id` 与 `source_url`：

```
数据库 projects.project_id  ←→  documents.project_id  ←→  documents.source_url（公告原文）
```

这样"数据库里的项目编号"与"文档里的项目名称"通过同一张桥表对上，对应赛题 `:92`。

## 九、必须提前说明的判断

1. **分数可能比现在低。** Chinook 15 题当前 73.33%；换到 10 张表、1.7 万行的新库，Schema Linking 难度上升，可能掉到 60% 左右。**不为好看调参，如实报。**
2. **题集是新的一套，与现有 74 题并存。** 报告写"基础能力（Chinook，74 题）+ 规模与跨源能力（政采库，75 题）"，两套都报。
3. **规则层是人工标注。** 25-30 条规则为人工整理，报告必须标注。
4. **样本时间跨度只有 10 天。** 政采网不保留历史归档，无法长出跨年度数据；若需跨年分析须另找有归档的省平台（浙江/广东，需逆向 JSON 接口）。
5. **品目明细只有 856 行。** 73% 的公告没有「主要标的信息」区块，这是源站公告体例决定的，不是抽取能力不足。
