## 1. 结论与适用范围

- 已在 **`ict-db`（PostgreSQL 16.9 + pgvector，`127.0.0.1:5432`，库 `chinook`）** 内建成三档同构规模表，
  位于**独立 schema `scale`**：`scale.sales_scale_1000` / `sales_scale_10000` / `sales_scale_100000`，
  行数分别为 **1000 / 10000 / 100000**（题面 1 千 / 1 万 / 10 万）。
- 三档**表结构完全相同**、日期区间与取值分布**刻意对齐**，使"同一逻辑查询在不同规模下"具备可比性；
  数据的确定性由内容 md5 锁定，可在任意机器复现（见第 3 节）。
- 本表只用于**效率轴**（系统效率 5 分），不参与任何质量分；不接入 RAG 检索链路。

## 2. 为什么放在独立 schema：不改任何既有断言

题面口径（丙）为"另建规模表、不碰 Chinook 11 表"。落地时必须解决一个冲突：

- `infra/scripts/verify_infra.py` 的「chinook 基表数」断言（`CHINOOK_EXPECT["tables"] = 11`）
  查的是 **`public` schema 下的全部基表**（`relkind='r' AND nspname='public'`）。
  规模表若落在 `public`，会把 11 顶成 **12 → 验收脚本直接 FAIL**。
- 另一条「chinook 字段总数 = 64」查 `information_schema.columns WHERE table_schema = 'public'`，同样会被顶破。

**处置：规模表置入独立 schema `scale`。** 这样：

| 断言 | 是否需改动 |
|---|---|
| `verify_infra.py`「chinook 基表数 = 11」 | **不需要**（仍数 `public`，实测 11） |
| `verify_infra.py`「chinook 字段总数 = 64」 | **不需要**（仍数 `public`） |
| `healthcheck/chinook.sql`「track = 3503」 | **不需要**（未碰 track） |
| `schema_meta.json`（chinook 部分） | **不需要**（未登记 scale 表） |

> 即："选口径丙后验收断言不用改"这一结论**成立**，但成立的前提是规模表**不落 `public`**。

实测（本机）：`verify_infra.py` → **通过 21 项，失败 0 项**；`public` 基表数实测 **11**。

另与 B 的做法一致：B 的规模实验同样使用独立 `rag_scale_*` schema，未向生产 `public` 混入规模样本。

## 3. 数据基座

生成器：**`infra/scripts/seed_scale_sales.py`**（新增，独立脚本；不改 `build_corpus.py`、不改 `infra/initdb/`）。

### 3.1 表结构（三档相同）

```sql
CREATE TABLE scale.sales_scale_<N> (
    sale_id    BIGINT         PRIMARY KEY,
    sale_date  DATE           NOT NULL,
    region     TEXT           NOT NULL,
    product_id INTEGER        NOT NULL,
    quantity   INTEGER        NOT NULL,
    unit_price NUMERIC(10, 2) NOT NULL,
    amount     NUMERIC(12, 2) NOT NULL
);
CREATE INDEX sales_scale_<N>_sale_date_idx ON scale.sales_scale_<N> (sale_date);
```

| 列 | 语义 | 生成规则（确定性） |
|---|---|---|
| `sale_id` | 订单主键 | `g`（1..N） |
| `sale_date` | 销售日期 | `2021-01-01 + mod(g*1826/N, 1826)`，铺满 2021-01-01~2025-12-31 |
| `region` | 销售大区 | 华东/华北/华南/西南/东北，`mod(g,5)` 轮转 |
| `product_id` | 商品编号 | `mod(g,100)+1`（1..100） |
| `quantity` | 数量 | `mod(g,20)+1`（1..20） |
| `unit_price` | 单价（元） | `(mod(g*37,90000)+1000)/100`（10.00~909.99） |
| `amount` | 金额（元） | `quantity * unit_price` |

### 3.2 隔离性、幂等与确定性

- **隔离**：只 `CREATE SCHEMA scale` 与自建表，**不 DROP 任何既有对象**，不碰 Chinook 的 11 张表。
- **幂等**：`DROP TABLE IF EXISTS → CREATE → INSERT`，重复执行结果恒同。
- **确定性**：全部取值由 `generate_series` 序号纯算术派生，**不含 `random()` / `now()`**；
  同一 `--rows` 在任意机器上得到逐字节相同的数据（内容 md5 可跨机复现）。
  复跑三遍，三档内容 md5 三次完全一致。

## 4. 计时方法与固定查询集（待执行）

口径照 [`docs/RAG规模效率实测_20261003.md`](RAG规模效率实测_20261003.md)，保持一致以便横向对照：

| 项 | 口径 |
|---|---|
| 轮次 | **三轮**；每轮三档 |
| 统计 | 每轮每档算 p50 / p95（线性插值）/ max，三轮对各统计量取**中位数**，**另列范围**；不把 30 个样本混合成一轮 |
| 分段 | **冷索引**与**端到端**分开计时，不做相减推算 |
| 缓存 | **每轮之间必须重启服务或清缓存**（否则第 2/3 次命中进程内缓存，数字不可比） |
| 查询 | 固定 **10 条，三档相同**（见下） |
| 异常 | 异常运行单独留档，**不纳入统计** |
| 记录 | 机器信息、代码版本、`git_dirty` 一并记录 |

**固定查询集（10 条，三档同用；表名 `scale.sales_scale_<N>` 按档位替换）**

1. 全表行数：`SELECT count(*) FROM <t>`
2. 各大区行数：`SELECT region, count(*) FROM <t> GROUP BY region ORDER BY region`
3. 各大区金额合计（降序）
4. 指定年份行数（`sale_date` 过滤）
5. 指定年份金额合计
6. 指定大区 + 指定年份的金额合计（复合过滤）
7. 商品 Top-10 金额（分组 + 排序 + LIMIT）
8. 按月聚合金额（`date_trunc('month', sale_date)`）
9. 平均单价、最大/最小单价
10. 金额降序 Top-100（排序代价）

> 上述查询在三档上**语义完全一致**，仅数据量不同 —— 这是"多规模性能对比"成立的前提。
> 由于日期区间与取值分布已对齐（第 3 节），同一查询在三档上都有结果，不会出现"小档无数据"的伪差异。

## 6. 异常、限制与后续

1. **本文件不含性能结论**：数据与口径已就绪，但计时尚未执行；任何秒数都须待实测填入，不得推算。
2. **绝对耗时不可外推为服务承诺**：本轮未记录操作系统级后台负载；端到端数字还受 LLM 网络波动影响。
3. **规模对齐的取舍**：`sale_date` 按行序均匀铺满而非真实增长分布，好处是三档查询可比；
   代价是它不是一份"业务真实"的销售流水，不能用于质量评测。
4. **待 A 确认**：`schema_meta.json` 登记三张表时，`row_count` 取各表真实行数（已与实际一致），
   无"同表多档"冲突；若 A 改用"单表反复重灌"的方案，则需重新评估该冲突。
