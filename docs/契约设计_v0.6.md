# 契约设计 v0.6：可选 KAG 深度检索

日期：2026-10-15
状态：接入支线候选契约；真实语料建库和端到端联调完成前，不作为已验收能力。
基于：[`契约设计_v0.5.md`](契约设计_v0.5.md)。事实账本、引用索引和其他响应字段沿用 v0.5。

## 1. 目的与边界

项目 RAG 仍是默认文档检索方式。用户可手动选择深度检索，让 KAG 补充候选原文；项目随后统一做来源映射、去重、排序、答案生成和引用绑定。KAG 不生成最终业务答案，也不改变 SQL 问数、默认路由或跨源对象确认流程。

`retrieval_mode` 是检索策略选择，不是新的问题类型；它只影响文档检索工具。纯问数、澄清和其他非文档工具不得因为该字段调用 KAG。模型配置与检索模式相互独立。

## 2. 请求字段

`AskRequest` 新增可选字段：

| 字段 | 类型与默认值 | 含义 |
|---|---|---|
| `retrieval_mode` | `"standard"` 或 `"deep"`；缺省为 `"standard"` | `standard` 只使用项目 RAG；`deep` 在项目 RAG 候选之外请求 KAG 候选。 |

请求示例：

```json
{
  "question": "这项服务涉及哪些文件中的履约要求？",
  "session_id": "session-id",
  "retrieval_mode": "deep"
}
```

标准请求应省略 `retrieval_mode`，依赖服务端默认值。这样旧客户端继续按原请求体工作，新前端也不会给旧版严格校验的服务发送未知字段。仅深度请求显式发送 `"retrieval_mode": "deep"`。服务端拒绝其他取值。

该字段可用于 `/api/ask` 和 `/api/ask/stream`。两种接口选择相同的文档检索策略；流式阶段只反映实际执行事件，不得在 KAG 尚未返回时显示补充完成。

## 3. 就绪状态接口

`GET /api/kag/status` 在现有登录校验下返回最小化状态：

```json
{
  "ready": false,
  "status": "unavailable",
  "reason_code": "index_not_ready"
}
```

`ready` 只表示本机 KAG 服务、运行环境和当前语料索引通过适配器就绪检查，不代表检索质量、答案质量或引用已验收。响应不得包含本地路径、服务密钥、连接串、堆栈或原始日志。前端仅在 `ready=true` 时允许选择深度检索；状态接口不可用时按未就绪处理。

## 4. 执行与响应约束

1. `standard` 路径保持原项目 RAG 行为，KAG 调用数为零。
2. `deep` 仅在文档检索工具中调用 KAG 候选适配器；候选必须映射到本轮许可语料及规范原文位置。
3. 项目合并 RAG 与 KAG 候选、去重并统一重排，再由项目模型生成答案。KAG 自带答案、解释文本和未经原文核对的图谱关系不能替代项目生成或引用。
4. 最终 `refs` 使用项目规范文档身份与本轮原文坐标。无法唯一映射、哈希不一致或区间回切不一致的候选不能作为支持性引用。
5. `AskResponse` 主体结构沿用 v0.5。深度请求的 `trace` 可以记录实际发生的 `kag_supplement` 与联合排序阶段；未执行的阶段不得伪装成已完成。
6. KAG 不可用、失败、部分返回或超时须保留可诊断状态。若项目 RAG 候选仍足以回答，可返回项目 RAG 答案并明确标出补充失败；不得把回退结果标成 KAG 成功。

## 5. 前端行为

- 默认选择“标准检索”，不改变用户既有模型配置。
- “深度检索（RAG + KAG）”是手动可选路线，仅对文档问答生效；它不成为默认路由。
- KAG 未就绪时禁用深度选项并显示安全原因；不隐藏标准 RAG 入口。
- 深度检索会增加等待时间，界面需提示；实际处理记录按服务端 trace 展示。
- 架构导览应标为“可选路线·验证中”，不得写成已接入默认链路或已通过效果验收。

## 6. 兼容与安全

- 缺省值为 `standard`，旧请求体不变；标准前端请求省略字段。
- 新后端仍接受旧请求；深度请求只由能够提供就绪状态的新前端发送。
- 字段不得改变 SQL 白名单、只读校验、鉴权、资料权限、会话隔离和跨源早停行为。
- 状态与诊断信息不含密钥、完整本地路径、提示词或原始异常。
- 新增该字段属于公共请求契约变更；冻结前需团队同步，并分别验证同步、流式和旧请求兼容性。
