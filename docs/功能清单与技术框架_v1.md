## 二、中级任务的选法（重要）

**原则：选"主链路本来就必须做的环节"，而不是另起炉灶。**

| 中级任务 | 是否主链路必经 | 结论 |
|---|---|---|
| 1 要素精准识别与问题改写 | 是（别名/纠错不解决，准确率上不去） | **选**，零额外成本 |
| 4 精准表定位 Schema Linking | 是（不解决，多表全错） | **选**，零额外成本 |
| 7 不标准目录结构鲁棒识别 | 是（不解决，切片就废） | **选**，零额外成本 |
| 3 智能语义校验与澄清 | 半必经（多轮交互与"澄清反问"必需） | **选**（2026-09-24 更新） |
| 8 文档复杂度评估 | 否，需新增检测器 | 备选（未选） |
| 9 文档质量综合评估 | 否，需新增检测器 | **决赛备选第 6 个（暂不选）** |
| 2 无 few-shot 要素提取 | 否，研究性 | 决赛高级任务弹药 |
| 5 高质量多表关联 NL2SQL | 是（NL2SQL 全链路一环） | **选**（2026-09-24 更新）；同时是初赛"NL2SQL 执行准确率"10 分的主战场 |
| 6 文档公式识别与计算 | 否，难度最高 | 决赛 |

**组合（2026-09-24 更新）：1 + 3 + 4 + 5 + 7 共五个**——全部落在两条主链路的必经环节上，等于把已经在做的事做到可举证。
初赛每个任务 5 分、上限 15 分，三项（1+4+7）即可拿满档位；决赛「广度与深度」**5 个及以上才满 15 分**，「攻克质量」10 分看相对于基础方案的改进幅度与独创性——五个同时支撑这两项。任务 9 为**决赛备选第 6 个**（暂不选）。

## 三、项目框架：分层与技术选型

### 3.1 五层结构

```
交互层   对话页 / 溯源页 / 跑分看板
   ↓ HTTP  /api/ask  {question, session_id} → {answer, trace, refs, sql, need_clarify}
编排层   意图路由 → 任务规划 → 工具调度 → trace 埋点 → 澄清 → 多轮记忆
   ↓ 统一工具签名  tool(input) → ToolResult{data, trace, refs}
工具层   NL2SQL 工具                    ｜  RAG 工具
   ↓              ↓
数据层   业务库 + pgvector               ｜  文档语料与索引  ｜  评测集
模型层   国产 LLM API ｜ bge 本地小模型 ｜ RapidOCR ｜ OpenCV
```

### 3.2 关键决策与理由

| # | 决策点 | 选项 | 建议 | 理由 |
|---|---|---|---|---|
| D1 | 后端框架 | FastAPI / Flask / Django | **FastAPI + pydantic v2** | pydantic 天然做契约校验；自动生成 OpenAPI；async 适合并发调 LLM |
| D2 | Agent 编排 | 自研 / LangChain / LangGraph | **自研轻量编排（约 300–500 行）** | 见下方「重要判断 ①」 |
| D3 | 编排范式 | 单智能体+工具 / 多智能体 | **单智能体 + 工具调用** | 3 人 5 周上多智能体是自杀；多智能体留作决赛「工程化创新」加分 |
| D4 | 业务数据库 | PostgreSQL / MySQL / SQLite | **PostgreSQL（Docker）** | 题面直接给了 `chriseaton/adventureworks:postgres` 镜像，跟着走省事 |
| D5 | SQL 校验 | 正则黑名单 / **sqlglot AST** | **sqlglot** | 准确率与安全闸门共用同一个库；方言转换顺带为信创适配留口 |
| D6 | 向量存储 | pgvector / faiss / Milvus / Chroma | **pgvector 为主，faiss 为备** | 与 PG 同容器，少一个组件，评委更容易一键跑起来 |
| D7 | 大模型 | 国产 API / 本地开源 / 混合 | **国产 API 做生成 + bge 本地做向量与重排** | 题面明确"大模型建议订购国产 Token，小模型采用开源产品"；本地小模型还省 API 成本 |
| D8 | OCR | 商业云 API / Sudden **RapidOCR** | **RapidOCR / PaddleOCR（离线）** | 评委是中电云/奇安信，信创方向上不要答"用了海外云 OCR" |
| D9 | 前端 | Vue 3 + Vite / Streamlit | **看队伍技能**：有人会 Vue 就上 Vue，否则 Streamlit | Vue 能拿满 Demo 5 分；Streamlit 通常 3–4 分，差 1–2 分但省 3 人日 |
| D10 | 可解释性载体 | 模型思维链 / 代码埋点 trace | **代码埋点** | 见下方「重要判断 ②」 |
| D11 | 仓库形态 | monorepo / 多仓库 | **monorepo** | 三人协作、接口变更频繁，单仓库最省沟通成本 |
| D12 | 部署 | docker-compose / 手工 | **docker-compose 一键起** | "可执行 Demo 的快速启动脚本"是提交硬要求 |
| D13 | 评测 | 自研 runner / MLflow 等 | **自研轻量 runner（一个脚本 + JSON 输出）** | 不引重框架；跑分要快、要能每轮都跑 |

### 3.3 三条重要判断（会显著影响成败）

**① 不要一上来就用 LangChain / LlamaIndex 全家桶。**
理由不是"手写更高贵"，而是：**框架能省掉的是通用的工具调用循环，而我们要交付的是业务级 trace**——`Ref` 要带文档 / 页码 / 章节路径 / 字符偏移，这套字段框架完全不认识，绕一圈仍要自己写埋点；出问题时也分不清是框架的错还是自己的错。自研编排 300–500 行足够，且完全可控。**如果队里有人熟 LangGraph 可以用 LangGraph**（1.0 起用显式 typed state，每个节点可读可写、可持久化，天然产出结构化 trace），但避开已弃用的 `AgentExecutor`。

> 口径更新（2026-09-17）：LangChain 1.0 与 LangGraph 1.0 于 2025-10-22 同时 GA。LangChain 已重新定位为 agent harness（主 API `create_agent`，内部运行 LangGraph 运行时），旧 chains 与 `AgentExecutor` 移入 `langchain-classic` 包并弃用。**上文原先"框架 callback 是黑盒、需二次逆向映射"的表述已按此修正**——LangGraph 的显式状态对 trace 恰恰是友好的，真正的问题不在黑盒，而在"框架替不了业务级 trace 字段"。

**② 可解释性绝不能用 LLM 的思维链充当。**
评分要的是"推理链路、工具调用链、数据来源、可溯源证据"——这是**确定性的事实记录**。让模型自己叙述"我是怎么想的"，既不可验证也容易是编的（模型会事后合理化）。所以 trace 必须在代码里埋点录制：哪一步调了什么工具、入参出参是什么、耗时多少、命中哪张表哪个字段、引用了哪份文档哪一页。**这一条做对了，可解释性 5 分 + 溯源可信度全都有了。**

**③ 数据层要留一层"方言适配"。**
初赛用 PostgreSQL，但赛道方向是"国产化网信系统"，决赛评委很可能会问"能不能换成达梦/人大金仓"。用 sqlglot 把 SQL 生成与执行方言解耦，将来换库只是换一个 dialect 参数——这是**几乎零成本的决赛期权**。

## 四、下一步要定的三件事（决定后即可进入分工细化）

1. **前端走 Vue 还是 Streamlit** —— 取决于你们队里有没有人会 Vue。
2. **算力与 Token 预算** —— 有没有指导老师/实验室资源？国产 API 走哪家？这决定能不能跑重排模型和做多轮评测。
3. **数据库选 Chinook 还是 AdventureWorks** —— 建议 **Chinook 打底 + AdventureWorks 做复杂案例**（题面推荐两者，起手用 Chinook 跑通，多表难题用 AdventureWorks 展示）。
